## Codebase Patterns
- Il progetto Laravel/Filament vive in `../../orchestrator` rispetto a questa cartella `scripts/ralph`
  (working dir di questo script), NON qui — sempre `cd` lì prima di git/composer/artisan.
- Quality gate di questo progetto: `vendor/bin/pint --test` (lint), `vendor/bin/phpstan analyse
  --memory-limit=1G` (typecheck), `vendor/bin/pest` (test). Su host servono SEMPRE `php -d
  memory_limit=1G` davanti a `vendor/bin/pest`/`phpstan` (il default CLI 128M non basta per la suite
  completa) — nota bene: passare `-d` a `php artisan test` non funziona (spawna un sotto-processo che non
  eredita l'ini), invocare `vendor/bin/pest` direttamente.
- Sull'host la suite completa ha SEMPRE 10 test rossi noti e ambientali (mancanza di `pdflatex`/
  `csquotes.sty`): tutti in `Collaudo*Test`/`LatexPdfCompilerTest`. Non è una regressione — confermato
  identico anche su `git stash` del proprio diff.
- Per una Filament Resource condivisa fra staff e customer, il gruppo di navigazione va reso dinamico con
  `public static function getNavigationGroup(): string|UnitEnum|null` (ramifica su
  `Auth::user()?->hasRole(...)`), MAI lasciato come proprietà statica `$navigationGroup` (quella è
  condivisa da ogni ruolo). Dettagli completi in `CLAUDE.md` → "Gruppo di navigazione condiviso
  staff/cliente".
- Verificare una story di navigazione in browser significa guardare l'INTERA sidebar per il ruolo target,
  non solo le voci elencate nell'AC: un `NavigationItem` registrato globalmente in `AdminPanelProvider`
  (es. "Mailpit") può violare silenziosamente un AC su un ruolo mai considerato dalla sua story originale.
- Docker locale: `docker ps` mostra `orchestrator-v2-app-1`/`orchestrator-v2-web-1` (nginx su
  `localhost:8080`) già in esecuzione con bind-mount del repo — utile per verifica browser reale senza
  `artisan serve` (che fallisce: `.env` punta a host Docker `db`, irraggiungibile da fuori container).
  `docker exec orchestrator-v2-app-1 php artisan tinker --execute="..."` per creare/pulire utenti di test.
- Verifica browser senza MCP disponibile: `npx --yes playwright install chromium --with-deps` seguito da
  uno script Node ad-hoc (`chromium.launch()` + screenshot) contro `localhost:8080` funziona bene come
  fallback quando nessun tool MCP di browser è configurato in sessione — impostare una password via
  tinker (`$user->password = bcrypt(...)`) per poter fare login reale dal form invece di bypassarlo.
- Filament 4 Global Search: `getGlobalSearchEloquentQuery()` di default delega a `static::getEloquentQuery()`
  — se una Resource ha già uno scoping Policy lì (es. `TicketResource::getEloquentQuery()` ->
  `Ticket::scopeVisibleTo()`), la ricerca globale eredita lo scoping automaticamente, NESSUN override
  necessario. `getGloballySearchableAttributes()` supporta dot-notation per relazioni (es.
  `'requester.name'`, `'messages.body_text'`) — Filament genera da solo `orWhereHas(...)`, gestisce
  case-insensitive/driver differences internamente, non serve scrivere SQL raw nella query Eloquent:
  l'indice full-text Postgres (`to_tsvector`) resta confinato alla sola migration per le performance, mai
  nella query stessa (altrimenti si rompe su sqlite in test).
- `TicketResource` è l'UNICA voce di menu per i ticket (US-110, AC #1: "nessuna sottoclasse per
  filtro", tutte le viste di stato sono tab di `ListTickets`). Una story che chiede badge/voci "per
  stato" (es. US-604 "In attesa"/"Problemi"/"Da testare") non può creare tre Resource/Page separate
  senza violare quel vincolo: la soluzione adottata è UN SOLO `getNavigationBadge()` con i conteggi
  combinati e `getNavigationBadgeTooltip()` per il dettaglio per categoria — non tre voci di menu
  distinte. Interpretazione applicata quando l'architettura a Resource singola confligge con un AC
  scritto pensando a più voci di menu.
- Interpolazione `${VAR}` nei file `.env`/`.env.example`: si risolve SOLO se `VAR` è definito PRIMA
  nello stesso file (parser single-pass di phpdotenv) — riferirsi a una variabile definita più in basso
  (es. `APP_PORT`, definito in fondo al file nella sezione Docker) produce un'interpolazione vuota senza
  errore. Verificare sempre l'ordine, o usare un valore letterale.
- Nessuna pagina Filament di questo repo usava un form editabile "vero" (stato + salvataggio) prima di
  US-605: per un bisogno semplice (lista di toggle/preferenze), niente Filament Schema/`InteractsWithForms`
  — bastano proprietà Livewire pubbliche + `wire:model.live` + blade custom (`<x-filament::input.checkbox>`,
  `<x-filament::button wire:click="...">`), stesso stile "custom blade + metodi" già in uso da
  `CustomerDashboard`. Il Form builder completo di Filament 4 (visto in `Filament\Auth\Pages\EditProfile`
  del vendor) è overkill per un semplice elenco di booleani.
- Una pagina di autenticazione Filament (Login/EditProfile/ecc.) con `$view` completamente custom (qui:
  `App\Filament\Auth\Pages\Login`, brand "Montagna Servizi") bypassa qualunque meccanismo condizionale nativo
  reso normalmente da `content(Schema $schema)` — inclusa la sfida MFA (`multiFactorChallengeForm`), mostrata
  solo se il blade la controlla esplicitamente (`@if ($this->userUndertakingMultiFactorAuthentication)`,
  poi `{{ $this->multiFactorChallengeForm }}`: una `Schema` Filament implementa `Htmlable`, si stampa con
  `{{ }}`). `actingAs()` nei test Pest bypassa `Login::authenticate()` interamente: NON basta per verificare
  che la sfida sia effettivamente mostrata/completabile, serve un test con `Livewire::test(Login::class)`
  che chiama `authenticate()` due volte (password, poi codice). Verificato SOLO in browser la prima volta —
  vedi `CLAUDE.md` → "MFA nativa Filament per ruolo" per il dettaglio completo, incluso il gotcha di timing
  di `Panel::multiFactorAuthentication(isRequired: ...)` (valutato al boot delle route, prima che la sessione
  esista: mai una closure che legge `Auth::user()` lì, la granularità per-ruolo va in un middleware custom
  valutato a runtime).
- Test di regressione "nessuna N+1" con `DB::enableQueryLog()`/`getQueryLog()`: `DB::disableQueryLog()`
  NON svuota il log, solo ferma la registrazione — misurare due volte nella stessa run (dataset piccolo vs
  grande) senza `DB::flushQueryLog()` fra le due finestre fa sommare i conteggi (falso N+1) invece di
  confrontarli. Pattern corretto: `enableQueryLog()` → azione → `count(getQueryLog())` → `flushQueryLog()`
  → `disableQueryLog()`, ripetuto per ciascuna misura, con `disableQueryLog()` anche durante il seeding fra
  le due misure (altrimenti le query di setup/factory finiscono nel conteggio). Per isolare il costo di un
  singolo metodo di una Filament Page (qui `WorkBoard::columns()`) da quello dell'intero ciclo di vita
  Livewire (mount+render, che in questo caso esegue ANCHE `assigneeOptions()`/`recentActivity()`), istanziare
  la Page direttamente (`new WorkBoard()`) invece di `Livewire::test(...)->instance()`: quest'ultimo va bene
  per i test di correttezza (già usato altrove in `WorkBoardTest.php`), non per isolare il conteggio query
  di un solo metodo. Attenzione anche alla cache dei permessi: `$user->can(...)` dentro uno scope (qui
  `Ticket::scopeVisibleTo()`) carica/cachea le relazioni roles/permissions sul model Eloquent al primo
  utilizzo — una chiamata di "riscaldamento" prima della prima misura evita che quella query una-tantum
  sballi il confronto fra dataset piccolo e grande.
- Quando una story chiede di "verificare il comportamento v1 prima di riprodurlo" (nota "Q" del PRD
  principale), `v1dumps/orchestrator-v1-backup-20260726.tar.gz` contiene l'INTERO codice applicativo v1
  (non solo un dump Postgres): `tar -xzf v1dumps/*.tar.gz 'orchestrator/app' 'orchestrator/routes'
  'orchestrator/database/migrations'` (BSD tar su macOS supporta i pattern senza `--wildcards`) in una
  directory temporanea, poi `grep -rli` sul termine cercato, PRIMA di concludere "non recuperabile con
  certezza" e ripiegare sulla lettura conservativa. Verificato concretamente per US-611
  (`tickets:archive-scrum`): nessun comando/colonna di archiviazione esiste nel v1 (solo tre viste Nova
  "Archived*" in sola lettura filtrate per `status`), quindi il ripiego conservativo era l'unica opzione
  corretta — ma la verifica va fatta comunque, non assunta.
