# Orchestrator v2 — note per agenti

Repository Laravel 13 + Filament 4 per Montagna Servizi. Spec completa: `../PRD-ORCHESTRATOR-V2.md`.
Piano e story: `../scripts/ralph/prd.json`. Log di avanzamento: `../scripts/ralph/progress.txt`.

## Convenzioni stabilite in Fase 0

- Stack: PHP ^8.4, Laravel 13, Filament 4 (`^4.0`, mai la beta v5).
- Test runner: **Pest 4.x** (non 3.x: `pestphp/pest-plugin-laravel` 3.x non supporta Laravel 13). Test in sintassi Pest (`test('...', function () {...})`), non classi PHPUnit.
- Ogni file PHP scaffoldato inizia con `declare(strict_types=1);` subito dopo `<?php`.
- Struttura a moduli sotto `app/`: `Domain/<Modulo>/{Models,Enums,Actions,...}`, `Import/{Stages,Mappers,Parsers,Validation}`, `Filament/{Resources,Pages,Widgets,Providers}`, `Support/`. Non aggiungere codice di dominio fuori da questa struttura.
- `app/Filament/Providers/AdminPanelProvider.php` (namespace `App\Filament\Providers`) — **non** `app/Providers/Filament/` (quello è il default dell'installer Filament, va spostato).
- Qualità: `composer run lint` (Pint, preset laravel), `composer run analyse` (Larastan livello 6, richiede `--memory-limit=1G` perché il default PHP CLI di 128M non basta), `php artisan test` (Pest).
- Niente business logic negli hook Eloquent (`boot()`/`booted()`/Observer) — vedi PRD §4.4 A1. Ogni mutazione passa da una Action esplicita.
- Enum sempre backed e castati, mai confronti su stringhe grezze (PRD §4.4 A4).
- Pacchetti vietati (non installare mai): `spatie/laravel-google-calendar`, `spatie/laravel-translatable`, `overtrue/laravel-favorite`, `filament-shield`.

## Ambiente locale vs Docker

Lo sviluppo di scaffold è stato verificato con PHP 8.5 locale (compatibile con il vincolo `^8.4`), ma il target Docker/produzione (US-002) è PHP 8.4-FPM: il Dockerfile deve pinnare 8.4, non assumere la versione locale dell'agente.

`docker-compose.yml` ha un `name: orchestrator-v2` esplicito in cima: senza di questo, Compose deriva il nome progetto dalla directory (`orchestrator`), che può collidere con altri stack Docker Compose presenti sulla stessa macchina host. Non rimuovere quel campo. Prima di un `docker compose down`/`rm` verificare sempre `docker ps -a` per non toccare container di altri progetti.

Se si aggiungono nuove viste Blade custom sotto `resources/views/filament/`, ricordarsi che le direttive `@source` sono già in quel file — non serve aggiungerle altrove.
- Gli asset di brand (`assets/*.png`) NON sono serviti dal web server da quella posizione: una copia va tenuta in `public/images/branding/` (referenziata con `asset(...)` in `AdminPanelProvider` per `brandLogo`/`darkModeBrandLogo`/`favicon`). `assets/` resta la posizione "sorgente" documentata da US-004; `public/images/branding/` è la copia servibile — se il committente fornisce un SVG in futuro, aggiornare entrambe le posizioni.
- Verifica di temi/branding senza browser MCP disponibile: portare su lo stack con `docker compose up -d db redis app web` (senza `mailpit` se la porta `1025` è occupata da uno stack Docker legacy su questa macchina, vedi nota sopra su `docker ps -a`) e ispezionare l'HTML con `curl` (branding/font/link tema in `<head>`), invece di fermarsi al solo `npm run build`.

## Identità / spatie-permission (US-010)

- `App\Models\User` è stato **spostato** in `App\Domain\Identity\Models\User` per rispettare la struttura a moduli (§4.3): qualunque riferimento nuovo (config, factory, seeder, Filament) deve puntare a `App\Domain\Identity\Models\User`, non più `App\Models\User` (la cartella `app/Models/` non esiste più).
- Spostare un modello fuori da `App\Models` rompe **due convenzioni Laravel basate sul namespace**, entrambe da sistemare esplicitamente quando si crea/sposta un modello di dominio:
  1. `HasFactory` prova a indovinare la classe factory dal namespace del modello; se la factory non segue quella convenzione (qui resta in `Database\Factories\UserFactory`, non annidata sotto `Database\Factories\Domain\Identity\Models\`), va aggiunto un override esplicito `protected static function newFactory(): UserFactory` nel modello.
  2. Il contrario: la Factory stessa indovina il modello dal proprio namespace (`Database\Factories\UserFactory` → `App\User` di default); se il modello non è lì, va impostato esplicitamente `protected $model = User::class;` nella classe Factory. Senza questi due fix si ottiene un errore runtime tipo `Class "App\User" not found` (o l'equivalente sul lato factory), non un errore a livello di autoload.
  3. Dopo un `git mv`/spostamento di file di classe, se `composer.json` ha `optimize-autoloader: true` (qui è il caso), rigenerare l'autoload con `composer dump-autoload -o`: altrimenti il classmap ottimizzato punta ancora al vecchio path e l'errore è un fuorviante `include(...): Failed to open stream` sul path vecchio.
- Pattern per un indice funzionale case-insensitive su una colonna (qui `users.email`, §5.2): `DB::statement('create index <nome> on <tabella> (lower(<colonna>))')` dentro la migrazione, dopo lo `Schema::create`. Sintassi portabile sia su Postgres sia su sqlite (usato dai test): non serve un `if` sul driver. Resta un indice separato dal vincolo `unique()` standard sulla colonna (case-sensitive) — non sostituisce l'unique, serve alle query che cercano per `lower(email)`.
- Le tabelle di `spatie/laravel-permission` si pubblicano con `php artisan vendor:publish --provider="Spatie\Permission\PermissionServiceProvider"` (migrazione + `config/permission.php`): **non riscriverle a mano**. Di default `config('permission.teams')` è già `false` e il guard di default (`config('auth.defaults.guard')` = `web`) è già l'unico usato: non serve altra configurazione per rispettare i vincoli di questo progetto (guard unico `web`, niente teams).
- Il modello `User` usa il trait `Spatie\Permission\Traits\HasRoles` (non `filament-shield`, vietato dal PRD): ruoli/permessi vanno creati solo dal seeder (§9.2), mai con `Role::create()`/`Permission::create()` da codice applicativo a runtime.

## Ruoli e permessi — enum (US-011)

- `App\Domain\Identity\Enums\UserRole` (5 case: `Admin`/`Developer`/`Manager`/`Customer`/`Fundraising`) e `App\Domain\Identity\Enums\Permission` (52 case, catalogo completo §9.3) sono la **sorgente di verità**: il seeder di ruoli/permessi (US-018) deve iterare `UserRole::cases()`/`Permission::cases()` per creare le righe Spatie, mai scrivere stringhe letterali. Aggiungere/rimuovere un permesso significa modificare `Permission` qui, non una tabella o un seeder scollegato.
- Naming dei case: `PascalCase` che rispecchia il `value` `<dominio>.<azione>[.<ambito>]` (es. case `TicketManageInternalFields` → value `'ticket.manage-internal-fields'`). Nuovi permessi vanno aggiunti seguendo questa stessa trasformazione (punti/trattini nel value, PascalCase nel nome del case) per restare consistenti.
- `UserRole` implementa `HasLabel`/`HasColor`/`HasIcon` di Filament (badge di ruolo pronti per resource/tabelle: `$role->getColor()` restituisce uno dei nomi di colore già registrati in `AdminPanelProvider`, es. `'danger'`/`'info'`/`'warning'`/`'success'`/`'gray'` — non un hex). `Permission` implementa solo `HasLabel` (colore/icona per 52 permessi granulari non veicolerebbe informazione utile, a differenza dei 5 ruoli).
- Nessuna delle due enum ha una migrazione/tabella propria: sono catalogate solo in PHP; le tabelle Spatie (`roles`/`permissions`/...) restano quelle pubblicate in US-010.

## ETL / dump v1 (US-007+)

- `db_legacy` (Postgres 16, database di appoggio in sola lettura per il dump v1) parte SOLO con `docker compose --profile etl up -d db_legacy` / `make etl-up`, mai con un `docker compose up` normale: non aggiungere `db_legacy` alle dipendenze di default di `app`/`web`/`queue`.
- `bin/load-v1-dump path/to/dump.sql` ripristina il dump in `db_legacy`.
- Comandi ETL (`v1:inspect` — US-008, `v1:import`/`v1:validate` in Fase 2+) leggono da `db_legacy` tramite la connessione Eloquent dedicata `legacy` (`config/database.php`, env `DB_LEGACY_HOST`/`DB_LEGACY_PORT`/`DB_LEGACY_DATABASE`/`DB_LEGACY_USERNAME`/`DB_LEGACY_PASSWORD`), mai riusando la connessione di default `pgsql`. Usare `DB::connection('legacy')->table(...)` (query builder), non Eloquent: le tabelle v1 non hanno (e non devono avere) un Model in questo repo.
- **Dump reali di produzione v1 vanno cercati in `v1dumps/`** (dentro questo repo, `mstickets/orchestrator/v1dumps/`, in `.gitignore`: mai committare `.sql`/`.sql.gz`, troppo grandi/sensibili). Il più recente conosciuto a oggi (26/07/2026) è `v1dumps/production_dump_20260726_101158.sql.gz` (scaricato via `scp` dall'host di produzione, alias SSH `ms` in `~/.ssh/config`), usato per il report `storage/app/import/inspect-20260726_101916.md`. Esiste anche un dump più vecchio fuori dal repo, `~/Documents/docker/orchestrator/storage/app/database/last-dump.sql` (19/02/2026, usato per il primo report di US-008, `inspect-20260725_225710.md`): non è più il riferimento, ma resta lì come storico. **Prima di rieseguire `v1:inspect` per una fase successiva**, verificare se il committente ha fornito un dump ancora più recente e preferire sempre quello con la data più alta.
- **Convenzione `v1dumps/latest.sql` (design ETL real data seeding, US-R02)**: un puntatore fisso (symlink o copia, es. `ln -sf production_dump_YYYYMMDD_HHMMSS.sql v1dumps/latest.sql`) all'ultimo dump reale, mantenuto **manualmente** da un umano con accesso SSH a produzione — nessuno script (né `make setup` né il deploy UAT) lo aggiorna da solo. `make setup` (vedi sezione US-024 sotto) e il deploy UAT (US-R06) leggono sempre questo path fisso, mai un pattern di data: qualunque script che debba "usare l'ultimo dump" va scritto contro `v1dumps/latest.sql`, non contro l'ultimo file per data di modifica.
- **Il volume `db_legacy_data` persiste tra un `docker compose --profile etl down`/`up` e l'altro** (down senza `-v` non lo rimuove): se si ricarica un dump diverso da quello già presente, resettare prima lo schema (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;` via `psql`), altrimenti il restore fallisce su oggetti già esistenti invece di ripartire pulito. Il ruolo Postgres `orchestrator` (richiesto dagli `ALTER ... OWNER TO` nel dump) va creato solo se non esiste già (verificare con `\du` prima).
- **Fermare `db_legacy` con `docker compose --profile etl stop db_legacy`, mai con `down`**, se gli altri servizi del progetto (`app`/`web`/`db`/`redis`/...) sono in uso attivo: `down` fermerebbe l'intero stack, non solo `db_legacy`, condividendo la stessa rete Compose.
- **Restore di un dump reale (pg_dump completo) contro `db_legacy` (`postgres:16-alpine` vanilla) fallisce di default** per due motivi indipendenti, entrambi non legati alle tabelle applicative:
  1. Il dump contiene `ALTER ... OWNER TO orchestrator` (il ruolo Postgres della VM sorgente): va creato prima con `CREATE ROLE orchestrator;` dentro `db_legacy`, altrimenti con `ON_ERROR_STOP=1` (usato da `bin/load-v1-dump`) il restore si ferma al primissimo statement e non crea NESSUNA tabella.
  2. Il cluster sorgente ha PostGIS installato (schemi `tiger`/`tiger_data`/`topology`, estensioni `postgis`/`postgis_topology`/`postgis_tiger_geocoder`) che `postgres:16-alpine` non ha: questi statement falliscono sempre, ma sono innocui (nessuna tabella applicativa dipende da PostGIS). Per un restore una-tantum di verifica, ricreare lo schema pulito (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`) e ripristinare con `psql` **senza** `-v ON_ERROR_STOP=1`, poi controllare con `\dt`/conteggi riga che le tabelle mstickets (stories, users, story_logs, ecc.) siano presenti — non serve investire tempo a rendere l'intero dump "pulito", il rumore PostGIS è atteso e documentato qui, non nel codice applicativo.
- **`Storage::disk('local')` NON scrive in `storage/app/`**: in Laravel 11+ il disco `local` di default ha `root` = `storage_path('app/private')` (`config/filesystems.php`). Se una story richiede esplicitamente un path letterale sotto `storage/app/...` (come l'AC di US-008 per `storage/app/import/inspect-<timestamp>.md`), non usare `Storage::disk('local')`: costruire un disco dedicato con `Storage::build(['driver' => 'local', 'root' => storage_path('app')])` (vedi `V1InspectCommand::appDisk()`).
- `storage/app/.gitignore` ignora tutto tranne `private/`, `public/`, `.gitignore`: qualunque nuova sottocartella di `storage/app/` che deve finire nel repository (es. `import/` con i report di `v1:inspect`) richiede un'eccezione esplicita (`!import/` + `!import/**`) in quel file, altrimenti `git add` non la traccia silenziosamente.
- **Scaffold di `v1:import` (US-201, `App\Import\Stages\*`)**: uno stage reale implementa `App\Import\Stages\Contracts\ImportStage` (nome, dipendenze dichiarate, `run(ImportContext): StageResult`) e si registra elencando la propria classe in `config('import.stages')` — nessuna story successiva deve toccare `V1ImportCommand`, `ImportRunner` o `ImportStageRegistry`, solo quel file di config. `ImportRunner::plan()` risolve l'ordine di esecuzione dalle dipendenze (ordinamento topologico): `--from-stage=X` esegue X e tutto ciò che segue nell'ordine completo (le dipendenze precedenti sono assunte già eseguite in una sessione precedente, punto di ripresa dopo un errore parziale); `--stage=X` esegue **solo** X e fallisce esplicitamente se X dichiara anche una sola dipendenza (usare `--from-stage` in quel caso). Vedi il commento in testa a `ImportRunner` per il ragionamento completo — è una scelta di design non ovvia dalla sola lettura del PRD.
- I test del runner usano stage fittizi (`Tests\Feature\Import\Fixtures\FakeImportStage`, parametrizzato con nome/dipendenze/closure) invece di una classe fittizia per scenario: nessuno stage reale esiste ancora, quindi ogni story che ne aggiunge uno reale scrive i propri test contro la sua classe, non contro le fixture del runner.
- **Come feature-testare uno stage reale senza `db_legacy` in esecuzione (US-202+)**: il trait `Tests\Feature\Import\Fixtures\InteractsWithLegacyDatabase` (metodo `useSqliteLegacyConnection()`) riconfigura a runtime la connessione `legacy` da pgsql a sqlite in-memory (`config()->set('database.connections.legacy', ...)` + `DB::purge('legacy')`). Il test poi crea con `Schema::connection('legacy')->create('nome_tabella_v1', ...)` solo le colonne v1 di cui lo stage ha bisogno e ci inserisce righe fixture: lo stage gira così per intero (lettura v1 + scrittura v2 + idempotenza) dentro `php artisan test`/CI, aggirando il limite già noto della connessione `legacy` reale. Riusare questo trait per ogni stage successivo invece di re-inventare la riconfigurazione.
- **Schema reale delle tabelle v1**: dato che `db_legacy` non gira in locale/CI, per conoscere le colonne esatte di una tabella v1 (invece di indovinarle dal PRD) leggere il `CREATE TABLE public.<tabella> (...)` direttamente nel dump SQL non compresso già presente in `v1dumps/production_dump_20260726_101158.sql` (`grep -n "CREATE TABLE public.<tabella>"` poi leggere le righe seguenti) — più affidabile del solo report `v1:inspect` (che riporta conteggi/valori distinti, non l'elenco colonne). Esempio già verificato per `users`: **non** ha `deactivated_at` né `deleted_at` (il v1 non ha il concetto di disattivazione/soft-delete utente, §11.5 del PRD principale, riga 1313), ha invece `activity_report_language` (→ `locale` v2), `google_drive_url`/`google_drive_budget_url` (→ `drive_url`/`drive_budget_url` v2) e `help_desk_chat`/`help_desk_chat_url` (fuori mapping: feature non confermata, Q17 del PRD).
- **Slug provvisorio per uno stage che importa in una tabella con `slug` unique/non-null e nessuna colonna v1 equivalente** (US-204, `documentation_pages`/`tags`): trait `App\Import\Stages\Concerns\GeneratesProvisionalSlugs` (metodo `uniqueSlug(string $source, array &$existingSlugs)`), che genera `Str::slug($source)` con suffisso numerico sui duplicati confrontando contro un array di slug già assegnati (precaricato una volta prima del loop, poi aggiornato per riferimento a ogni insert). Lo slug è generato **solo in fase di insert**, mai ricalcolato quando la riga esiste già e viene aggiornata: il ricalcolo definitivo/idempotente è delegato allo stage `derive` (US-215). Riusare questo trait per ogni futuro stage con lo stesso bisogno, non re-implementare la disambiguazione.
- **Il morph polimorfico v1 `tags.taggable_id`/`taggable_type` (colonne dirette della tabella `tags`) è diverso dalla pivot `taggables`** (che collega invece `Story`↔`Tag` e alimenta lo stage `ticket_tags`, US-207): non confonderli quando si legge lo schema v1. Solo `tags.taggable_type = 'App\Models\Documentation'` sopravvive in v2 come FK esplicita `tags.documentation_id`; qualunque altro `taggable_type` (v1 aveva anche `Project`/`Customer`/`App`) collassa a tag semplice con `documentation_id = null`, contato in un unico warning aggregato di fine stage (stesso pattern di `RolesPermissionsStage` per gli id `developer`), non un warning per riga.
- **Colonne derivate una-tantum al primo insert, mai ricalcolate su un ticket già importato** (`TicketsStage`, US-205: `status_changed_at`/`previous_status` ricostruiti da `story_logs`, `worked_minutes` fissato a 0): l'attributo va incluso nell'array passato a `insert()` ma **escluso** dall'array `$attributes` usato per il confronto/`update()` di una riga già esistente, altrimenti una riesecuzione idempotente dello stage sovrascriverebbe silenziosamente valori nel frattempo mantenuti dall'applicazione (status_changed_at aggiornato da un vero cambio di stato, worked_minutes ricalcolato da `derive`/US-215) con la ricostruzione storica una-tantum. Stesso principio di `GeneratesProvisionalSlugs` (slug generato solo in insert) ma qui senza un trait dedicato, perché la logica di derivazione (lettura `story_logs`) è specifica dello stage. Riusare questa distinzione insert-only per qualunque futura colonna "ricostruita dai log, poi mantenuta dall'app".
- **`stories.user_id`/`creator_id`/`tester_id` → `tickets.assignee_id`/`requester_id`/`tester_id`** (§0.3 del PRD principale, riga 67-68): i nomi non corrispondono 1:1 (`user_id` v1 è il developer assegnato, non un utente generico) — verificare sempre la tabella di glossario §0.3 prima di assumere una corrispondenza per nome colonna.
- **Idempotenza via `App\Import\Models\ImportMapping` (usata per la prima volta da `TicketLogsStage`, US-208)**: per uno stage che crea righe v2 **senza** una chiave naturale/composita su cui ri-matchare (a differenza delle pivot `ticket_tag`/`ticket_participants`/`organization_user`, idempotenti su `(a_id, b_id)`), registrare `ImportMapping::create(['source_table' => 'nome_tabella_v1', 'source_key' => (string) $row->id, 'target_table' => 'nome_tabella_v2', 'target_id' => $newId])` a ogni insert, e precaricare una volta per stage l'insieme delle `source_key` già mappate (`array_flip(ImportMapping::query()->where('source_table', ...)->where('target_table', ...)->pluck('source_key')->all())`) per uno skip idempotente O(1) per riga, mai una query per riga. Rilevante per gli stage successivi con lo stesso bisogno (`ticket_messages`/US-210 su `(story_id, indice, hash)`, non solo `story_logs.id`).
- **`story_logs.changes` (JSON libero v1) → colonne esplicite v2, priorità mutuamente esclusiva** (`TicketLogsStage`, US-208): `status` presente vince su `user_id` presente, che vince sul fallback generico `event = updated` con il diff residuo in `changes` (mai il corpo di `description`, solo il marker `'changed'`, stesso principio di `TicketLogChanges::descriptionChanged()` anche se lo stage scrive `ticket_logs` con `DB::table(...)->insert()`, non tramite quel DTO/Eloquent, per restare coerente con lo stile già adottato dagli altri stage). I log con **sola** chiave `watch` sono esclusi da questo stage (alimentano `ticket_views`, US-209): stessa tabella sorgente `story_logs`, filtro mutuamente esclusivo, da verificare quando si implementa US-209 che le due letture non si sovrappongano.
- **Stage di aggregazione (molte righe sorgente → una riga v2), non un mapping 1:1** (`TicketViewsStage`, US-209): stesso `story_logs` di `TicketLogsStage` (US-208), ma filtro complementare (`array_keys($changes) === ['watch']`, non `!==`) — un test dedicato (`ticket_logs and ticket_views read the same story_logs input with zero overlap`) lancia entrambi gli stage sullo stesso set di righe e verifica che la somma di `ticket_logs`+`ticket_views` create coincida col totale, mai una riga contata da entrambi. Le righe `watch` sono raggruppate **in memoria** per `(ticket_id, user_id, date(viewed_at))` prima di scrivere: `view_count` = conteggio del gruppo, `last_viewed_at` = timestamp massimo del gruppo (non l'ultimo letto, il più recente in valore). Idempotenza sul vincolo unique applicativo già esistente (`ticket_id, user_id, viewed_on`), non su `ImportMapping`: un gruppo il cui `ticket_views` esiste già (riesecuzione) viene saltato per intero, mai un secondo insert né un aggiornamento del `view_count` — corretto perché lo stage non deve mai sovrascrivere visualizzazioni reali registrate dall'app dopo l'import (`RecordTicketView`, US-108) con la ricostruzione storica. Pattern riusabile per qualunque futuro stage "molte righe v1 → una riga v2 aggregata": raggruppare prima in un array PHP chiave→dati, poi un solo controllo di esistenza per gruppo, non per riga sorgente.
- **`stories.customer_request` (conversazione accumulata, `TicketMessagesStage`/US-210, il mapping più delicato)**: nel dump reale, ogni risposta è **prepesa** dall'applicazione v1 con un template HTML fisso e riconoscibile: `"<Autore> ha risposto il: DD-MM-YYYY HH:MM\n <div style='background-color: #XXXXXX; border-left: 4px solid #YYYYYY; padding: 10px 20px;'>...corpo...</div><div style='height: 2px; background-color: #e2e8f0; margin: 20px 0;'></div>"` (colore diverso per ruolo del mittente, verificato nel dump: `#f8f9fa`/`#6c757d` staff, `#fff7e6`/`#ffa940` esterni — irrilevante per il parsing, il regex usa un pattern esadecimale generico). `App\Import\Parsers\CustomerRequestParser::parse()` (puro, senza I/O) riconosce **solo** questo template esatto in sequenza dall'inizio della stringa; qualunque altra forma di conversazione accumulata (email inoltrate in chiaro con intestazioni `Da:`/`Date:`, citazioni Gmail annidate in `<blockquote>` con `"... ha scritto:"`, notifiche di form) non viene scomposta — resta un unico messaggio "originale" con l'HTML integrale. Il contenuto rimasto dopo l'ultimo blocco di risposta è sempre il messaggio più vecchio (il testo con cui il ticket è stato creato): lo stage gli assegna `tickets.requester_id` (già risolto da `TicketsStage`) come autore, mai "non ricavabile". Gli autori dei blocchi di risposta portano solo un nome v1 (mai un id/email): risolti per corrispondenza case-insensitive esatta su `users.name`, **solo se univoca** (un nome duplicato o assente resta `author_id = null`). Verificare sempre `checkdate()` prima di `Carbon::create()` su una data testuale non fidata: quest'ultimo non lancia mai un'eccezione per un giorno fuori range (es. 31 aprile), la trabocca silenziosamente al mese successivo invece di segnalare un timestamp non ricostruibile.

Pattern riusabile per qualunque futuro stage che debba "agganciarsi" a un'entità creata da uno stage precedente ma che potrebbe mancare per alcune righe.
- **`activity_reports.owner_type`/`customer_id`/`organization_id` (v1) → `owner_kind`/`owner_user_id`/`owner_organization_id` (v2), vincolo CHECK già esistente in v2** (`ActivityReportsStage`, US-212): `customer_id` v1 punta in realtà a `users` (§0.3 del PRD, `owner_type = 'customer'` → `owner_kind = 'user'`), non a un'entità "cliente" separata. Nessun test l'ha mai intercettato perché OGNI test di `v1:validate` (inclusa la fixture CI di US-218) girava con lo schema v2 su sqlite: solo la connessione `legacy` era Postgres reale. Fix: `->havingRaw('count(*) > 1')` (nessun alias referenziato, valido su entrambi i driver). **Pattern generale**: qualunque `->having(...)` su un alias di `selectRaw`/`select` va scritto con `havingRaw('<espressione letterale>')`, mai riferendo l'alias — stesso principio di "sintassi Postgres-only mai validata da sqlite" già noto per `setval`/sequenze (US-215), ma qui il problema era l'opposto: una sintassi che sqlite tollera SILENZIOSAMENTE ma Postgres no, non una sintassi che sqlite rifiuta.
- **Il job CI `etl-fixture` (US-218) è stato esteso in US-219 per usare un vero Postgres anche per lo schema v2** (nuovo servizio `db` accanto a `db_legacy`, porta host 5433 per non collidere con `db_legacy` su 5432; env `DB_CONNECTION=pgsql`/`DB_HOST=127.0.0.1`/`DB_PORT=5433` invece di sqlite), proprio perché il bug sopra dimostra che v2-su-sqlite in CI è un angolo cieco reale, non solo teorico. Se una fase futura introduce altro codice ETL con `selectRaw`/aggregazioni SQL dirette, verificarlo sempre anche contro questo job (o manualmente contro un Postgres reale come descritto nel bullet precedente), mai fidarsi della sola suite sqlite.

## Schema — Ticketing (US-012)

- **FK verso una tabella non ancora esistente**: quando un AC richiede una colonna FK verso una tabella che una story successiva creerà (qui: `tickets.fundraising_project_id` → `fundraising_projects`, arriva in US-015; `ticket_messages.email_message_id` → `email_messages`, arriva in US-016; `ticket_tag.tag_id` → `tags`, arriva in US-013), creare la colonna come `unsignedBigInteger` **senza** `->constrained()`/vincolo FK, con un commento che rimanda alla story che introduce la tabella. Quella story successiva deve aggiungere il vincolo FK vero e proprio con una migrazione dedicata (`Schema::table(...)->foreign(...)`), non riscrivere questa migrazione.
- **Indici Postgres-only nelle migrazioni (GIN, full-text)**: `to_tsvector(...)` e gli indici `GIN` (usati su `tickets.title` e `ticket_logs.changes`) non hanno equivalente su sqlite (usato dai test, `phpunit.xml`). Guardia esplicita nella migrazione: `if (Schema::getConnection()->getDriverName() === 'pgsql') { DB::statement(...); }`. Verificare comunque questi `DB::statement` contro Postgres reale (`docker compose up -d db app` + `php artisan migrate:fresh` nel container `app`), non solo su sqlite: la sintassi non viene mai eseguita/validata dai test.
- **`$table->foreignId(...)->constrained()` NON crea un indice standalone su Postgres** (a differenza di MySQL, dove la FK crea un indice implicito): se un AC richiede un indice su una colonna FK isolata (es. `ticket_messages.author_id`), aggiungere sempre un `$table->index('colonna')` esplicito, non fare affidamento su `constrained()`.
- **Colonna `ulid` pubblica separata dalla PK `id` autoincrementale** (§5.2 `ticket_messages`, pattern riusabile per qualunque tabella futura con lo stesso bisogno): usare il trait nativo `Illuminate\Database\Eloquent\Concerns\HasUlids` ma **sovrascrivere `uniqueIds(): array` per restituire `['ulid']`** invece del default (che assume la PK stessa come colonna ulid). Così `id` resta intero autoincrementante (FK/ordinamento) e `ulid` viene generato automaticamente solo se vuoto al momento del `save()` (`HasUniqueIds::setUniqueIds()`, framework core — non è business logic in un hook custom, §4.4 A1 non si applica). `ulid` non è nella lista `#[Fillable]`: per testarne il vincolo unique forzare l'attributo via assegnazione diretta (`$model->ulid = '...'`) o `forceFill()`, non `::create(['ulid' => ...])` (verrebbe ignorato in mass assignment e rigenerato).
- **Prima vera integrazione di `spatie/laravel-medialibrary`** (installato da US-001 ma mai pubblicato): la migrazione `media` e `config/media-library.php` NON esistevano ancora, vanno pubblicati con `php artisan vendor:publish --provider="Spatie\MediaLibrary\MediaLibraryServiceProvider"` **prima** di qualunque migrazione che li referenzia (qui `ticket_messages`, ordinata dopo). Il comando pubblica anche `resources/views/vendor/media-library/*.blade.php` (stub di viste non personalizzate): rimuoverli se non si sta effettivamente personalizzando il rendering, per non lasciare file inutili nel repo.
- Dopo un valore Eloquent `Model::create([...])` con colonne che hanno un **default a livello di database** (es. `status` default `'new'`, `worked_minutes` default `0`) e nessun valore esplicito passato, l'istanza in memoria ha quell'attributo `null` finché non si rilegge dal DB (`->fresh()`/`->refresh()`): Eloquent non conosce il default SQL lato PHP. Nei test che verificano i default, sempre `->fresh()` dopo la `create()`.
- Mappatura colori `TicketStatus::getColor()` (Filament, non hex): dove il mockup (US-004, `docs/design-system.md`) definisce un badge per lo stato, usato quello come riferimento semantico; per i 6 stati senza badge nel mockup, scelta la categoria Filament più vicina all'hex v1 di riferimento (§5.3 del PRD) — vedi commento nell'enum. Se il committente fornirà una palette di stato completa al checkpoint di fine Fase 0, questa mappatura va aggiornata (l'enum resta l'unico posto dove vive).

## Schema — Tag/commesse e Documentazione (US-013)

- **Come completare una FK "differita" annunciata da una story precedente**: quando US-012 ha creato `ticket_tag.tag_id` come `unsignedBigInteger` senza vincolo (perché `tags` non esisteva ancora), questa story ha aggiunto una **migrazione dedicata separata** (`..._add_tag_foreign_key_to_ticket_tag_table.php`, con `Schema::table('ticket_tag', fn ($t) => $t->foreign('tag_id')->references('id')->on('tags')->cascadeOnDelete())` in `up()` e `dropForeign(['tag_id'])` in `down()`), **non** ha modificato la migrazione originale di `ticket_tag`. Stesso pattern da riusare in US-015 (`tickets.fundraising_project_id` → `fundraising_projects`) e US-016 (`ticket_messages.email_message_id` → `email_messages`): una migrazione `add_..._foreign_key_to_..._table` a parte, ordinata dopo la migrazione che crea la tabella target.
- Il vincolo FK differito, una volta aggiunto, va anche **testato con dati reali** (non solo ispezionato via `psql \d`): un test che crea le due righe collegate, verifica la relazione Eloquent, poi `forceDelete()` la riga referenziata e verifica il cascade/nullify lato SQLite (i vincoli FK di SQLite sono abilitati di default in questo progetto, `config/database.php` → `'foreign_key_constraints' => env('DB_FOREIGN_KEYS', true)`, quindi il comportamento è verificabile anche dalla suite `php artisan test`, non solo contro Postgres reale).
- `documentation_pages.category` (`DocumentationCategory`: `internal`/`customer`) implementa solo `HasLabel`, non `HasColor`/`HasIcon`: per un enum a 2 valori senza semantica di stato (a differenza di `TicketStatus`), un colore/icona non aggiungerebbe informazione — stessa scelta già fatta per `Permission` in US-011.
- Anti-pattern esplicito da non riprodurre (§16.2 #13 del PRD): il v1 aveva `Documentation::creator()` verso una colonna `creator_id` inesistente. `DocumentationPage` in questo repo **non ha alcuna colonna/relazione autore**: né l'AC né nessun'altra story la richiedono ancora. Se una story futura avrà bisogno di tracciare l'autore, aggiungere una migrazione `created_by` FK→users nullable esplicita (l'ETL non potrà popolarla sui dati storici, resterà `null`) — non aggiungerla preventivamente senza un bisogno reale.

## Schema — Rendicontazione (US-014)

- **Vincolo CHECK multi-colonna, portabile su Postgres e sqlite**: Blueprint di Laravel non ha un metodo `check()` generico per nessun driver (solo l'helper interno per colonne `enum`, un `varchar check (col in (...))`). Su Postgres un `ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)` via `DB::statement` dopo `Schema::create` funziona normalmente; su **sqlite** (usato dai test) `ALTER TABLE` non supporta `ADD CONSTRAINT` in nessuna forma (verificato: errore di sintassi), quindi il vincolo va **emulato con due trigger** `BEFORE INSERT`/`BEFORE UPDATE` che fanno `SELECT RAISE(ABORT, '...')` quando la condizione è falsa — i trigger si aggiungono liberamente dopo la creazione della tabella (non è un `ALTER TABLE`), e producono la stessa `QueryException` lato applicativo di un vero CHECK Postgres. Vedi `2026_07_26_110000_create_activity_reports_table.php` (`activity_reports_owner_check`) per il pattern completo, riusabile per qualunque futuro vincolo CHECK multi-colonna.
- **Un `unique()` composito su colonne nullable NON basta quando i valori NULL fanno parte della chiave logica**: sia Postgres sia sqlite trattano NULL come distinto da se stesso ai fini di un vincolo `UNIQUE` standard, quindi righe "duplicate" che differiscono solo per una colonna sempre-NULL passano indisturbate (verificato: due insert identici con `owner_organization_id = NULL` sono entrambi accettati da un `$table->unique([...])` letterale). Soluzione: un indice unique su **espressione con `coalesce(colonna, valore_sentinella)`** al posto della colonna nullable, stesso pattern già usato per l'indice funzionale case-insensitive `lower(email)` (US-010) — sintassi identica su Postgres e sqlite, aggiunto con `DB::statement('create unique index ... on ... (coalesce(col, 0), ...)')` dopo `Schema::create`. Riusare per qualunque futura tabella con un vincolo unique che includa colonne FK nullable "a scelta" (pattern owner_kind/owner_*_id).

## Schema — Sottosistema email (US-016)

- **Non confondere il pattern `coalesce()` di US-014 con un AC che dice letteralmente "univoco dove/quando la colonna non è null"**: sono due bisogni opposti. In US-014 il NULL fa parte della chiave logica (owner_user_id NULL è un valore significativo, "non è questo il proprietario") e va normalizzato con `coalesce()` perché altrimenti righe realmente duplicate sfuggirebbero al vincolo. In US-016 invece l'AC di `email_messages` dice esplicitamente "unique (direction, message_id) dove message_id non null" e "unique (imap_folder, imap_uid) per l'inbound": qui il comportamento voluto è che le righe con quella colonna NULL **non partecipino affatto** al controllo di unicità — che è **esattamente** il comportamento nativo di un `$table->unique([...])` letterale (NULL distinto da se stesso), senza bisogno di `coalesce()`/`DB::statement`. Aggiungere un `coalesce()` qui sarebbe stato un bug: avrebbe reso univoche anche le righe con la colonna NULL (es. tutte le righe outbound, che non hanno `imap_folder`/`imap_uid`), facendo fallire il secondo insert outbound. Prima di applicare il pattern coalesce, verificare se l'AC vuole davvero "NULL come valore significativo della chiave" o solo "il vincolo si applica quando il valore è presente" — nel secondo caso basta `unique()` semplice.
- Verificato con `docker compose up -d db app` + `php artisan migrate:fresh --force` + `psql -c "\d email_messages"` che Postgres genera gli unique index compositi attesi (`email_messages_direction_message_id_unique`, `email_messages_imap_folder_imap_uid_unique`) e le tre FK con `ON DELETE SET NULL` (thread_id/ticket_id/user_id) — nessun guard `pgsql`-only necessario in questa story (nessun GIN/full-text, solo `jsonb` semplice su `to`/`cc`/`bcc`/`participants`, già astratto in modo portabile da `$table->jsonb(...)` come in `ticket_logs.changes`).

## Seeder idempotente ruolo → permessi (US-018)

- Pattern riusabile per qualunque "seeder di catalogo" che deve restare idempotente E revocare ciò che sparisce dalla fonte di verità PHP (qui: `RolePermissionSeeder`, matrice §9.4): (1) `firstOrCreate` ogni riga del catalogo enum corrente (permessi, poi ruoli); (2) per ogni ruolo, `$role->syncPermissions([...])` con i nomi attesi — `syncPermissions` è già di per sé idempotente (aggiunge i mancanti, rimuove gli eccedenti sul singolo ruolo) senza bisogno di calcolare il diff a mano; (3) per revocare le righe "orfane" (rimosse dal catalogo enum): `Permission::whereNotIn('name', $catalogoAttuale)->delete()` — il `delete()` su un `Permission`/`Role` di Spatie fa cascade reale a livello DB su `role_has_permissions`/`model_has_permissions` (FK `onDelete('cascade')`, vedi migrazione pubblicata in US-010), quindi non serve staccare manualmente i pivot prima.
- Il catalogo permessi/ruoli è quello degli enum `Permission`/`UserRole` (US-011), mai stringhe sparse nel seeder: la mappa ruolo→permessi vive come `const array` di case enum (non stringhe), convertiti a `->value` solo al momento di chiamare l'API di Spatie.
- Test di un seeder così fatto vanno oltre "gira senza errori": verificare (a) la matrice esatta per ruolo (pluck + sort per confronto stabile), (b) una seconda esecuzione non introduce differenze (stessi conteggi), (c) un permesso/ruolo creato manualmente FUORI dal catalogo enum (simulando "rimosso da un refactor futuro") viene effettivamente cancellato da una nuova esecuzione del seeder — non serve modificare l'enum per testarlo, basta inserire una riga spuria con `Permission::create(...)`/`Role::create(...)` prima di ri-lanciare il seeder.

## Policy deny-by-default per modello (US-019)

- Ogni modello Eloquent di dominio ha una Policy in `App\Domain\<Modulo>\Policies\<Modello>Policy` (parallela a `Models/`, mai in `app/Policies/`): Laravel la trova **da solo** sostituendo `\Models\` con `\Policies\` nel namespace (`Illuminate\Auth\Access\Gate::guessPolicyName`), senza bisogno di registrarla in nessun Provider/`AuthServiceProvider` (questo repo non ne ha uno). Verificato empiricamente: un modello senza Policy registrata nega già `$user->can('view', $model)` di default (nessun bisogno di un `Gate::before` esplicito per il deny-by-default).
- Ogni metodo di policy controlla il permesso via `$user->can(Permission::X)`/`$user->canAny([Permission::X, Permission::Y])` **passando direttamente il case dell'enum**, non `->value`: Laravel 11+ normalizza da solo un `BackedEnum` passato come ability tramite l'helper globale `enum_value()` (vedi `Illuminate\Auth\Access\Gate::inspect()`). Questo evita ogni confronto su stringa grezza (§4.4 A4) senza bisogno di un helper custom — `canAny()` è già nativo di `Illuminate\Foundation\Auth\Access\Authorizable`, non serve scriverne uno.
- Questa fase implementa **solo il livello 1 (permesso)** del PRD §9.1: nessun metodo di policy ispeziona la relazione tra l'utente autenticato e il record per decidere l'esito (niente "sono io l'assignee?"). Fa eccezione il branching su un **attributo del record stesso** che il catalogo §9.3 già modella come permesso dedicato (es. `TicketMessage::$visibility` → `ticket-message.view.internal` vs i permessi `ticket.view.*`; `DocumentationPage::$category` → `documentation.view.customer` vs `.view.internal`): non è record-ownership, è comunque un gate di permesso puro. Le vere regole di record-ownership (assignee/tester del ticket) arrivano in Fase 1 con la macchina a stati.
- Diversi modelli/azioni non hanno un permesso 1:1 nel catalogo §9.3 (`TicketParticipant`, `TicketView`, `TicketWorkLog`, `NotificationPreference`, `FundraisingEvaluationScore`, tutto il modulo Mail salvo `email.view`/`email.manage`): in questi casi la Policy riusa il permesso del modello "padre" più vicino concettualmente (es. gestire i partecipanti → `ticket.assign`; loggare ore lavorate → `ticket.update.*`; preferenze di notifica → `email.manage`). Se in una fase successiva emerge il bisogno di un permesso dedicato o di una regola "posso gestire le MIE preferenze" più permissiva, aggiungerlo al catalogo enum (US-011) e stringere la Policy di conseguenza — non il contrario.
- `UserPolicy::delete()` è mappato su `user.deactivate` (non esiste `user.delete` nel catalogo: "eliminare" un utente in questo dominio è la soft-delete, semanticamente una disattivazione) mentre `forceDelete()` è negato a chiunque (nessuna cancellazione irreversibile prevista).
- **Larastan non inferiva il tipo backed-enum degli attributi castati** (`Ticket::$status`, `TicketMessage::$visibility`, ecc.), trattandoli come `string` e facendo fallire ogni `match()`/confronto sull'enum con "arm sempre falso": il repo casta tutti i modelli con il metodo `protected function casts(): array` (stile Laravel 11+), non la vecchia proprietà `protected $casts`, e Larastan supporta questo stile solo dietro il flag `parseModelCastsMethod: true` (default `false`), abilitato in `phpstan.neon`. Se un futuro upgrade di Larastan cambia questo default, non rimuovere il flag esplicito.

## Gate di accesso al pannello (US-020)

- `User implements Filament\Models\Contracts\FilamentUser` con `canAccessPanel(Panel $panel): bool`: nega se `deactivated_at` non è null, altrimenti richiede `hasAnyRole(array_column(UserRole::cases(), 'value'))` (i 5 ruoli applicativi validi, mai un controllo su permesso qui: è un gate di navigazione, non un'autorizzazione di dominio, coerente con §9.1/§9.2 — i ruoli restano solo per landing/navigazione, non per esprimere capacità).
- In test, `Filament\Panel` **non ha costruttore**: si può istanziare direttamente con `new Panel` (nessun bisogno di risolvere un panel reale via `Filament::getPanel('admin')`) per chiamare `$user->canAccessPanel(new Panel)`.
- `User::scopeActive()` (`whereNull('deactivated_at')`) è il punto unico da usare in qualunque futura query di selezione utenti (campi di assegnazione ticket, participants, ecc.) per escludere gli utenti disattivati: non duplicare `whereNull('deactivated_at')` a mano nelle resource Filament successive, usare `User::query()->active()`.

## UI gestione ruoli/permessi — primo Filament Resource del repo (US-021)

- Prime due Filament Resource create in questo repo: `App\Filament\Resources\Users\UserResource` (CRUD normale, gated dalla `UserPolicy` di US-019) e `App\Filament\Resources\Roles\RoleResource` (**sola lettura**, nessuna Policy). Scaffoldate con `php artisan make:filament-resource <Model> --model-namespace="..." --view` (Filament 4 genera `Resource/Pages/Schemas/Tables` in cartelle separate, non embedded): per un modello fuori da `App\Models` passare sempre `--model-namespace`.
- **Proprietà statiche tipo `$navigationGroup`/`$navigationIcon` in una Resource devono usare il tipo union dichiarato dalla classe base** (`UnitEnum|string|null`, non `?string`): un tipo più stretto di quello ereditato è un **fatal error a runtime** (non un errore Larastan), perché PHP verifica la covarianza delle proprietà tipizzate in fase di caricamento della classe, prima ancora che gira l'analisi statica o i test.
- **Resource Filament di sola lettura su un modello SENZA una Policy Laravel** (qui: `Spatie\Permission\Models\Role`, un modello vendor — non gli è mai stata scritta una `RolePolicy` in questo repo): il deny-by-default nativo (§9.1) nega tutto per mancanza di Policy, quindi bisogna **sovrascrivere direttamente `canViewAny()`/`canView()`/`canCreate()`/`canEdit()`/`canDelete()`/`canDeleteAny()`** nella classe Resource (metodi statici di `Filament\Resources\Resource\Concerns\HasAuthorization`) invece di scrivere una Policy. Per rendere una risorsa realmente di sola lettura: registrare in `getPages()` **solo** `index`/`view` (niente `create`/`edit`), rimuovere `CreateAction`/`EditAction` dalle pagine generate, e comunque forzare `canCreate()`/`canEdit()`/`canDelete()`/`canDeleteAny()` a `false` esplicitamente (non basta l'assenza delle pagine: alcuni pulsanti/azioni di terze parti potrebbero comunque tentare l'azione).
- **Larastan non conosce le proprietà magiche (`->name`) né i metodi di relazione (`->permissions()`) dei modelli Eloquent che vivono FUORI dai `paths` analizzati** (qui: `Spatie\Permission\Models\{Role,Permission}`, in `vendor/`, mentre `phpstan.neon` analizza solo `app`, `database`, `routes`). Sintomi: `Access to an undefined property Model::$name` anche se la colonna esiste davvero, `Call to an undefined method Model::relationName()` anche se il metodo esiste davvero nel trait. Pattern per aggirarlo senza `@phpstan-ignore`/baseline/cast: usare `$model->getAttribute('name')` (metodo reale su `Illuminate\Database\Eloquent\Model`, sempre risolvibile) invece della proprietà magica; per una relazione many-to-many il cui provenienza-per-riga serve (qui: "quali permessi vengono da quale ruolo"), sostituire il giro `$role->permissions` con una **query diretta `DB::table(...)` sulle tabelle pivot** (`role_has_permissions` join `roles`/`permissions`), che restituisce `stdClass` (proprietà dinamiche, nessun errore Larastan) invece di istanze Eloquent tipizzate a metà — bonus: una sola query invece di N+1. Il contrario funziona invece regolarmente: un modello Spatie passato come **parametro di closure esplicitamente tipizzato** (es. `fn (SpatieRole $record) => $record->name` dentro `CheckboxList::getOptionLabelFromRecordUsing()`) non genera errori, perché lì Larastan controlla solo la firma dichiarata della closure, non i generici di una Collection.
- **`Collection<int, Model>::map()`/`::each()` non accettano un callback tipizzato su un sottotipo** (`Closure(Role): string` quando la Collection è tipata `Collection<int, Model>`, il default quando la relazione Spatie non dichiara i generici): è un errore di varianza dei parametri (il callback deve accettare almeno il tipo dichiarato dalla Collection, non un tipo più specifico), non risolvibile restringendo il tipo del parametro closure. Usare un parametro **non tipizzato** nella closure (`fn ($permission) => ...`) e narrowing solo internamente (`getAttribute()`), oppure evitare del tutto `map()`/`each()` su quella collection (vedi punto sopra).
- Pattern "sezione del form visibile solo con un permesso specifico" (qui: `CheckboxList::make('roles')` visibile solo con `user.assign-roles`, `CheckboxList::make('permissions')` diretto visibile solo con `user.grant-permissions`, entrambe dentro `Filament\Schemas\Components\Section::make(...)->visible(fn (): bool => Auth::user()?->can(Permission::X))`): un componente Filament nascosto da `->visible()` non viene dehydratato nel form (il suo stato non viene salvato né sovrascrive quello esistente), quindi un admin senza il permesso che salva il form di un altro campo non altera involontariamente ruoli/permessi che non doveva nemmeno vedere.
- Per collegare un `CheckboxList`/`Select` di Filament a una relazione many-to-many Spatie con **etichette localizzate diverse dal valore grezzo in colonna** (`roles.name`/`permissions.name` sono valori enum come `'admin'`/`'ticket.view.any'`, non testo per l'utente): `->relationship('roles', 'name', modifyQueryUsing: fn ($query) => $query->orderBy('name'))` **non** usa `name` come etichetta se si aggiunge anche `->getOptionLabelFromRecordUsing(fn (SpatieRole $record) => UserRole::tryFrom($record->name)?->getLabel() ?? $record->name)`: quest'ultimo callback ha sempre precedenza sul secondo argomento di `relationship()` per la label mostrata, che resta comunque necessario per dire a Filament quale relazione Eloquent usare per salvare la selezione.
- Testare una Filament Resource **senza** il pacchetto `pestphp/pest-plugin-livewire` (non installato in questo repo, solo `pest-plugin-laravel`): usare `\Livewire\Livewire::test(PageClass::class, ['record' => $model->getKey()])` direttamente (il pacchetto `livewire/livewire`, dipendenza di Filament, espone comunque il proprio helper di test) invece dell'helper globale `livewire()`. Serve `Filament::setCurrentPanel('admin')` in un `beforeEach()` prima di ogni test che monta pagine Filament fuori da una richiesta HTTP reale, altrimenti il contesto pannello/tema non è impostato.

## Comando diagnostico `orchestrator:doctor` (US-022)

- Architettura a controlli indipendenti (§12): `App\Support\Doctor\Contracts\DoctorCheck` (un metodo `run(): list<DoctorCheckResult>`) + `App\Support\Doctor\Checks\*` (una classe per famiglia di controllo: `EnvironmentVariablesCheck`, `StorageWritableCheck`, `SystemUserCheck`, `FeatureFlagsCheck`). `OrchestratorDoctorCommand` è un orchestratore sottile: istanzia ogni check elencato in `self::CHECKS` via il container (`$this->laravel->make(...)`), stampa un esito per riga, exit code 1 se un qualunque `DoctorCheckResult::$passed` è `false`. Per aggiungere un controllo di una fase successiva (IMAP/SMTP, logo PDF, stato ultimo import): creare una nuova classe `DoctorCheck` e aggiungerla a `self::CHECKS`, non toccare le altre.
- **`EnvironmentVariablesCheck` NON chiama `env()` direttamente** (vietato fuori da `config/`, §13.3): legge lo snapshot `config('orchestrator.required_env')` (nome variabile → valore, popolato in `config/orchestrator.php` con `env('X')` **senza default**, cosicché un valore `null`/vuoto rifletta fedelmente una variabile assente nell'ambiente reale). Per estendere la lista di variabili obbligatorie di una fase futura, aggiungere la chiave in `config/orchestrator.php`, non nel Check.
- L'utente di sistema (`config('orchestrator.system_user')`, fallback per l'autore dei log/eventi generati dal sistema, non da un utente reale) è creato con `User::query()->firstOrCreate(['email' => ...], ['name' => ...])`, **senza** la chiave `password` nell'array di creazione (non `password => null`): il cast `'hashed'` di `User::casts()` gestisce già `null` senza errori (`HasAttributes::hashAttribute()` fa `if (! is_null($value) && ...)`), ma passare esplicitamente `password => null` sarebbe comunque equivalente — omesso per chiarezza. Nessun ruolo assegnato: `canAccessPanel()` (US-020) nega comunque l'accesso al pannello anche a un utente senza password, quindi non serve altra protezione.
- `--help` è documentato gratuitamente da Symfony Console a partire da `protected $description` sul comando: non serve altro per soddisfare l'AC "il comando è documentato con --help".

## Seed di sviluppo (US-023, rimosso in US-R03)

- US-023 introduceva un seeder di dati fittizi per l'ambiente locale (utenti-ruolo, organizzazioni, ticket con conversazioni/allegati finti via medialibrary, tag, documentazione, report attività, opportunità fundraising), richiamato da `DatabaseSeeder` dopo il seeder di ruoli/permessi. **Rimosso interamente in US-R03** quando `make setup` (US-R02, vedi sezione sotto) è passato a popolare l'ambiente locale con l'ETL reale (`v1:import --anonymize` su un dump reale, mai dati fittizi): `DatabaseSeeder::run()` richiama oggi solo il seeder di ruoli/permessi.
- **Pattern Larastan riusabile per qualunque futuro seeder che debba stampare output solo quando lanciato da `db:seed`**: `Illuminate\Database\Seeder::$command` è documentato (`@var`) come sempre presente, ma non lo è quando il seeder è istanziato direttamente nei test invece che tramite `php artisan db:seed`. Con `treatPhpDocTypesAsCertain` (default true, non disattivato in questo repo) Larastan tratta sia `$this->command?->...` (nullsafe) sia `isset($this->command)` come errori ("mai null"/"proprietà mai nullable"), pur essendo realmente `null` a runtime in quel caso. Pattern per aggirarlo senza modificare `phpstan.neon`: dichiarare una **propria** proprietà `private ?Command $console = null;`, sovrascrivere `setCommand(Command $command): static` per popolarla (chiamando comunque `parent::setCommand($command)`), e usare `$this->console?->...` ovunque nel seeder — essendo una proprietà propria dichiarata `?Command`, Larastan la tratta correttamente come nullable.

## `make setup` — avvio da zero (US-024)

- **`docker/php/Dockerfile` deve installare l'estensione `exif`** (`docker-php-ext-install ... exif`): `spatie/image`/`spatie/laravel-medialibrary` la richiedono e `composer install` fallisce con "it is missing from your system" se non c'è. Il gap è passato inosservato da US-002 a US-023 perché `composer install` era sempre stato lanciato sull'host (PHP locale, con `exif` già abilitato), mai dentro il container `app`: qualunque comando che deve girare nel container va verificato eseguendolo davvero nel container, non assumendo che "ha funzionato sull'host" basti.
- **Ordine critico in `make setup`**: `composer install` e `php artisan key:generate` vanno eseguiti con `docker compose run --rm app ...` (container effimero) **prima** di `docker compose up -d` dei servizi long-running (`app`/`queue`/`scheduler`), non dopo. `env_file: .env` in `docker-compose.yml` inietta le variabili d'ambiente nel container **al momento della creazione**: se `app`/`queue`/`scheduler` vengono creati con `docker compose up` mentre `.env` ha ancora `APP_KEY=` vuoto (come da `.env.example`), quella stringa vuota resta l'`APP_KEY` effettivo del processo per tutta la vita del container anche se `key:generate` riscrive il file `.env` subito dopo (il file bind-mounted cambia, ma le variabili d'ambiente già iniettate nel container no, e Dotenv non sovrascrive una variabile già definita nell'ambiente reale, nemmeno se vuota) — sintomo: `MissingAppKeyException` nonostante `.env` contenga una chiave valida. Qualunque variabile scritta in `.env` da un comando (`key:generate` e in futuro comandi simili) deve essere finalizzata prima di portare su i container che la useranno per tutta la loro vita.
- **`npm install && npm run build` restano un passo host**, non containerizzato (nessun servizio Node in `docker-compose.yml`, l'immagine `app` è solo PHP-FPM): `make setup` richiede quindi Node.js sull'host oltre a Docker. `public/build/manifest.json` (Vite) deve esistere prima di servire qualunque pagina del pannello, altrimenti `Illuminate\Foundation\ViteManifestNotFoundException` su ogni vista che usa `->viteTheme(...)` (US-005).
- **`composer install` dentro un container con volume bind-mount su macOS (virtiofs) può fallire in modo non deterministico** durante l'estrazione parallela dei pacchetti (`RecursiveDirectoryIterator::__construct(...): Failed to open directory`, un pacchetto diverso ogni volta) — race innocua tra creazione directory e scrittura file sul filesystem condiviso, non un problema dei pacchetti. Si risolve da solo con un retry (i pacchetti già estratti non vengono ri-scaricati): `make setup` esegue `composer install` dentro un piccolo loop di retry (`for i in 1 2 3; do composer install && exit 0; done; exit 1`) invece di assumere che il primo tentativo basti.
- **AGGIORNAMENTO (design ETL real data seeding, US-R02): `make setup` non esegue più `db:seed --force` (che richiamava `DatabaseSeeder` con il seeder di ruoli/permessi e, fino a US-R03, anche il seeder di sviluppo)**. La sequenza finale è: fallisce subito se `v1dumps/latest.sql` manca (messaggio esplicito, prima di qualunque altro passo) → `docker compose up -d` → `bin/load-v1-dump v1dumps/latest.sql` (porta su `db_legacy` da solo, nessun `make etl-up` separato) → `migrate --force` → `db:seed --class=RolePermissionSeeder --force` (esplicito, non l'intero `DatabaseSeeder`) → `php artisan v1:import --anonymize` (mai `--truncate`, non adatto a un contesto non interattivo: richiede una conferma `$this->confirm()`). Gli allegati restano best-effort: se `storage/app/v1-media/` è vuota il target non fallisce, `TicketAttachmentsStage` segnala solo i media come compromesso. Idempotente: rilanciabile senza `migrate:fresh`/`--truncate` (stesso principio già consolidato per l'ETL, vedi sezione ETL sopra).

## Macchina a stati del ticket (US-101)

- `App\Domain\Ticketing\StateMachine\TicketStateMachine` (Fase 1, A2 del PRD) tiene TUTTA la tabella delle transizioni in `transitions(): array<Transition>` (memoizzata con `static $transitions`, la classe non ha stato per-istanza: tutti i metodi sono statici, coerente con l'essere una pura funzione di lookup). Per aggiungere/modificare una transizione, tocca solo quell'array — nessun `if` sparso altrove.
- Il "chi" di una riga (colonna "Chi" del PRD §6.1.3) **non è un ruolo**: è `App\Domain\Ticketing\StateMachine\TransitionActor` (enum senza backed value), che verifica insieme permesso (§9.3, `$user->can(Permission::X)`) e rapporto col record (`assignee_id`/`tester_id` = utente corrente) in un solo metodo `authorize()`. Un developer "generico" senza rapporto col ticket non è mai un attore valido di per sé: o è `Assignee`/`Tester` (rapporto già esistente), o `AutoAssigningDeveloper` (il contesto passato alla transizione lo autoassegna contestualmente), o `NoRelationRequired` (la riga non richiede alcun rapporto perché il ticket non ha ancora un assignee, es. `new → backlog`). Il `TicketPolicy` di Fase 0 resta solo livello-permesso: le regole di record-ownership sui ticket vivono qui, non nella Policy.
- **Guard con precedenza sul contesto rispetto alla colonna esistente**: ogni guard (es. "tester_id valorizzato") controlla prima `$context['tester_id'] ?? $ticket->tester_id` — così la macchina a stati può validare *prima* che un'Action (US-103) scriva davvero la colonna, passando il valore che sta per applicare in un array `$context` (`assignee_id`/`tester_id`/`waiting_reason`/`problem_reason`). Riusare questo pattern per qualunque futuro guard che dipenda da un campo che l'Action valorizza nella stessa chiamata della transizione.
- **Transizioni con target dinamico** (`waiting`/`problem` → `previous_status`, §6.1.3): `Transition::$to` è `?TicketStatus`, `null` significa "il target è `$ticket->previous_status`, non un valore fisso della tabella". `matchesTarget(Ticket $ticket, TicketStatus $to)` risolve il confronto a runtime. Se `previous_status` è `null` o non coincide col target richiesto, nessuna transizione fa match e l'esito è "transizione non ammessa" (non un guard fallito) — comportamento corretto, non serve un guard dedicato per "il target combacia".
- **Un errore di validazione localizzato, mai un'eccezione generica** (A2): sia "transizione non in tabella" sia "attore non autorizzato" sia "guard fallito" lanciano `Illuminate\Validation\ValidationException::withMessages(['status' => [...]])` con un messaggio in italiano leggibile. `TicketStateMachine::can(...)` è un wrapper `try/catch` che restituisce `bool` per i punti che vogliono solo un check booleano (es. abilitare/disabilitare un bottone in UI, Fase 1 US-110) senza dover gestire l'eccezione.
- **Attore "sistema" incluso solo dove serve davvero ora**: `waiting → previous_status` include `TransitionActor::System` (serve all'effetto T7 di US-106, un listener che gira ora), ma `released → done` **non** include `System` anche se il PRD lo elenca (quell'uso è legato al comando schedulato T4 `tickets:auto-close-released`, che arriva in Fase 6). Se una story futura introduce un comando/listener che deve agire da sistema su una transizione che oggi non ha `System` tra gli attori, aggiungerlo esplicitamente in quel momento — non prima, per non lasciare un varco di autorizzazione inutilizzato.
- `User::isSystem(): bool` (confronta l'email con `config('orchestrator.system_user.email')`) è il modo per riconoscere l'utente di sistema in un guard/attore: non introdurre un secondo meccanismo (flag, ruolo dedicato, ecc.) per la stessa cosa.
- `effects` su una `Transition` (`App\Domain\Ticketing\StateMachine\TransitionEffect`) è **solo metadato dichiarativo** in questa fase: la macchina a stati non scrive nulla sul ticket né emette eventi, si limita a dichiarare quali effetti la transizione comporta. L'esecuzione reale (scrittura colonne, `ticket_logs`, eventi di dominio, demote §6.1.4) arriva con l'Action `ChangeTicketStatus` (US-103): quando la implementi, itera `$transition->effects` invece di reintrodurre `if` sparsi per side effect.

## Validation Rules di dominio (US-102, A3 del PRD)

- Le regole di business testabili in isolamento vivono in `App\Domain\Ticketing\Rules\*` come classi che implementano `Illuminate\Contracts\Validation\ValidationRule` (`validate(string $attribute, mixed $value, Closure $fail): void`), non `throw new Exception` dentro un metodo di salvataggio. Ogni regola espone il proprio messaggio italiano come `public const string MESSAGE`, così il messaggio ha un'unica fonte di verità: sia il chiamante che vuole solo il testo (es. `Transition::$guardMessage` in `TicketStateMachine`), sia un futuro form Filament/richiesta API che userà la stessa Rule direttamente in un `Validator`, leggono la stessa costante — non duplicarla come stringa letterale altrove.
- `TicketStateMachine` non duplica la condizione delle Rule nei guard: ogni guard privato (`guardTesterValued`, ecc.) calcola il valore con la solita precedenza `$context[...] ?? $ticket->...` e lo passa a `TicketStateMachine::passesRule()`, un helper che invoca `$rule->validate()` con una closure che si limita a segnare "fallito" e tornare un `Illuminate\Translation\PotentiallyTranslatedString` (richiesto dalla firma dell'interfaccia: Larastan la valida a livello 6). Se aggiungi una nuova Rule con lo stesso schema "valorizzato sì/no", riusa `passesRule()` invece di reinventare un adattatore.
- **Gotcha Larastan sulla firma di `$fail`**: `ValidationRule::validate()` dichiara `$fail` come `Closure(string, ?string=): PotentiallyTranslatedString`, non `Closure(): void`. Una closure di test/adattamento che ignora i parametri e non ritorna nulla fa fallire l'analisi statica (livello 6) con `argument.type`, anche se a runtime funziona lo stesso (PHP non impone l'arità sulle closure). Quando adatti un `$fail` a un booleano, dichiara i parametri `(string $attribute, ?string $message = null)` e ritorna `new PotentiallyTranslatedString($message ?? $attribute, app('translator'))`.
- Rule che leggono lo stato del DB (es. `TicketParentDepthRule`, che verifica la profondità massima 1 di §6.1.6 controllando sia che il padre scelto non abbia già un padre, sia che il ticket stesso non abbia già dei figli) accettano il record "corrente" via costruttore (`new TicketParentDepthRule($ticket)`), non tramite un secondo parametro di `validate()`: è il pattern da seguire per qualunque Rule che deve conoscere il modello in salvataggio oltre al singolo valore di campo (stesso spirito di `Rule::unique()->ignore($id)`).
- Helper di test condiviso `ruleFails(ValidationRule $rule, mixed $value, string $attribute = 'value'): bool` in `tests/Pest.php` (accanto a `userWithPermissions`): usalo per testare una Rule in isolamento senza costruire un `Validator`/richiesta HTTP completa. Qualunque helper di test riusabile tra più file va messo lì, non ridichiarato come funzione globale in un singolo file di test (altrimenti un secondo file che dichiara la stessa funzione causa un fatal error di redeclare non appena Pest carica entrambi i file nello stesso processo).

## Action di dominio, eventi, ticket_logs (US-103)

- Ogni mutazione significativa del ticket passa da un'Action statica in `App\Domain\Ticketing\Actions\*` (`CreateTicket::run()`, `ChangeTicketStatus::run()`, `AssignTicket::run()`), mai da un hook Eloquent (A1). Ognuna avvolge le proprie scritture in `DB::transaction()`: se una qualunque scrittura secondaria fallisce (es. la demozione §6.1.4), l'intera mutazione viene annullata, log compresi.
- `TicketStateMachine::authorize()` (US-101) ora **restituisce** la `Transition` risolta (non più `void`): `ChangeTicketStatus` la usa per iterare `$transition->effects` e applicarli davvero (scrittura colonne, side effect), invece di ripetere la ricerca nella tabella. Se estendi `authorize()`, mantieni questo valore di ritorno: è il contratto con l'Action.
- **Il chiamante risolve sempre l'attore esplicitamente**: le Action prendono `User $user` obbligatorio (mai `auth()->user()` interno). "Utente autenticato o, in assenza, l'utente di sistema" (§6.2.1) è responsabilità del chiamante: usa `App\Domain\Identity\Models\User::system()` (che fa `firstOrCreate` per email da `config('orchestrator.system_user.email')`, stesso comportamento di `orchestrator:doctor`) quando non c'è un utente autenticato reale. Non hardcodare mai un id.
- **REGOLA §6.1.4 (un solo ticket `progress` per assegnatario)**: `ChangeTicketStatus` la esegue solo quando la `Transition` risolta dichiara l'effect `TransitionEffect::DemoteOtherProgressTickets` (oggi solo `todo → progress`). La demozione aggiorna direttamente `status`/`status_changed_at` e scrive il proprio `ticket_log` per ciascun ticket demosso, SENZA ripassare da `TicketStateMachine::authorize()` (è un side effect di sistema dichiarato dalla tabella, non una nuova decisione di autorizzazione).
- `App\Domain\Ticketing\DTO\TicketLogChanges`: unico modo per popolare `ticket_logs.changes`, sempre tramite costruttori nominati (`assigneeChanged()`, `descriptionChanged()`), mai un array libero. `descriptionChanged()` registra solo il marker `'changed'`: qualunque futura Action che logghi un cambiamento di `description` deve passare da qui per non violare la regola v1 (mai il corpo del campo salvato nel log).
- Eventi di dominio in `App\Domain\Ticketing\Events\*` (`TicketCreated`, `TicketStatusChanged`, `TicketAssigned`): classi `readonly` semplici, nessun listener reale ancora agganciato in questa fase (arriva in US-106/US-109). Emessi con `event(new ...)` **dentro** la transazione dell'Action: un listener di test che lancia un'eccezione durante l'evento fa quindi rollback anche delle scritture già eseguite nella stessa Action — pattern usato per testare la transazionalità della demozione (vedi `tests/Feature/Domain/Ticketing/Actions/ChangeTicketStatusTest.php`).
- Helper di test condivisi `ticket()` e `systemUser()` sono stati spostati in `tests/Pest.php` (erano prima duplicati/locali a `TicketStateMachineTest.php`): riusali da qualunque nuovo file di test sul dominio Ticketing invece di ridichiararli.

## Propagazione esplicita ai figli (US-104, decisione Q5)

- `App\Domain\Ticketing\Actions\ApplyStatusToChildren::run(Ticket $parent, TicketStatus $to, User $user, array $context = [])` è l'UNICO modo per applicare lo stesso cambio di stato ai figli diretti di un ticket: `ChangeTicketStatus` (US-103) non la richiama mai da sé, la propagazione automatica del v1 è stata deliberatamente rimossa (Q5).
- Pattern "un figlio alla volta, isolato": itera `$parent->children`, invoca `ChangeTicketStatus::run()` per ciascun figlio dentro un `try/catch (ValidationException)`. Un figlio la cui transizione non è ammessa (tabella/attore/guard di US-101) finisce in `skipped` col motivo, SENZA bloccare gli altri figli — non serve una transazione che avvolga l'intera propagazione, perché ogni chiamata a `ChangeTicketStatus::run()` è già transazionale ed è corretto che il fallimento di un figlio non tocchi gli altri.
- Esito tipizzato in `App\Domain\Ticketing\DTO\ApplyStatusToChildrenResult` (`applied: list<Ticket>`, `skipped: list<array{ticket: Ticket, reason: string}>`): riusa questo DTO (o lo stesso schema) per qualunque futura Action "applica a più record, salta chi fallisce senza bloccare gli altri" (es. bulk action Filament).

## Regole sul record nella TicketPolicy (US-105, §9.5)

- `Ticket::scopeVisibleTo(Builder $query, User $user)` è l'UNICA fonte di verità per "quali ticket può vedere `$user`" (§9.5): `ticket.view.any` non ha vincoli, `ticket.view.assigned` restringe a `assignee_id`/`tester_id = $user->id`, `ticket.view.own` restringe a `requester_id = $user->id`. Nessuno dei tre permessi → `whereRaw('1 = 0')` (nessuna riga), mai una policy senza scope che ritorna sempre `false` a mano. `TicketPolicy::view()` **delega** a questo scope (`Ticket::query()->whereKey(...)->visibleTo($user)->exists()`) invece di ripetere la stessa condizione: qualunque query futura (viste/filtri Filament, US-111/US-112) deve incatenare lo stesso scope, non un `where` scritto a mano.
- `TicketPolicy::update()` verifica il permesso **e** il rapporto col record separatamente per ciascun livello, perché ogni permesso implica un confronto diverso: `ticket.update.any` nessun vincolo, `ticket.update.own` richiede `requester_id = $user->id`, `ticket.update.assigned` richiede `assignee_id = $user->id` **oppure** `tester_id = $user->id`. Non è riconducibile a un unico scope condiviso con `view()` perché i permessi coinvolti sono un set diverso (`update.*` non `view.*`).
- `TicketMessage::scopeVisibleTo(Builder $query, User $user)` esclude i messaggi `visibility = internal` per chi non ha `ticket-message.view.internal`: pensato per essere incatenato a `$ticket->messages()` in qualunque query futura (timeline conversazione, US-106), non solo per un singolo `TicketMessagePolicy::view()` — così un cliente non raggiunge mai un messaggio interno nemmeno con un accesso diretto by-id attraverso la relazione.
- Attenzione: i test di `TicketPolicy` scritti in Fase 0 (livello permesso soltanto) assumevano che avere `ticket.view.own`/`ticket.update.assigned` bastasse indipendentemente dal record — sono stati riscritti in questa story per riflettere il livello 2 (record-ownership): se una story futura tocca `TicketPolicy`, verificare che i fixture dei test impostino `requester_id`/`assignee_id`/`tester_id` coerenti con l'esito atteso, non un ticket "vuoto".

## Conversazione del ticket (US-106, §6.1.7)

- `App\Domain\Ticketing\Actions\PostTicketMessage::run(Ticket $ticket, User $author, string $bodyHtml)` è l'UNICO modo per pubblicare un messaggio: canale sempre `web` e visibilità sempre `public` in questa fase, nessun parametro permette di aggirarlo (il punto di estensione `internal`/`email` resta esplicitamente fuori scope, §15.2). Aggiunge l'autore ai `ticket_participants` (`syncWithoutDetaching`, mai un duplicato), scrive il `ticket_log` `message_posted` ed emette `TicketMessagePosted` DENTRO la stessa transazione.
- `App\Domain\Ticketing\Support\TicketMessageSanitizer` è la SOLA via per sanitizzare un `body_html` prima di salvarlo o mostrarlo: allowlist esplicito (`symfony/html-sanitizer`, aggiunto come dipendenza diretta in questa story), non un blocklist — qualunque tag non elencato viene rimosso INSIEME al suo contenuto (`<script>` incluso). `toPlainText()` deriva sempre dal corpo GIÀ sanitizzato, mai dal grezzo. Mai un `{!! !!}` altrove nel codice su questo campo: l'output è già sicuro.
- `Ticket::messageRecipients(User $author)`: partecipanti + richiedente + assegnatario + tester, deduplicati per id, escluso l'autore — riusabile senza modifiche da una futura Action di invio email (Fase 3); questa fase si limita a esporlo, nessun invio reale avviene ancora.
- Regola T7 (decisione Q14, semplificazione del PRD) vive in `App\Domain\Ticketing\Listeners\RestoreTicketStatusOnRequesterMessage`, MAI dentro `PostTicketMessage`: quando l'autore del messaggio è il `requester_id` del ticket, se lo stato è `waiting` torna a `previous_status`; se è `assigned`/`progress` passa a `todo` (se già `todo`, nessuna azione: non esiste una riga `todo → todo` in tabella). Passa sempre da `ChangeTicketStatus::run()` con `User::system()`, mai una scrittura diretta di `status`.
- I listener di dominio vivono in `App\Domain\<Dominio>\Listeners` (non `App\Listeners`): l'auto-discovery di Laravel NON li trova. Vanno registrati a mano in `AppServiceProvider::boot()` con `Event::listen(EventoDiDominio::class, ListenerDiDominio::class)` — qualunque nuovo listener di dominio futuro deve essere aggiunto lì, altrimenti non gira mai.
- Per la regola T7 serve l'attore `System` su transizioni che PRIMA non lo prevedevano: `TicketStateMachine::transitions()` ora ammette `TransitionActor::System` anche su `assigned → todo` e `progress → todo` (oltre a `waiting → previous_status`, US-101), perché il listener invoca queste transizioni con `User::system()`. Se un futuro comando/listener ha bisogno del System actor su un'altra riga, aggiungerlo lì con lo stesso criterio: solo dove un chiamante di sistema reale esiste già, mai "per sicurezza".

## Allegati sui messaggi (US-107, §9.6/§17.2)

- Unica lista di tipi/dimensione ammessi in `config/ticketing.php` (letta da env, `TICKET_ALLOWED_{DOCUMENT,IMAGE,AUDIO}_{TYPES,MIMES}`/`TICKET_MAX_FILE_SIZE` in byte/`TICKET_ATTACHMENTS_DISK`), esposta via `App\Domain\Ticketing\Support\TicketAttachmentTypes` (`allowedExtensions()`/`allowedMimeTypes()`/`maxFileSize()`/`disk()`/`isAllowed()`): qualunque futuro punto di ingresso (parser email inbound, Fase 3) deve leggere da qui, mai duplicare la lista.
- `TicketMessage::registerMediaCollections()` registra `attachments` su un disco **privato dedicato** (`ticket-attachments` in `config/filesystems.php`, `serve => false`: nessuna route di framework che lo esponga) con `->acceptsMimeTypes(TicketAttachmentTypes::allowedMimeTypes())` come guardia di difesa aggiuntiva lato medialibrary.
- **Gotcha mime-sniffing**: `FileAdder::toMediaCollection()` deriva `$media->mime_type` da `Spatie\MediaLibrary\Support\File::getMimeType()`, che sniffa il **contenuto reale** del file (Symfony `MimeTypes`), non l'estensione dichiarata né `UploadedFile::getMimeType()` (che per `Illuminate\Http\Testing\File` in test è invece extension-based, vedi sotto). Un file di test con byte finti (`UploadedFile::fake()->create('x.pdf', 100)`, senza contenuto reale) può quindi fallire silenziosamente `acceptsMimeTypes()` lato medialibrary anche se il nome estensione è corretto: nei test, usare sempre contenuto reale (`UploadedFile::fake()->image(...)` per le immagini, genera bytes JPEG/PNG veri via GD; `UploadedFile::fake()->createWithContent($nome, $contenutoVero)` per altri formati, es. un vero SVG testuale) quando il test deve attraversare davvero `addMedia()->toMediaCollection()`. Per testare solo il guard applicativo (`AddTicketAttachment`, che valida PRIMA di chiamare medialibrary usando `$file->getMimeType()`/`getSize()`, gli attributi "dichiarati" di `Illuminate\Http\Testing\File`), un file fake senza contenuto reale basta.
- `App\Domain\Ticketing\Actions\{AddTicketAttachment,RemoveTicketAttachment}` sono l'UNICO modo per aggiungere/rimuovere un allegato: validano tipo+dimensione con `ValidationException` localizzata PRIMA di scrivere (A2, mai un'eccezione generica del vendor), scrivono un `ticket_log` dedicato (`TicketLogEvent::AttachmentAdded`/`AttachmentRemoved`, già presenti nell'enum da questa story) con `TicketLogChanges::attachmentAdded()`/`attachmentRemoved()` (nuovi costruttori nominati sul DTO esistente). `RemoveTicketAttachment` verifica esplicitamente che il `Media` passato appartenga davvero al `TicketMessage` indicato (`model_type`/`model_id`/`collection_name`) prima di cancellare: mai fidarsi solo dell'id fornito dal chiamante.

## Calcolo ore lavorate — WorkedTimeCalculator (US-109, §6.2.2, decisione Q15)

- `App\Domain\TimeTracking\WorkedTimeCalculator` è un service **puro** (nessuna query, nessun side-effect): riceve i `ticket_logs` di un ticket già caricati e ordinati per `occurred_at` e restituisce dei `WorkedTimeSegment` (`workDate`/`userId`/`minutes`). Configurazione (`workday_start`/`workday_end`/`granularity_minutes`/`non_status_change_cap_minutes`) SEMPRE iniettata nel costruttore, mai letta da `config()` dentro l'algoritmo: `fromConfig()` è l'unico punto che legge `config/timetracking.php`, usato dall'Action; i test unitari istanziano il service direttamente con valori noti.
- Algoritmo: intervalli tra un log `to_status = 'progress'` e il successivo `from_status = 'progress'`; per ciascun intervallo si itera giorno per giorno, si scartano sabato/domenica, si ritaglia (clamp, non discard) alla finestra oraria configurata, si arrotonda per difetto alla granularità. Un intervallo ancora **aperto** (nessun log di chiusura, ticket tuttora in `progress`) non proietta fino a `now()` indefinitamente: il totale calcolato per l'intero intervallo aperto viene limitato al tetto `non_status_change_cap_minutes` (`min($minuti, tetto)`), attribuito al giorno più recente toccato — questa è la scelta di unificazione della DECISIONE Q15 (il v1 aveva due politiche divergenti, "totale ticket" con scarto secco fuori finestra e "aggregato giornaliero" con clamp+tetto sui soli log senza cambio di stato): i numeri storici confrontati col v1 in Fase 2 potranno divergere per questa scelta.
- L'utente attribuito a un intervallo è lo `user_id` del log che lo ha APERTO (`to_status = 'progress'`), non l'assegnatario corrente del ticket: copre correttamente il caso "più assegnatari nel tempo" senza dover leggere lo storico di `assignee_id`.
- `App\Domain\TimeTracking\Actions\RecalculateWorkedTime::run(Ticket $ticket, ?CarbonInterface $asOf = null)` è l'UNICO punto di scrittura per `tickets.worked_minutes`/`ticket_work_logs`: dentro una transazione, ricalcola il totale, CANCELLA tutte le righe `ticket_work_logs` esistenti per quel ticket e le ricrea da zero (mai un upsert differenziale) — è ciò che rende il ricalcolo idempotente a prescindere da chi lo invoca (listener in coda o comando artisan).
- Il ricalcolo "live" (listener di `TicketStatusChanged`) fa debounce per ticket con un lock in `Cache` (chiave `timetracking:recalculate-debounce:{ticket_id}`, TTL breve) verificato SINCRONAMENTE nel listener PRIMA di accodare `App\Domain\TimeTracking\Jobs\RecalculateTicketWorkedTimeJob`: il listener stesso NON implementa `ShouldQueue` (se lo facesse, il controllo del lock avverrebbe solo quando un worker preleva il job, troppo tardi per fare da debounce reale su una raffica di transizioni). Pattern riusabile per qualunque futuro "coalesci N eventi ravvicinati in un solo job", testabile con `Queue::fake()` + `Queue::assertPushed(Job::class, N)` (il fake sostituisce solo il dispatch del Job, non tocca il lock in `Cache` che vive nel listener).
- Comando `timetracking:recalculate {--from=} {--to=} {--ticket=}` riusa la stessa `RecalculateWorkedTime` (mai una seconda implementazione dell'algoritmo): `--ticket` ricalcola un solo ticket e ignora `--from`/`--to`; senza `--ticket` i due filtrano su `created_at` (entrambi opzionali).
- Su questo host reale `Symfony\Component\Mime\MimeTypes::guessMimeType()` rileva correttamente `image/svg+xml` per un vero contenuto SVG testuale (verificato empiricamente con `file --mime-type` e con la libreria): non serve un pacchetto SVG-sanitizer dedicato (`enshrined/svg-sanitize` non è installato in questo repo) per attraversare la guardia `acceptsMimeTypes()`, un DOMDocument allowlist scritto ad-hoc basta.
- **BUG REALE trovato e corretto (US-219, 2026-08-02) in `progressIntervals()`**: il codice originale aveva due `if` separati con un `continue` dopo il primo (`if to_status===Progress { apri; continue; } if from_status===Progress { chiudi; }`). Un log "progress -> progress" (nessun cambio di stato intermedio, **frequente sui dati reali** — es. riassegnazione dentro `progress`, verificato su più ticket v1) ha CONTEMPORANEAMENTE `from_status=Progress` e `to_status=Progress`: il primo `if` scattava per primo e usciva con `continue` PRIMA che il codice potesse riconoscere che quello stesso log avrebbe dovuto chiudere l'intervallo già aperto. Risultato: l'intero intervallo precedente spariva silenziosamente (caso reale sul dump v1: un intervallo di 27 giorni azzerato da un singolo log di questo tipo, ticket v1 #2855). Fix: controllare **prima** la chiusura (`from_status===Progress`) e **poi**, senza `continue` fra le due, l'apertura (`to_status===Progress`) — un log che è sia chiusura sia apertura fa entrambe le cose alla stessa istante (chiude l'intervallo vecchio esattamente dove apre il nuovo: zero minuti persi, zero doppio conteggio, e se l'utente è cambiato l'attribuzione prima/dopo il confine resta corretta). **Pattern generale**: in un parser di eventi sequenziali dove un singolo evento può essere SIA la chiusura di uno stato SIA l'apertura del successivo, i due controlli non vanno mai messi in rami mutuamente esclusivi (`if`/`continue` o `if`/`else`) se l'evento può soddisfare entrambe le condizioni contemporaneamente — verificare esplicitamente questo caso prima di assumere che `if A ... if B` sia equivalente a `if A elseif B`. Test di regressione dedicati in `WorkedTimeCalculatorTest.php` (`does not lose time when a ticket is re-affirmed as progress...`, `re-affirming progress with a different user...`).
- **Tolleranza del confronto ore v1/v2 in `v1:validate` (US-219)**: `WorkedHoursDeviationAnalyzer::analyze()` ora richiede un secondo parametro `toleranceAbsoluteMinutes` (default 15) oltre alla tolleranza percentuale (default 0.05): un ticket è entro tolleranza se lo scostamento è ≤ percentuale **oppure** ≤ soglia assoluta in minuti. La sola percentuale non è un criterio sensato sui ticket con poche ore v1: un ticket da 10 minuti che in v2 arrotonda a 0 per la granularità configurata risulta "100% di scostamento" pur essendo rumore di arrotondamento di pochi minuti (confermato sul dump reale: 1980/2732 "oltre tolleranza" del primo report avevano meno di 1h in v1). Il report espone ora anche `deviation_minutes` per ogni ticket oltre tolleranza, non solo la percentuale.

## TicketResource — prima Resource Filament "reale" del repo (US-110)

- **Bottoni di transizione dinamici da `TicketStateMachine`**: `App\Filament\Resources\Tickets\Support\TicketTransitionActions::build(Ticket $ticket): list<Action>` itera `TicketStatus::cases()`, risolve la `Transition` applicabile (`TicketStateMachine::transitions()` + `Transition::appliesTo()`/`matchesTarget()`, entrambi pubblici) e decide se mostrare il bottone SOLO in base ad attore+tabella (`Transition::isAuthorizedFor()`), **mai** `TicketStateMachine::can()`/`guardPasses()`: i guard "campo valorizzato" (tester/waiting_reason/problem_reason/assignee_id) dipendono da un dato che l'utente fornisce nel modale dell'action stessa, quindi falliscono SEMPRE se verificati prima che quel modale esista — un bottone gated sul guard non comparirebbe mai. Il guard resta comunque verificato per davvero al submit da `ChangeTicketStatus::run()`: un fallimento a quel punto produce una notifica d'errore (mai un'eccezione non gestita), non un bottone mancante. Riusare questo schema ("visibilità = attore+tabella, guard reale solo al submit") per qualunque futura action dinamica costruita sopra una macchina a stati con guard "a valore".
- **`Action::schema([...])` invece di `requiresConfirmation()`**: quando un'action ha SEMPRE almeno un campo nel modale (qui: il checkbox "Applica anche ai ticket figli" presente su ogni transizione), non serve `requiresConfirmation()` — il modale del form è già la conferma. Aggiungerlo in più sarebbe ridondante/confuso.
- **Un `Select` con `modifyQueryUsing` tipizzato `Builder $query` (generico) non eredita il generic del modello collegato**: Larastan segnala `method.notFound` su uno scope locale (es. `User::scopeActive()`) chiamato dentro quella closure. Soluzione riusabile: estrarre un metodo privato con `@param Builder<User> $query` / `@return Builder<User>` esplicito e passarlo come **first-class callable** (`modifyQueryUsing: self::metodo(...)`), invece di una closure inline — Larastan verifica il metodo con il tipo dichiarato, e la chiamata a `modifyQueryUsing()` (parametro `?Closure` non generico lato Filament) resta comunque compatibile.
- **Gotcha "il valore è già cambiato quando arriva al tuo `handleRecordUpdate()`"**: per un `Select::make('assignee_id')->relationship('assignee', ...)` (BelongsTo), Filament associa già la nuova relazione sul **modello in memoria** (`$relationship->associate($state)`) come parte del calcolo dello stato del form, PRIMA che `EditRecord::handleRecordUpdate($record, $data)` venga invocato — quindi `$record->assignee_id` a quel punto è GIÀ il nuovo valore, non quello persistito. Per rilevare "è cambiato rispetto a prima" (necessario qui per decidere se chiamare `AssignTicket::run()`, che scrive il proprio `ticket_log`), confrontare col valore ORIGINALE via `$record->getOriginal('assignee_id')`, mai con l'attributo corrente. Pattern riusabile per qualunque futura Action di dominio agganciata a un `handleRecordUpdate()` che deve reagire a un cambiamento di un campo gestito da un `Select` relazionale di Filament.
- **`->hidden()` (non `->disabled()`) per ogni campo che un cliente non deve mai poter scrivere**: intere `Section` del form (`Assegnazione e classificazione`, `Link ambienti`, `Tempo`, più il campo `description`) sono `->hidden(fn () => ! $permesso)`, non solo `->disabled()`: un componente nascosto non viene dehydratato, quindi sopravvive anche a una `fillForm()` manipolata via test/DevTools (stesso principio già stabilito per le sezioni Ruoli/Permessi di `UserForm`, US-021, qui applicato a un caso con più campi eterogenei — testo, select, url, numerico). Verificato con test che chiamano `Livewire::test(EditTicket::class, [...])->fillForm([...campi interni manomessi...])->call('save')` e poi asserzioni su `$ticket->fresh()`, non solo sull'assenza del campo nel form renderizzato.
- **Permesso "ombrello" per una distinzione UI ricorrente**: `Permission::TicketManageInternalFields` (già nel catalogo, concesso a admin/manager/developer e negato a customer/fundraising) è il modo corretto per esprimere "è staff, non cliente" a livello di campo/sezione — non serve un secondo meccanismo (`hasRole(UserRole::Customer)`) quando un permesso già cattura esattamente quella distinzione. Centralizzato in `App\Filament\Resources\Tickets\Support\TicketFieldAccess::canManageInternalFields()`, riusato da form/tabella/infolist invece di ripetere `Auth::user()?->can(...)` in ogni file.
- **Nessun `RelationManager` in questa fase**: conversazione/storico del ticket sono implementati come `Filament\Infolists\Components\RepeatableEntry` con `->state(fn (Ticket $record) => Query::...->get())` esplicito (non la relazione grezza `$record->messages`/`$record->logs`), perché serve applicare `TicketMessage::scopeVisibleTo()` (esclude i messaggi `internal` per chi non ha il permesso) e l'ordinamento — un `RelationManager` con `getEloquentQuery()` avrebbe fatto lo stesso lavoro con più boilerplate per due sole liste di sola lettura. Se una fase futura ha bisogno di azioni CRUD complete su una relazione del ticket (non solo lettura + un'action separata), quello è il momento di introdurre il primo `RelationManager` del repo — non prima.
- **Allegati mostrati come link, mai un URL medialibrary diretto**: dentro il `RepeatableEntry` dei messaggi, gli allegati si renderizzano con un `TextEntry->html()` che genera `<a href="{{ route('ticket-attachments.download', $media) }}">` (la rotta autorizzata di US-107) — `route()` accetta direttamente un'istanza `Media` come parametro di rotta (risolve `getRouteKey()` automaticamente), non serve estrarre l'id a mano.
- **Badge di stato fuori da una colonna tabella/entry** (qui: il campo `status` nel form, sempre read-only per AC): `Illuminate\Support\Facades\Blade::render('<x-filament::badge :color="$color" :icon="$icon">{{ $label }}</x-filament::badge>', [...])` dentro un `Placeholder::make('status')->content(...)` riusa esattamente lo stesso componente Blade che Filament usa per `->badge()` nelle tabelle/infolist, invece di reinventare l'HTML/CSS del badge a mano.

## TicketResource — viste come query object (US-111, §8.5)

- **Ogni vista di §8.5 è un query object statico in `App\Domain\Ticketing\Queries`, MAI un metodo/scope su `Ticket` o una closure inline in una pagina Filament**: firma uniforme `for(User $user): Builder<Ticket>` che incatena SEMPRE `Ticket::query()->visibleTo($user)` (US-105) prima di applicare il proprio filtro, così un query object resta corretto anche se invocato fuori da un contesto Filament (comando artisan, altra vista futura, test isolato). Le viste "derivate" (In test/In attesa/Problemi) non ripetono la condizione di "Richieste attive": `ActiveRequestsQuery` espone un secondo metodo `apply(Builder $query): Builder` che accetta un builder già scoped, riusato dalle altre tre invece di duplicare `whereNotNull('requester_id')->whereNotIn('status', [...])`.
- **Non usare gli scope `role()`/`withoutRole()` di Spatie in una query "verificata a runtime su dati incerti"**: risolvono il ruolo con `findByName()` e lanciano `RoleDoesNotExist` se la riga `roles` non esiste ancora nel DB (es. nessun cliente mai registrato in un ambiente fresco) — un comportamento sbagliato per un filtro che deve solo restituire zero righe in quel caso, mai un'eccezione. Usare invece `whereHas('roles', fn ($q) => $q->where('name', $ruolo))` / `whereDoesntHave(...)` direttamente sulla relazione, che non fa alcun lookup del ruolo e quindi non lancia mai quell'eccezione (vedi `AllCustomerTicketsQuery`/`InternalTicketsQuery`).
- **Tab della tabella (`ListRecords::getTabs()` + `Tab::make()->modifyQueryUsing(...)`)**, non `SelectFilter`/pagine dedicate, è il meccanismo scelto per esporre le viste: ogni `Tab` delega per intero al query object corrispondente (`fn (): Builder => XyzQuery::for($user)`), zero logica di filtro scritta nella pagina. Il set di tab differisce per ruolo usando lo stesso gate già stabilito in US-110 (`TicketFieldAccess::canManageInternalFields()`): un cliente vede solo "I miei ticket"/"Archivio", lo staff vede tutte le altre. Riusare questo schema per qualunque futura famiglia di viste su un'altra resource: un tab per vista, query object come unica fonte del filtro.
- **"Giorni in attesa"/"giorni nello stato corrente" si calcola da `status_changed_at` (colonna diretta, sempre popolata dalla macchina a stati) con `->diffInDays(now())`**, mai una subquery o un campo derivato salvato: la colonna `Giorni in stato` di `TicketsTable` usa `getStateUsing()` proprio per questo. Nota Larastan: il cast di `status_changed_at` è dichiarato non-nullable nel PHPDoc del modello, quindi un `?->` su quella proprietà genera l'errore `nullsafe.neverNull` — usare `->` semplice.
- **Costruire il bottone giusto per l'auto-assegnazione silenziosa** (§6.1.3, attore `AutoAssigningDeveloper`): se `$transition->actors` include `AutoAssigningDeveloper` e l'utente corrente NON ha `Permission::TicketTransitionAny` (quindi non è admin/manager), il context `assignee_id` va precompilato con l'id dell'utente corrente e **nessun campo di scelta assegnatario va mostrato nel modale** — un admin/manager che esegue la stessa transizione, invece, deve poter scegliere esplicitamente a chi assegnare (nessuna auto-assegnazione silenziosa per loro). La stessa `Transition` serve quindi due UX diverse a seconda di chi la sta eseguendo.

## TicketResource — filtri (US-112, §8.5.1)

- **Tre forme di `Tables\Filters\*` per tre bisogni diversi, tutte in `TicketsTable::configure()`**: (1) `SelectFilter::make('colonna')->options(...)` SENZA `->relationship()` per un filtro diretto su una colonna scalare della tabella `tickets` (status/type/priority — `apply()` produce un semplice `where`/`whereIn`, nessuna subquery); (2) `SelectFilter::make('relazione_id')->relationship('relazione', 'campoTitolo')` per un filtro su una BelongsTo/BelongsToMany (assignee/tester/requester/tags — Filament genera da sé un `whereHas`/`whereIn` coerente, con `->multiple()` per selezione multipla come su `tags`); (3) `Filter::make('nome')->schema([...])->query(fn (Builder $query, array $data) => ...)` per qualunque filtro che non è un semplice match di valore (organizzazione del richiedente via doppio `whereHas` innestato `requester→organizations`, pattern sul nome di un tag, intervallo di date su un campo scelto a runtime, conteggio `has('tags', '>', 1)`/`whereDoesntHave('tags')`). Non forzare la forma (1)/(2) quando serve la (3): il `->query()` custom su un `Filter` riceve `$data` con le chiavi esatte dei componenti dichiarati in `->schema()` (qui `pattern`, o `field`/`from`/`until`), non `value`/`values` (quelle sono solo per `SelectFilter`/`TernaryFilter`).
- **I filtri compongono con i tab di `getTabs()` (US-111) senza alcun collegamento esplicito**: un `Tab::make()->modifyQueryUsing(...)` e i filtri dichiarati in `->filters([...])` sono due modifiche indipendenti applicate in sequenza allo stesso `Builder` della tabella — non serve far leggere ai query object un filtro attivo né viceversa. Se una futura resource aggiunge sia viste (tab) sia filtri, non introdurre un meccanismo di composizione ad-hoc: funziona già così.
- **Un campo la cui colonna cambia a runtime in una query (qui `period`, `created_at` **oppure** `done_at` a scelta dell'utente) va sempre whitelistato esplicitamente nel `->query()`** (`in_array($data['field'] ?? null, ['created_at', 'done_at'], true) ? ... : 'created_at'`), anche se il valore arriva da un `Select` con opzioni fisse in UI: un Livewire `set()` diretto in test (o una richiesta manipolata) può scrivere un valore arbitrario in quella chiave prima che la validazione del form scatti.
- **Testare un `Filter`/`SelectFilter` con `Livewire::test(ListPage::class)->filterTable($nome, $dato)`** (trait `Filament\Tables\Testing\TestsFilters`, già disponibile senza setup): la forma di `$dato` dipende dal TIPO di filtro, non dal nome del campo — per un `SelectFilter` singolo un valore scalare/Model/BackedEnum diventa `['value' => ...]` automaticamente (`['values' => [...]]` se `->multiple()`), per un `Filter` senza schema un booleano diventa `['isActive' => bool]`, per un `Filter`/`SelectFilter` con `->schema([...])` custom passare invece l'array completo con le chiavi esatte dei campi (es. `filterTable('period', ['field' => 'done_at', 'from' => '2026-03-01', 'until' => '2026-03-31'])`, `filterTable('tag_name_pattern', ['pattern' => 'T1 2026'])`) — passare un valore scalare a un filtro con schema non fa nulla silenziosamente, va sempre l'array. `->set('activeTab', 'chiave_tab')` seguito da `filterTable(...)` è il modo per verificare che un filtro si componga con una vista.
- Helper di test `grantTicketPanelRole()` (prima locale a `TicketResourceTest.php`, US-110) e il nuovo `tag(array $attributes = [])` sono stati spostati/aggiunti in `tests/Pest.php`: qualunque test Filament futuro sul dominio Ticketing che ha bisogno di un ruolo minimo per il gate del pannello o di un `Tag` di fixture li riusa da lì, mai una seconda dichiarazione locale (stesso gotcha di redeclare già documentato per `ticket()`/`systemUser()`).

- **Una sola query per popolare N colonne di un board, mai una query per colonna**: `WorkBoard::columns()` carica TUTTI i ticket visibili (+ filtro assegnatario opzionale) in un'unica query con `->with(['requester.organizations', 'tags'])`, poi raggruppa in PHP con `->groupBy(fn (Ticket $t) => $t->status->value)` e mappa su `TicketStatus::cases()` per garantire una entry (anche vuota, `collect()`) per ogni stato. Per "attività recenti" invece di un `whereHas('ticket', fn ($q) => $q->visibleTo($user))` (che Larastan non riesce a tipizzare: il closure di `whereHas` riceve un `Builder<Model>` generico, non `Builder<Ticket>`, quindi non risolve lo scope locale `visibleTo()` → errore `method.notFound`), si passa da un `pluck('id')` esplicito (`Ticket::query()->visibleTo($user)->pluck('id')`) seguito da un `whereIn('ticket_id', $ids)` sul modello target: due query semplici, nessun problema di generici, ancora nessun N+1.
- **`TicketLogFormatter` (`App\Filament\Resources\Tickets\Support`)**: il testo leggibile di un `TicketLog` (`describe(TicketLog $log): string`, già usato dallo "Storico" di `TicketInfolist`, US-110) è stato estratto in questa classe dedicata perché serviva anche alla sezione "Attività recenti" della vista di lavoro — riusarlo per qualunque futuro punto che deve mostrare un log in una riga, mai duplicare di nuovo il `match` sugli eventi.
- **Cambio di stato dal board = link alla pagina del ticket, non un secondo set di action dinamiche**: l'AC richiede solo che il cambio di stato passi dalle transizioni ammesse, non che il board stesso le esponga; costruire N ticket × M transizioni possibili come `Filament\Actions\Action` dinamiche in un contesto multi-record (a differenza di `TicketTransitionActions::build()`, pensata per un solo record) sarebbe complessità reale senza necessità per una "versione essenziale" — ogni card è semplicemente `<a href="{{ TicketResource::getUrl('view', ['record' => $ticket]) }}">`, dove i bottoni di transizione già testati (US-110) restano l'unico modo di cambiare stato. Drag & drop non è stato implementato (esplicitamente opzionale nell'AC): la rifinitura resta in Fase 6.
- **Gotcha Larastan su un `Collection::first()` di una relazione `BelongsToMany`**: un `?->` dopo `->organizations->first()` viene segnalato `nullsafe.neverNull` anche se `first()` può restituire `null` a runtime (collection vuota) — a differenza del solito pattern "estrai una variabile e testa `=== null`", qui l'unica soluzione pulita è assegnare il risultato a una variabile e fare il confronto esplicito (`$organization = $requester->organizations->first(); return $organization !== null ? $organization->name : ...;`), non un secondo `?->` in linea.
- **Gotcha ambientale**: `php artisan test` in questo ambiente ignora il flag `-d memory_limit=1G` passato al binario `php` (artisan `test` rilancia PHPUnit in un processo figlio senza propagare gli ini settings dal comando di lancio) e va comunque in OOM sulla suite intera con il default 128M — usare invece `php -d memory_limit=1G vendor/bin/pest` (Pest/PHPUnit diretto, stesso processo) per un run completo.
- **Gotcha ambientale CRITICO (scoperto durante US-R02)**: dentro il container `app`, `DB_CONNECTION=pgsql`/`DB_HOST=db`/ecc. sono variabili d'ambiente **reali del processo** (iniettate da `env_file: .env` in `docker-compose.yml` al momento della creazione del container), non solo valori nel file `.env`. Gli `<env>` di `phpunit.xml` (`DB_CONNECTION=sqlite`, `DB_DATABASE=:memory:`, ...) **non hanno `force="true"`**: PHPUnit non sovrascrive una variabile d'ambiente già presente nel processo reale, quindi `docker compose exec app vendor/bin/pest`/`php artisan test` girano silenziosamente contro il vero Postgres di sviluppo (`db`) invece che sqlite in-memory. Effetto collaterale serio: `RefreshDatabase` esegue `migrate:fresh` sul primo test della suite, **cancellando i dati reali del database di sviluppo** (es. quelli appena importati con `v1:import`). Sintomo tipico: decine di failure spurie non legate al proprio codice (es. `SQLSTATE[25P02]: current transaction is aborted`, ruoli Spatie che risultano non assegnati) che spariscono se isolate correttamente. Workaround verificato per un run corretto: `docker compose exec -T app env -u DB_CONNECTION -u DB_DATABASE -u DB_HOST -u DB_PORT -u DB_USERNAME -u DB_PASSWORD php -d memory_limit=512M vendor/bin/pest` (rimuove le var d'ambiente reali prima di invocare Pest, lasciando che gli `<env>` di `phpunit.xml` si applichino). Non è stato corretto qui (fix di `phpunit.xml`/`docker-compose.yml` fuori scope per una story ETL): resta da fare in una story dedicata. Nel frattempo, isolare sempre così prima di interpretare un test fallito come una regressione.
- **Failure pre-esistenti reali confermati con l'isolamento corretto sopra (non causati da US-R01/US-R02, verificati a diff `*.php` vuoto rispetto a `86530c2`)**: 22 failure, tutte per limiti dell'immagine Docker locale o bug applicativi indipendenti dall'ETL — estensione PHP `gd` non installata (`AddTicketAttachmentTest`/`RemoveTicketAttachmentTest`/`TicketAttachmentDownloadControllerTest` generano immagini fake via GD), più un gruppo eterogeneo in `RecalculateWorkedTimeOnStatusChangeTest`/`PasswordResetTest`/`RoleAndPermissionManagementTest`/`TicketResourceTest` (job non accodati, notifiche non inviate, salvataggi Filament che non persistono) — non indagati oltre perché fuori scope per US-R02. Il vecchio riferimento a "7 failure LaTeX/pdflatex preesistenti" (nota US-R01) non è più accurato: quei test passano ora.
- **AGGIORNATO in US-R05 (nessun file PHP toccato da questa story, diff `*.php` vuoto): il conteggio è salito a 23**, un `Tests\Feature\Filament\Ticketing\TicketResourceTest` in più rispetto al 305 sopra (7 invece di 6, riprodotto anche isolando il solo file: `vendor/bin/pest tests/Feature/Filament/Ticketing/TicketResourceTest.php` dà consistentemente 7 failed/9 passed, non è quindi un flake order-dependent) — non indagato oltre perché fuori scope per una story di sola infrastruttura Docker/env. Se il conteggio cambia ancora, verificare sempre prima con `git diff --stat -- '*.php'` se la propria story ha davvero toccato codice applicativo prima di considerarlo una regressione.
- **Gotcha Docker Compose (US-R05, `docker-compose.uat.yml`)**: `env_file: <file>` su un servizio e `docker compose --env-file <file>` sono due meccanismi distinti che qui capita puntino allo stesso file (`.env.uat`) — il primo inietta OGNI variabile del file nell'ambiente reale del container a runtime, il secondo risolve solo le interpolazioni `${VAR}` nel compose file al parse time. Una variabile usata SOLO per un bind-mount lato host (es. `LEGACY_MEDIA_HOST_PATH`, un path del filesystem di msuat) non va MAI chiamata come l'env var applicativa che il container legge per lo stesso concetto (`LEGACY_MEDIA_PATH`, letta da `config/filesystems.php` come path DENTRO al container): se condividessero il nome, `env_file:` la inietterebbe nel container con il valore host, un path che non esiste dentro l'immagine, rompendo silenziosamente il disco. Nomi deliberatamente distinti quando lo stesso "concetto" serve sia all'host (interpolazione Compose) sia al container (env applicativa). Nota anche per la verifica (`docker compose config --quiet` con variabili `${VAR:?err}`): serve un vero file `.env.uat` temporaneo nella working directory (rimosso subito dopo), non un file con nome diverso passato a `--env-file` — `env_file:` dentro il servizio è un riferimento letterale al nome file e non risente di quel flag.

## Verifica end-to-end di Fase 1 (US-114, §14)

- **Un test E2E percorre l'intero ciclo di vita con Action reali in sequenza (`CreateTicket` → N × `ChangeTicketStatus` → ...), mai stato seminato direttamente nel DB** (a differenza dell'helper `ticket([...])` usato dai test per-Action/regola): è l'unico modo per verificare che la composizione delle story funzioni davvero insieme, non solo ogni Action in isolamento. Vedi `tests/Feature/Domain/Ticketing/TicketLifecycleEndToEndTest.php`.
- **`$this->travelTo(CarbonImmutable::parse(...))` prima di ogni `ChangeTicketStatus::run()`** è il modo per costruire una sequenza di `ticket_logs` con `occurred_at` deterministici, poi passata a `WorkedTimeCalculator`/`RecalculateWorkedTime::run()` per assertare `worked_minutes`/`ticket_work_logs` con numeri esatti (non solo "maggiore di zero"). Usare sempre un giorno feriale noto (es. lunedì) per evitare il weekend-skip dell'algoritmo.
- **Un log identificato solo da `to_status` non è univoco quando lo stesso stato di destinazione viene raggiunto più volte nello stesso test** (es. `to_status = todo` sia dalla transizione ordinaria `assigned → todo` sia da una demozione `progress → todo` successiva): filtrare sempre anche su `from_status` prima di uno `->sole()`, mai un `->latest(...)->sole()` (`sole()` conta l'intero risultato della query, l'ordinamento non lo riduce a una riga).
- **Due livelli di difesa distinti contro una transizione/contesto manipolato, da testare separatamente**: (1) Filament risolve `$data` di un'action dallo **stato dello schema dichiarato**, non dall'array grezzo — un campo iniettato via `setActionData()` ma assente dallo schema (es. `assignee_id` quando l'attore si auto-assegna, US-110) viene ignorato, non genera un errore; (2) `TicketStateMachine::authorize()`/i guard degli attori (es. `AutoAssigningDeveloper::authorize()`, US-101) restano comunque la difesa "vera", verificabile chiamando `ChangeTicketStatus::run()` direttamente con un `context` impersonato, indipendentemente da qualunque comportamento di Filament. Un test che assume che (1) da solo basti a dimostrare la sicurezza è un test debole: verificare sempre anche (2).

## Verifica in browser di un'Action Filament autenticata (US-402)

- **Lo screenshot statico via `chrome --headless --screenshot` (vedi nota sotto) basta per una pagina pubblica
  (login), ma NON permette di cliccare un bottone/riempire un modale**: è un singolo page-load, nessuna
  interazione JS scriptabile da CLI. Per verificare un'Action Filament/Livewire autenticata (aprire il modale,
  compilare i campi precompilati, inviare, controllare la notifica di successo) serve un vero driver browser:
  Playwright è già installabile via `npx --yes playwright install chromium` (cache in
  `~/Library/Caches/ms-playwright/`, non richiede un tool MCP dedicato) e uno script `.mjs` in `/tmp` (mai nel
  repo) con `chromium.launch()` → `page.goto('/admin/login')` → `fill`/`click` sulle credenziali → naviga alla
  pagina/record target → `click` sul bottone dell'action per aprire il modale → `click` sul bottone di submit
  DENTRO al modale (selettore per testo del bottone reale nel modale, es. "Invia", non il bottone trigger
  dietro — il trigger ha lo stesso testo dell'action e Playwright altrimenti clicca quello sbagliato/bloccato
  dall'overlay) → screenshot con `Read`.
- **I container Docker di questo progetto (`app`/`web`/`db`) non sono necessariamente già `Up`**: solo
  `queue`/`scheduler`/`redis` girano di default su questa macchina (altri servizi condivisi con altri
  progetti restano avviati separatamente). Verificare con `docker compose ps` prima di assumere che
  `http://localhost:8080` risponda, ed eventualmente avviare con `docker compose up -d app web db` (porta
  pubblicata da `web`, non da `app`: il servizio `db` non pubblica una porta host, quindi `php artisan serve`
  lato host con `DB_HOST=db` non funziona — usare sempre i container per una verifica autenticata completa).
- **Utente/dati di verifica creati via `docker compose exec -T app php artisan tinker`** (assegna un ruolo con
  `Role::findOrCreate` + `syncPermissions` su tutti i case di `Permission`, crea il record di dominio serve):
  rimuoverli sempre con `forceDelete()` subito dopo lo screenshot, per non lasciare dati fittizi nel DB di
  sviluppo condiviso.
- **Selettori Playwright per le tab di un `ListRecords` Filament (`getTabs()`)**: sono `role="tab"`, mai un
  link/testo generico — `page.getByRole('tab', { name: 'Nome tab' }).click()`. Il bottone che apre il pannello
  filtri della tabella non ha testo visibile, solo `aria-label="Filtro"` (badge numerico col conteggio filtri
  attivi accanto): `page.getByRole('button', { name: 'Filtro' }).click()`. Se un selettore per testo esatto va
  in "strict mode violation" con più corrispondenze, è quasi sempre perché un `<select>` di un `TernaryFilter`
  contiene un `<option>` con lo stesso testo del bottone/tab cercato (es. opzione "Attive" dentro un filtro
  "Scaduto") — disambiguare con `getByRole` invece di `getByText`.

- **Pipeline font Manrope (US-004) verificata end-to-end e risultata già corretta, nessun bug reale

  (dichiarazione esplicita, `!important` solo se realmente necessario dopo aver verificato in DevTools che
  serve). Regression guard: `tests/Feature/Http/AuthFontLoadingTest.php` (asserzioni HTTP sul markup
  `@font-face`/preload della pagina di login, stesso pattern di `MarketingAssetsSeparationTest.php`).
- **Gotcha selettore discendente vs figlio diretto in `components/auth/panel.blade.php` (US-005)**:
  `.mkt-auth__panel img` (pensato solo per la foto di sfondo full-bleed, figlio diretto di
  `.mkt-auth__panel`) intercettava per errore anche `img.mkt-logo`, annidato più a fondo dentro
  `.mkt-auth__panel-content`, applicandogli `position: absolute; inset: 0` e togliendolo dal flusso —
  qualunque `margin`/spaziatura sul logo diventava ininfluente, indipendentemente dal valore. Fix:
  combinatore di figlio diretto (`.mkt-auth__panel > img`). Se una story futura tocca questo
  componente e un elemento non risponde a `margin`/spacing nonostante il CSS compilato sia corretto
  (verificato via grep), controllare prima se ha ereditato `position: absolute/fixed` da un selettore
  discendente troppo generico scritto per un altro elemento — non solo il valore della proprietà.
  Tecnica di diagnosi utile: riprodurre in un file HTML statico isolato (fuori da Laravel/Livewire)
  con la stessa CSS compilata, per escludere interferenze di Alpine/Livewire. Regression guard:
  `tests/Unit/AuthHeroLogoSpacingTest.php`.
- **Misurare un dettaglio geometrico del mockup quando "a occhio" non basta a scegliere tra due token
  vicini (US-006)**: per confrontare un border-radius/spacing del mockup PNG
  (`docs/features/login-design-pixel-fixes/reference-design.png`) con l'implementazione, uno script
  Python veloce con PIL+numpy è più affidabile della sola ispezione visiva: crop della zona
  d'interesse, mask su un range di grigio per isolare il bordo dell'elemento, poi ricerca della riga/
  colonna in cui la coordinata minima si stabilizza per stimare il raggio dell'arco dell'angolo. Non
  serve conoscere lo scale factor esatto dello screenshot (Figma/design tool esportano a risoluzioni
  arbitrarie): basta la proporzione relativa fra il raggio misurato e le dimensioni dell'elemento
  (es. altezza dell'input) per capire quale token CSS esistente è il più vicino.
- **Gotcha `Livewire::test(...)->assertSeeText($value)` (US-009)**: a differenza di `assertSeeHtml()`,
  `assertSeeText()` ha `$escape = true` come default e passa il valore atteso per `e()` (HTML-encode)
  prima di confrontarlo col markup renderizzato — un apostrofo dritto (`'`) nell'asserzione diventa
  `&#039;` e non matcha più testo Blade statico (non passato da `{{ }}`), che nel markup resta un
  apostrofo letterale non incodificato. Se un'asserzione `assertSeeText()` su una stringa con
  apostrofo/`&`/`<`/`>` fallisce in modo apparentemente incomprensibile (il messaggio di errore mostra
  il valore atteso già con l'entità HTML), passare `false` come secondo argomento
  (`assertSeeText("...l'account...", false)`), esattamente come già si fa con `assertSee($value, false)`.
- **Il plugin Alpine `@alpinejs/focus` (direttiva `x-trap`) è già caricato globalmente su tutte le pagine
  Filament** (incluse le view custom come `filament/auth/login.blade.php`, che include
  `@filamentScripts(withCore: true)`), perché i modali nativi di Filament lo usano internamente
  (`vendor/filament/support/resources/views/components/modal/index.blade.php`). Per una modale Alpine
  inline "fatta a mano" (niente componente Filament, per rispettare un AC che vieta librerie di dialog
  di terze parti) si può quindi usare `x-trap.noscroll="apertaBool"` senza caricare nulla in più: la
  direttiva intrappola il focus e lo ripristina automaticamente sull'elemento che aveva il focus prima
  dell'apertura quando l'espressione torna `false` — non serve reimplementare a mano il ripristino del
  focus (va comunque bene farlo esplicitamente in aggiunta, per robustezza, come in
  `resources/views/filament/auth/login.blade.php`). Nessun rule CSS globale per `[x-cloak]` risulta
  definita nei bundle di questo progetto: per una modale con `x-show`, impostare `style="display: none;"`
  inline sull'elemento invece di affidarsi a `x-cloak`, altrimenti c'è un breve flash del contenuto prima
  che Alpine si inizializzi.

## Processo di collaudo (obbligatorio per ogni fase)

Ogni fase completata (Fase 2 in poi) deve produrre, prima di essere considerata chiusa:

1. `docs/collaudo/fase-<N>.php` — manifest topic → test numerati (es. `F2-01`) → riferimento a un test
   automatico REALMENTE esistente (`php artisan collaudo:verify-manifest <N>` deve passare).
2. **Il manuale narrativo di collaudo** (`docs/collaudo/0N-fase-N.md`, stesso formato per-test di
   `03-fase-1.md`: Obiettivo/Riferimenti/Modalità di esecuzione/Priorità/Ruolo del tester/Prerequisiti/
   Procedura di esecuzione/Criterio di superamento/Campi di consuntivazione) **è sempre l'ULTIMO passo
   dello sviluppo di una fase**, dopo che tutte le story della fase sono complete e il manifest del punto 1
   passa — mai in parallelo alle story, perché ogni test narrativo richiede di leggere il codice/test
   automatico REALE già scritto per descrivere passi ed esito attesi accurati, non ipotetici. Questa
   regola vale per ogni fase futura, non solo per quelle già chiuse: prevedere sempre, come task esplicito
   di fine fase (dopo il checkpoint end-to-end, prima del merge finale), la scrittura di questo manuale.
   Va aggiornato in coerenza anche il resto del pacchetto cumulativo: `README.md` (indice + riepilogo
   numerico), `00-istruzioni-generali.md` (§1 versione, §2/§3 ambito incluso, §4 ambito escluso, e ogni
   altra sezione toccata dalla nuova fase — es. §10 se la fase introduce un nuovo uso reale di Mailpit),
   `01-matrice-tracciabilita.md` (una riga per test, colonne Area/Titolo/Modalità/Priorità/Ruolo/Test
   automatico/Stato redazione) e `07-registro-esiti.md` (una riga ID+Titolo per test, generabile
   meccanicamente dal manifest). Le due fasi Fase 2 e Fase 3 non avevano questo manuale fino al 24 agosto
   2026 (retrofit fatto in quella data, versione 3.0 del pacchetto): non ripetere questo gap per le fasi
   successive (Fase 4/5/6).
3. `php artisan collaudo:generate <N>` — PDF di collaudo con carta intestata Montagna Servizi, Parte 1
   (istruzioni: URL app UAT, URL Mailpit, credenziali) + una sezione per topic con i test numerati.
   `storage/app/collaudo/` deve contenere **sempre e solo l'ultima versione generata per ciascuna fase**
   (sia la variante sintetica `collaudo-fase-<N>-*.pdf` sia, quando applicabile, quella dettagliata
   `collaudo-dettagliato-fase-<N>-*.pdf`): `CollaudoGenerateCommand` cancella da sé ogni PDF precedente
   della stessa fase/variante prima di scrivere quello nuovo (vedi sezione successiva) — non disabilitare
   né aggirare questo comportamento, e non lasciare accumulare manualmente PDF vecchi in quella cartella.
4. Il deploy su UAT (automatico al merge su `develop`) deve riflettere lo stato descritto nel manifest:
   l'ETL reale (`migrate:fresh` → `RolePermissionSeeder` → `v1:import --anonymize`, `deploy/remote-deploy.sh`,
   US-R05/US-R06) gira ad ogni deploy — sostituisce il seed fittizio usato prima di questo PRD.
5. Se un test del collaudo fallisce durante una sessione di collaudo reale, il test automatico
   corrispondente (dal manifest) va rivisto: non copriva il caso reale che ha fatto fallire il collaudo.

## Pipeline email inbound — configurazione IMAP (US-301)

- `App\Domain\Mail\Contracts\InboundMailTransport` (§7.4 del PRD) ha due metodi: `fetch(int $limit, ?DateTimeInterface $since = null): list<RawInboundEmail>` (limit sempre esplicito, mai un default nell'interfaccia) e `move(string $imapFolder, int $imapUid, ImapFolderRole $targetFolder): void`. `App\Domain\Mail\Support\RawInboundEmail` (readonly DTO: `rawMessage`/`imapFolder`/`imapUid`) e `App\Domain\Mail\Enums\ImapFolderRole` (`Inbox`/`Processed`/`Errors`/`Quarantine`) vivono accanto al contratto. `App\Domain\Mail\Transports\WebklexImapTransport` è l'unica implementazione oggi, legata all'interfaccia in `App\Providers\MailServiceProvider` (registrato in `bootstrap/providers.php`, stesso pattern "un provider per modulo isolato" di `ImportServiceProvider`) con un semplice `$this->app->bind(...)` (non un registry: qui c'è una sola implementazione, a differenza degli stage ETL).
- **`webklex/php-imap` (libreria standalone, mai `webklex/laravel-imap`, vietato dal PRD)**: `Webklex\PHPIMAP\ClientManager::make($accountConfig)` costruisce un `Client` da un array di configurazione (forma: `host`/`port`/`encryption`/`validate_cert`/`username`/`password`, vedi `vendor/webklex/php-imap/src/config/imap.php` per lo schema completo) — poi `$client->connect()`. Un messaggio si legge con `$client->getFolder($nome)->query()->whereSince($data)` (o `->whereAll()` senza `$since`) `->limit($n)->get()`: `Query::fetch()` esegue prima una SEARCH IMAP (solo UID, nessun body) e applica `limit`/`page` alla lista di UID risultante PRIMA di scaricare header/body solo per quella pagina — è già di per sé la protezione OOM richiesta dal PRD (mai bisogno di un guard applicativo aggiuntivo per questo). Un singolo messaggio per uid: `$client->getFolder($nome)->query()->getMessageByUid($uid)`; per spostarlo: `$message->move($nomeCartellaDestinazione, expunge: true)`.
- **Ricostruzione del `.eml` grezzo**: `webklex/php-imap` non espone un metodo "raw message" diretto, ma `Message::save()` (usato internamente dalla libreria) rivela il pattern esatto: `$message->getHeader()->raw."\r\n\r\n".$message->getRawBody()` (header raw + separatore CRLF doppio + body raw) è l'`.eml` completo. Riusare questa stessa concatenazione ovunque serva il contenuto grezzo (qui in `WebklexImapTransport::fetch()`, e in US-302 per scrivere il file su disco prima di qualunque parsing) — non improvvisare un formato diverso.
- **Nomi di cartella IMAP mai come stringa letterale nel codice applicativo**: `App\Domain\Mail\Enums\ImapFolderRole` astrae il "ruolo" (inbox/processed/errors/quarantine) dal nome reale sul server (arbitrario, configurato da chi gestisce la casella); `WebklexImapTransport::folderName(ImapFolderRole)` risolve il nome reale da `config('mail_pipeline.folders')` e lancia `RuntimeException` se il ruolo richiesto non ha una voce configurata. Questa risoluzione avviene sempre PRIMA di toccare la connessione IMAP (`$this->folderName(...)` chiamato come statement separato, non inline nell'argomento di una chiamata che already networked) — permette di testare la configurazione mancante senza un server IMAP reale né mock del client Webklex (vedi `WebklexImapTransportTest`, due test "fails fast... before ever attempting to connect").
- `config/mail_pipeline.php` (distinto da `config/mail.php`, che resta l'invio SMTP nativo Laravel) è la SOLA fonte di `env()` per questo modulo (§13.3 del PRD): account IMAP, cartelle, `fetch.default_limit` (50), `rate_limit.max_per_hour`/`max_per_day` (soglie anti-loop, US-304), `staff_notification_group` (array da CSV, stesso pattern di `config('orchestrator.anonymization.mail_test_domains')`) e `support_address`. Le fasi successive (US-302+) aggiungono chiavi qui, mai un secondo file di config per lo stesso modulo.

## Scheduler — niente `->timeout()` su `Schedule::command()` (Laravel 13, US-302)

`Illuminate\Console\Scheduling\Event` in questo Laravel (v13.22) **non ha un metodo `timeout()`**: esiste solo per i comandi lanciati in un vero sottoprocesso in background (`->runInBackground()`), non per l'esecuzione in-process di default. Chiamarlo su una entry `Schedule::command(...)` qualsiasi (anche senza `->runInBackground()`) fa fallire l'intero bootstrap di Laravel con `BadMethodCallException`, quindi ANCHE `php artisan` e Larastan smettono di funzionare finché non si rimuove la chiamata — non è un errore silenzioso, ma vale la pena saperlo prima di scriverlo. Per un timeout esplicito su un comando schedulato, imporlo dentro `handle()` del comando stesso con `set_time_limit((int) config(...))` (vedi `MailFetchInboundCommand::handle()`); `->withoutOverlapping()` invece esiste ed è il modo corretto per l'anti-overlap a livello di scheduler. Rilevante anche per US-316/US-325 (altri comandi da schedulare in questa fase).

## Parsing del `.eml` grezzo — subject/corpo/citazioni (US-303)

- `Webklex\PHPIMAP\Message::fromString($blob)` (nessuna connessione IMAP, stessa libreria di US-301) è il modo corretto per riaprire un `.eml` già archiviato da US-302 e riestrarne subject/corpo: `$message->hasTextBody()`/`getTextBody()`, `hasHTMLBody()`/`getHTMLBody()`. La conversione di **charset del corpo** (`text/plain`/`text/html`) funziona correttamente anche senza l'estensione PECL `imap` (verificato empiricamente con un fixture ISO-8859-1) — nessun problema noto lì.
- **Gotcha reale, verificato empiricamente**: `Message::fromString()`/`getSubject()->toString()` NON decodifica gli header MIME "encoded-word" (`=?UTF-8?Q?...?=`, RFC 2047) quando l'estensione PECL `imap` non è caricata — mai il caso in questo progetto (`webklex/php-imap` è stato scelto proprio per non dipendere da quell'estensione). `HeaderDecoder::mimeHeaderDecode()` senza quell'estensione si limita a un `convertEncoding()` sulla stringa ancora codificata: il pattern `=?...?=` resta intatto nell'output. Qualunque codice che legge un header testuale (subject, ma potenzialmente anche i display name `From`/`To` per US-305/US-307) da un `Message` costruito con `fromString()` deve decodificare da sé con `mb_decode_mimeheader()` — non fidarsi che la libreria l'abbia già fatto. `App\Domain\Mail\Parsers\SubjectNormalizer` lo fa per il subject; se una story futura legge un altro header MIME-encoded, applicare lo stesso pattern lì.
- `App\Domain\Mail\Parsers\{SubjectNormalizer,EmailBodyParser,QuotedTextRemover}` sono le tre classi pure (nessuna dipendenza da Eloquent/IO) di questa story, orchestrate da `App\Domain\Mail\Actions\ParseInboundEmail::run(EmailMessage $m): EmailMessage`, che è l'unico punto che tocca disco/DB: legge `raw_path` dal disco `mail_pipeline.storage.raw_disk`, chiama `Message::fromString()`, scrive `subject`/`body_text`/`body_html`/`status=parsed` sul record. **Qualunque eccezione** in questo processo (file mancante, `.eml` malformato) è catturata dentro l'Action stessa: mai propagata, sempre loggata (`Log::warning`), il messaggio passa a `status=failed` con `failure_reason` — un batch futuro che processa più email in sequenza non deve mai fermarsi al primo messaggio corrotto.
- `SubjectNormalizer::normalize()` **non rimuove** il token `[#<id>]` dal subject restituito (lo espone solo separatamente come comodità): US-306 (risoluzione thread, livello 3) lo cerca direttamente dentro il subject normalizzato già salvato su `email_messages.subject`, quindi deve restarci.
- `EmailBodyParser` riusa direttamente `App\Domain\Ticketing\Support\TicketMessageSanitizer` (cross-domain, esplicitamente sanzionato dal PRD per questa story) sia per sanitizzare `body_html` sia per derivare `body_text` da HTML quando il `text/plain` manca (`toPlainText()` sul HTML già sanitizzato, mai sul grezzo).
- `QuotedTextRemover::stripHtml()` rimuove i nodi `<blockquote>` via `DOMDocument`/`DOMXPath` (il modo in cui Gmail/Outlook web/Apple Mail marcano semanticamente il testo citato in HTML), non con una regex sui tag — coerente con "mai una regex generica non testata" del PRD (problema 8 del v1). `strip()` (versione plain text) taglia al primo indizio di citazione/firma trovato riga per riga (non un singolo regex su tutto il blob): righe che iniziano con `>`, `On ... wrote:`/`Il ... ha scritto:`, `-----Original Message-----`, il delimitatore di firma RFC 3676 (riga esattamente `--`/`-- `), o un blocco header Outlook `From:`/`Da:` **verificato** guardando le 4 righe successive per `Sent:`/`Inviato:`/`To:`/`A:`/`Subject:`/`Oggetto:` (evita falsi positivi su una frase normale che inizia per "From:").
- **Pest**: `->throwsNoExceptions()` in coda a un test che ha già delle `expect()` reali va in conflitto ("not expected to perform assertions but performed N") — usarlo SOLO su test che non fanno alcuna asserzione esplicita, mai insieme a `expect()`.

## Classificazione anti-loop — header di controllo e rate limit (US-304)

- Gli header di controllo (`Auto-Submitted`, `Precedence`, `List-Id`, `List-Unsubscribe`, `X-Auto-Response-Suppress`, `Content-Type`) non sono mai stati estratti da `ParseInboundEmail` (solo subject/corpo lo sono): `App\Domain\Mail\Actions\ClassifyInboundEmail` rilegge il `.eml` da `mail_pipeline.storage.raw_disk` e chiama di nuovo `Webklex\PHPIMAP\Message::fromString()->getHeader()`, stesso pattern I/O di `ParseInboundEmail` (try/catch totale, `status=failed` con `failure_reason` su qualunque eccezione, mai propagata).
- `Webklex\PHPIMAP\Header::get($name)` restituisce sempre un `Attribute`, mai `null`, e il nome è case/dash-insensitive (`get('Content-Type')` == `get('content-type')`). **Gotcha verificato empiricamente**: `Attribute::toString()` concatena TUTTI i valori con virgola se l'header appare più volte anche solo semanticamente (es. `Content-Type` di un messaggio multipart viene ri-registrato una seconda volta dalla struttura MIME) — usare sempre `Attribute::first()` per leggere il valore "vero" dell'header, mai `toString()`, quando serve un singolo valore da confrontare. `Attribute::first()` restituisce `false` (non `null`) se l'header non è presente (`reset()` su un array vuoto) — va normalizzato esplicitamente a `null`.
- Un DSN si riconosce SOLO da `Content-Type: multipart/report; report-type=delivery-status` (verificato con un fixture multipart valido: boundary + parti `text/plain` e `message/delivery-status`, altrimenti `Message::fromString()` lancia `MessageContentFetchingException: no content found` — un multipart/report senza boundary/parti valide non è un test utile). Altri `report-type` (es. `feedback-report`) non sono DSN e proseguono nella pipeline normale.
- Il "mittente della piattaforma stessa" per la regola self-sender è `config('mail_pipeline.support_address')` (lo stesso indirizzo usato come mittente degli auto-reply, non un secondo indirizzo da configurare).
- `App\Domain\Mail\Models\EmailSuppression::scopeActive()` (nuovo) filtra le soppressioni senza `expires_at` o non ancora scadute: da riusare per qualunque controllo futuro su "il mittente è soppresso adesso" (outbound E1-E7+E9, US-311+), non solo per l'anti-loop di questa story.
- Il rate limit anti-loop (`mail_pipeline.rate_limit.max_per_hour`/`max_per_day`) NON scarta il messaggio (a differenza di tutte le altre regole di questa story): il messaggio prosegue a `status=classified`, ma il mittente va/rimane in `email_suppressions` con `reason=loop_protection` ed `expires_at = now()->addHours(mail_pipeline.rate_limit.suppression_hours)` — è compito delle story outbound (US-311+) controllare `EmailSuppression::active()` prima di inviare un auto-reply, questa story si limita a popolare la tabella.
- `App\Domain\Mail\Enums\EmailDiscardReason` è il motivo salvato in `email_messages.failure_reason` quando `status=discarded` (riuso della colonna esistente, nessuna nuova colonna: lo schema è congelato da Fase 0). Un futuro US-319 può filtrare `status=discarded AND failure_reason='delivery_status_notification'` per correlare i DSN all'email originale invece di reinterpretare uno scarto generico.

## Risoluzione del thread — VERP/In-Reply-To/subject/euristica (US-306)

- `email_messages.to`/`in_reply_to`/`references` NON erano mai stati popolati prima di questa story (US-302 scriveva solo `message_id`/`from_email`/`from_name`/`subject`): `RawInboundEmail` (US-301), `WebklexImapTransport::fetch()` e `StoreRawInboundEmail` sono stati estesi per leggerli/salvarli, altrimenti `App\Domain\Mail\Actions\ResolveEmailThread` non avrebbe mai dati su cui matchare in produzione. `references` è una colonna `text` (non jsonb): salvata come stringa singola con i message-id separati da spazio (stesso formato del header RFC), non JSON — va sempre `explode(' ', ...)` per rileggerla, mai `json_decode`.
- **Gotcha ULID verificato empiricamente**: in questo progetto `HasUlids` genera ULID in MINUSCOLO (es. `01m0a66ty8xa3n29xg7jx961j1`), non nel case canonico Crockford (maiuscolo) che ci si aspetterebbe da Symfony Ulid. Qualunque confronto su una colonna `ulid` (qui il local-part VERP `ticket+<ulid>` estratto dal destinatario `To`) deve essere case-insensitive (`whereRaw('lower(ulid) = ?', [strtolower($valore)])`), mai un confronto diretto `where('ulid', $valore)` — vale per `ticket_messages.ulid` ed `email_messages.ulid` allo stesso modo.
- `App\Domain\Mail\Parsers\SubjectNormalizer::normalizeForThreadMatching()` (nuovo, pubblico) è ORA l'unica funzione di normalizzazione "per confronto" del subject: `App\Import\Stages\DeriveStage::normalizeSubject()` (Fase 2, popola `email_threads.subject_normalized` dai titoli ticket importati) delega a questa stessa funzione invece di duplicarla — se in futuro cambia l'algoritmo di normalizzazione per il matching euristico, va cambiato SOLO qui, mai in `DeriveStage` separatamente, altrimenti i due lati del confronto (subject email vs `subject_normalized` del thread) divergono silenziosamente. Diversa da `SubjectNormalizer::normalize()` (US-303): quella preserva il token `[#<id>]` e il case originale (serve per il livello 3 e per mostrare il subject "vero" all'utente), questa lo rimuove e minuscolizza (serve solo per il confronto di uguaglianza del livello 4).
- `App\Domain\Mail\Actions\ResolveEmailThread::run()` è puramente in lettura (nessuna scrittura su `email_messages`/`email_threads`): restituisce un `App\Domain\Mail\Support\ThreadResolution` (`ticketId`/`matchLevel`/`isHeuristic()`), è `US-307` (applicazione) a decidere cosa scriverci sopra. I quattro livelli (VERP → In-Reply-To/References → token subject → euristica) si fermano al primo match, mai un "livello migliore vince se in conflitto" — l'ordine di chiamata stesso garantisce questo, non serve comparare priorità esplicitamente.

## Applicazione sul ticket — orchestrazione resolve-sender→thread→apply, notifiche post-commit (US-307)

- `App\Domain\Mail\Actions\ApplyInboundEmail::run(EmailMessage $m): EmailMessage` (§7.3.7) è il primo punto della pipeline che concatena PIÙ Action con codice reale, non solo per story separate: chiama `ResolveEmailSender` (US-305) poi, solo se il mittente è identificato, `ResolveEmailThread` (US-306), e in base al risultato crea un ticket (`CreateTicket`, `type=helpdesk`) o accoda un messaggio su uno esistente (`Ticket::findOrFail($resolution->ticketId)`) — SEMPRE seguito da `PostTicketMessage::run($ticket, $user, $bodyHtml, TicketMessageChannel::Email)` e dall'update di `email_messages` (`status=applied`, `ticket_id`) nella STESSA `DB::transaction()`. Precondizione: se `$m->status !== Classified` è un no-op immediato; se il mittente non è identificabile esce senza creare nulla (`status` resta quello impostato da `ResolveEmailSender`, quarantena/US-308).
- **`App\Domain\Ticketing\Actions\PostTicketMessage` ora accetta un 4° parametro opzionale** `TicketMessageChannel $channel = TicketMessageChannel::Web` (retro-compatibile): l'enum `TicketMessageChannel::Email` esisteva già da Fase 1 ma nessun chiamante lo passava. La regola T7 (`RestoreTicketStatusOnRequesterMessage`, registrata su `TicketMessagePosted` in `AppServiceProvider::boot()`) si applica automaticamente a qualunque canale, nessuna modifica necessaria al listener.
- **Notifiche post-commit senza Mailable ancora esistenti**: nuovo evento `App\Domain\Mail\Events\InboundEmailApplied` (`Ticket`, `EmailMessage`, `bool $isNewTicket`), dispatchato con `event()` DOPO che `DB::transaction()` è già tornato (mai dentro), con la chiamata avvolta nel proprio try/catch che loggasi soltanto — un fallimento nella notifica non deve mai disfare il ticket/messaggio già committati (problema 2 del v1: un fallimento SMTP che impediva di marcare l'email come elaborata causava duplicati infiniti). **Nessun listener è ancora registrato** su questo evento (stesso pattern già usato per `TicketCreated` in Fase 1): US-311 (E1, conferma al mittente) e US-312 (E3, notifica staff) devono registrarsi qui in `AppServiceProvider::boot()`, e i loro listener DEVONO implementare `ShouldQueue` — è il listener, non il dispatch dell'evento, a garantire "mai in modo sincrono". US-308, quando gestisce il riprocessamento post-quarantena (US-322), può richiamare direttamente `ApplyInboundEmail::run($m)` una volta associato l'utente: non serve una nuova Action che duplichi la chiamata a `ResolveEmailSender`.
- **`App\Console\Commands\MailFetchInboundCommand` (US-302) NON chiama ancora questa Action**: wire-uppare l'intera pipeline fetch→parse→classify→apply dentro il comando romperebbe `MailFetchInboundCommandTest`, che asserisce `status === EmailStatus::Received` subito dopo `mail:fetch-inbound`. Quel wiring end-to-end (e l'adeguamento dei test US-302 che oggi assumono `status=received` a fine comando) è compito esplicito di US-326.

## Quarantena mittente sconosciuto — riprocessamento e notifica (US-308)

- `App\Domain\Mail\Actions\ApplyInboundEmail::run()` accetta ora `status` iniziale `Classified` **o** `Quarantined` (non solo `Classified`): questa è la precondizione che rende possibile il riprocessamento richiesto da US-322 ("associa a utente esistente"/"crea nuovo utente e ticket" → richiama di nuovo `ApplyInboundEmail::run($m)` sullo stesso `EmailMessage`). Nessuna nuova Action dedicata al riprocessamento: è la stessa Action di sempre, resa idempotente.
- **Gotcha reale trovato scrivendo il test di riprocessamento**: `App\Domain\Mail\Actions\ResolveEmailSender` on-success (mittente risolto) DEVE riportare esplicitamente `status` a `Classified` (`forceFill(['user_id' => ..., 'status' => EmailStatus::Classified])`), non solo impostare `user_id`. Senza questo reset, un messaggio richiamato da `status = Quarantined` che ora risolve il mittente resterebbe con `status` ancora `Quarantined` nonostante `user_id` sia valorizzato, e `ApplyInboundEmail` lo tratterebbe di nuovo come quarantena invece di procedere alla creazione/aggiornamento del ticket — bug silenzioso, catturato solo da un test end-to-end che ricrea esattamente lo scenario "riprocessa dopo associazione manuale", non da un test isolato su `ResolveEmailSender` chiamato da uno stato `Classified` pulito.
- **Notifica E9 ancora senza Mailable/listener** (stesso pattern di `InboundEmailApplied`, US-307): nuovo evento `App\Domain\Mail\Events\EmailQuarantined(EmailMessage $emailMessage, bool $autoReplyAllowed)`, dispatchato da `ApplyInboundEmail` subito dopo che `ResolveEmailSender` lascia il messaggio in `status = Quarantined` (mittente non identificato), avvolto nel proprio try/catch che loggasi soltanto. `$autoReplyAllowed` è già calcolato qui (nessuna soppressione attiva su `from_email` — l'unico modo per cui una soppressione può essere attiva a questo punto della pipeline è un `loop_protection` appena registrato da `ClassifyInboundEmail`/US-304 sullo STESSO messaggio, perché un mittente già soppresso PRIMA avrebbe fatto scartare il messaggio a monte): un futuro listener (US-312, `UnknownSenderStaffMail`/E9 + l'eventuale auto-reply al mittente) deve solo rispettare questo flag, mai ricalcolare i controlli anti-loop da zero.

## Allegati inbound — sniffing MIME, ULID sul path, limiti dedicati (US-309)

- `App\Domain\Mail\Actions\ImportInboundEmailAttachments::run(EmailMessage $emailMessage, TicketMessage $ticketMessage): void` è chiamata da `ApplyInboundEmail` SUBITO DOPO `PostTicketMessage::run(...)` (di cui ora si cattura il valore di ritorno), dentro la stessa `DB::transaction()`: rilegge il `.eml` grezzo (stesso pattern I/O di `ParseInboundEmail`/`ClassifyInboundEmail`), e se `raw_path` è vuoto o il file non esiste ritorna silenziosamente senza importare nulla (mai un'eccezione) — necessario perché molti test di `ApplyInboundEmailTest` costruiscono un `EmailMessage` in-memory senza `.eml` reale su disco.
- **Gotcha verificato empiricamente**: `Webklex\PHPIMAP\Attachment::getSize()` restituisce i byte della parte MIME ANCORA CODIFICATA (tipicamente base64), non i byte decodificati — per la dimensione reale da confrontare con i limiti e da salvare in `email_attachments.size_bytes` usare sempre `strlen($attachment->getContent())`, mai `getSize()`.
- **Gotcha PHPStan**: `Attachment` non ha un metodo `getFilename()` dichiarato nel blocco `@method` della classe (solo `getName()`/`getDisposition()`/etc.), anche se `filename` è un `@property` documentato — chiamare `->getFilename()` passa a runtime (magic `__call`) ma fallisce Larastan (`method.notFound`). Per leggere quell'attributo specifico usare l'accesso a proprietà `->filename` (magic `__get`), non il metodo.
- `Attachment::getMimeType()` fa già lo sniffing reale del contenuto (`(new \finfo())->buffer($content, FILEINFO_MIME_TYPE)`): soddisfa da solo il requisito "MIME reale, non l'header dichiarato" del PRD, nessun bisogno di reimplementare finfo. `getDisposition()` (`inline`/`attachment`) è il campo giusto per il filtro allegati-inline-esclusi-per-default.
- `App\Domain\Mail\Support\EmailAttachmentTypes` legge `config('mail_pipeline.attachments.*')` (mai `config/ticketing.php`): configurazione distinta e più permissiva di `App\Domain\Ticketing\Support\TicketAttachmentTypes` (US-107), stesso identico shape (`maxFileSize()`/`allowedExtensions()`/`allowedMimeTypes()`/`isAllowed()`) più `maxTotalSize()`/`maxCount()`/`includeInline()` specifici del contesto email.
- **Path mai costruito dal nome originale (problema 15 del v1, path traversal)**: il file fisico su disco (via `TicketMessage::addMediaFromString($content)->usingFileName(...)->toMediaCollection('attachments')`, stessa collection/disco `ticket-attachments` degli allegati web US-107) usa sempre un nome generato da `Str::ulid()` + estensione sniffata; il nome originale (sanitizzato con `Str::slug()` sulla sola parte senza estensione) resta solo come metadato (`email_attachments.filename`, `usingName()` su Media, mai come path).
- Ogni allegato è processato nel proprio try/catch indipendente: un tipo non ammesso produce `status=rejected_mime`, una dimensione (per-file, totale-messaggio, o conteggio massimo) fuori soglia produce `status=rejected_size`, un'eccezione qualunque (es. disco di destinazione non configurato) produce `status=failed` con `rejection_reason` — mai uno scarto silenzioso, mai un allegato che blocca gli altri o l'intera applicazione del messaggio. Per un `rejected_*`/`failed` (nessun file scritto), `email_attachments.disk`/`path` sono valorizzati con `TicketAttachmentTypes::disk()`/stringa vuota (colonne NOT NULL nello schema Fase 0, ma nessun file reale esiste per queste righe: `media_id` resta `null`).

## Invio outbound — punto unico di invio, VERP, canale del ticket (US-311, §7.5.1/§7.5.2)

- **`App\Domain\Mail\Actions\SendOutboundTicketMail::run()` è il punto unico di invio per TUTTO il catalogo E1-E9**, non solo per E1/E2: genera Message-ID e Reply-To VERP dallo stesso ULID della riga `email_messages` outbound che crea SEMPRE (anche quando l'invio è bloccato: `status = Suppressed`, mai un salto silenzioso — §7.7), controlla `email_suppressions`/`notification_preferences` PRIMA di accodare, e accoda il Mailable solo se nessuno dei due gate blocca. Ogni Mailable futuro (E3-E9) deve passare da qui, non chiamare `Mail::to()->queue()` direttamente: altrimenti perde l'audit trail e il Reply-To VERP.
- **US-317 ha estratto il controllo `notification_preferences` in `App\Domain\Mail\Support\NotificationGate::allows(User $user, NotificationType $notificationType): bool`**, chiamato da `SendOutboundTicketMail::blockedReason()`: nessuna riga per quella combinazione utente/tipo/`channel='email'` → notifica consentita (default abilitato). Qualunque futuro controllo "l'utente vuole ricevere questo tipo di notifica" deve passare da qui, non ripetere la query.
- **`App\Domain\Mail\Mailables\TicketOutboundMailable` è la base comune per un Mailable legato a un ticket** (`extends Mailable implements ShouldQueue`): tries/backoff/retryUntil, `envelope()`/`headers()` letti dalla riga `email_messages` già decisa da `SendOutboundTicketMail` (mai generati nel Mailable stesso). Una sottoclasse implementa solo `content()`. **US-312 l'ha spezzata**: la parte comune (tries/backoff/envelope/headers, nessun `Ticket`) ora vive in `App\Domain\Mail\Mailables\OutboundMailable`, e `TicketOutboundMailable extends OutboundMailable` aggiunge solo il `Ticket`. Un Mailable senza ticket reale (es. E9, mittente mai identificato) estende `OutboundMailable` direttamente.
- **VERP (§7.3.6, US-306) non richiede più un `ticket_message` reale**: `ResolveEmailThread::byVerp()` risolve un token `ticket+<ulid>@dominio` sia contro `ticket_messages.ulid` sia — fallback aggiunto in questa story — contro `email_messages.ulid` (la riga outbound stessa). Necessario per E2 (ticket aperto dal pannello web, nessun `ticket_message` associato all'apertura): usare SEMPRE l'ulid della riga `email_messages` outbound per il Reply-To di un Mailable, mai tentare di inventare/collegare un `ticket_message` fittizio solo per il threading.
- **Gotcha reale**: `EmailMessage`/`TicketMessage` non hanno `ulid` nel proprio `#[Fillable]` (lo genera `HasUlids::setUniqueIds()` da sé quando manca) — passare `'ulid' => $valore` a `::create()` viene silenziosamente IGNORATO dal mass-assignment guard, e il modello ne genera comunque uno diverso (con lo stesso identico prefisso monotonico ULID, perché generato microsecondi dopo: un bug quasi invisibile a occhio, i due ulid sembrano "quasi uguali"). Quando serve decidere l'ulid in anticipo (per incorporarlo in `message_id`/`reply_to` PRIMA di salvare la riga), usare `EmailMessage::query()->forceCreate([...])`, mai `::create()`.
- **`App\Domain\Ticketing\Events\TicketCreated` porta ora un secondo parametro** `TicketMessageChannel $channel = TicketMessageChannel::Web` (backward-compatible, stesso pattern di estensione già usato per `PostTicketMessage`/US-307): `CreateTicket::run()` lo accetta e lo propaga. `ApplyInboundEmail` (US-307) lo forza a `TicketMessageChannel::Email`. Necessario perché `TicketCreated` è condiviso da ENTRAMBI i percorsi di creazione (Filament `CreateTicket` page per il web, `ApplyInboundEmail` per la pipeline email): senza un modo esplicito di distinguerli sull'evento, un listener non può decidere se inviare E1 o E2 — non basarsi mai sull'ordine/timing con cui un `ticket_message` viene creato dopo l'evento, è un percorso fragile (il canale email crea sempre un primo `ticket_message`, quello web di oggi non ne crea nessuno).
- **`App\Domain\Mail\Enums\NotificationType`**: catalogo dei tipi verificati da `notification_preferences` (`channel` sempre `'email'` in questa fase, nessun altro canale implementato). Aggiungere un case solo quando la comunicazione corrispondente viene davvero implementata (oggi solo `TicketReceivedByEmail`/`TicketOpenedFromWeb`), non in anticipo per tutto il catalogo E1-E9.
- **Non ancora implementato, lasciato esplicitamente per una story futura**: la transizione di stato `Queued → Sent` via i listener Laravel `MessageSending`/`MessageSent` menzionata da §7.5.1 — la riga `email_messages` outbound resta `status = Queued` dopo l'accodamento, non `Sent`. Chi tocca `US-325` (`mail:retry-failed`) o introduce un bisogno reale di distinguere "accodato" da "consegnato" deve aggiungere quel listener (stesso pattern di `App\Support\Mail\BlockRealRecipientsOutsideProduction`), non prima.

## Assegnazione E6, due percorsi di scrittura per assignee_id/tester_id unificati sullo stesso Mailable (US-315, §7.5.2)

- **`assignee_id`/`tester_id` cambiano da DUE Action distinte, non una sola**: `App\Domain\Ticketing\Actions\AssignTicket` (US-110, unico punto per una riassegnazione manuale da `EditTicket`, solo `assignee_id`) e il `$context` di `App\Domain\Ticketing\Actions\ChangeTicketStatus` (una transizione può valorizzare `assignee_id` E/O `tester_id` contestualmente, es. New→Assigned o Progress→Testing). Prima di questa story solo la prima aveva un evento dedicato (`TicketAssigned`, senza attore); la seconda non emetteva nulla di specifico sul cambio di campo. `TicketAssigned` è stato esteso con un 4° parametro `public User $actor` (stesso pattern additivo di `TicketStatusChanged`/US-313, verificato con `grep -rn "TicketAssigned("` prima di toccarlo: nessun chiamante costruiva l'evento con argomenti posizionali fuori da `AssignTicket::run()`), e `ChangeTicketStatus::run()` ora confronta `$context['assignee_id']`/`$context['tester_id']` con `$ticket->getOriginal()`-equivalente catturato PRIMA di `fill($context)`: se il context tocca il campo e il valore è diverso da quello precedente, dispatcha lo STESSO `TicketAssigned` (per l'assegnatario) o il nuovo `TicketTesterAssigned` (per il tester) — un solo evento "l'assegnatario è cambiato" indipendentemente da quale Action l'ha causato, invece di duplicare la semantica per percorso.

- **`SendTicketAssignedMail::run(Ticket $ticket, int $newUserId, bool $asTester, User $actor)` è il punto unico per E6**, richiamato da due listener sottili (`SendTicketAssignedNotification` su `TicketAssigned`, `SendTicketTesterAssignedNotification` su `TicketTesterAssigned`): il guard "mai notificare chi ha eseguito l'azione" è un confronto diretto `$newUserId === $actor->id` (non `Ticket::messageRecipients()`, che restituisce l'INTERO set di destinatari del ticket — sbagliato qui, E6 deve andare SOLO al nuovo assegnatario/tester).
- **Gotcha permessi nei test: `Event::fake()` PRIMA di una seconda `userWithPermissions()` con un permesso DIVERSO nello stesso test rompe la cache di Spatie `laravel-permission`** — il `created` del modello `Permission` che invalida la cache viene anch'esso intercettato da `Event::fake()`, quindi la cache resta quella (stale) calcolata dalla prima chiamata e la seconda permission "non esiste" (`PermissionDoesNotExist`) anche se la riga è stata appena creata nella stessa transazione. Un solo `userWithPermissions()` dopo `Event::fake()` non manifesta il problema (nessuna cache preesistente da invalidare); il fix è creare TUTTI gli utenti/permessi PRIMA di `Event::fake()`, poi fakare solo per l'azione da osservare — schema riusabile per qualunque test futuro che combina permessi multipli e asserzioni su eventi di dominio.

## Reminder E7, working days "trascorsi" vs ore lavorate, comando trigger diretto senza listener (US-316, §7.5.2)

- **`App\Domain\TimeTracking\WorkedTimeCalculator` NON è riusabile per "sono passati N giorni lavorativi senza attività"**: quella classe somma MINUTI lavorati dentro una finestra oraria a partire da intervalli `to_status=progress`/`from_status=progress`, non conta giorni di calendario trascorsi da un istante. Per US-316 è stato creato un secondo helper puro e indipendente, `App\Domain\Ticketing\Support\WorkingDaysCalculator::haveElapsed(CarbonInterface $since, int $workingDays, ?CarbonInterface $asOf = null): bool`, che riusa solo il *principio* (`Carbon::isWeekend()` per escludere sabato/domenica), non la classe. Qualunque story futura che debba contare "giorni lavorativi trascorsi" (non ore lavorate) deve usare/estendere `WorkingDaysCalculator`, mai forzare `WorkedTimeCalculator` a fare un lavoro diverso da quello per cui esiste.
- **Un Mailable il cui trigger è un comando schedulato (non un evento di dominio) non ha bisogno di nessun listener**: `App\Domain\Mail\Actions\SendTicketWaitingReminderMail::run(Ticket $ticket)` è chiamata direttamente da `TicketsRemindWaitingCommand::handle()`, stesso principio "Action dedicata per essere testabile in isolamento" già visto per E6 (`SendTicketAssignedMail`, US-315), ma senza nessun `AppServiceProvider::boot()` da toccare — l'Action esiste per la testabilità della logica di invio, non perché ci sia un evento da ascoltare.
- **Non esiste una colonna dedicata "ultimo promemoria inviato" sul ticket**: la finestra di cooldown di US-316 (AC "un ticket già ricordato di recente non riceve un secondo reminder duplicato") è verificata riusando `email_messages` come registro storico già esistente — `EmailMessage::query()->where('ticket_id', ...)->where('mailable_class', TicketWaitingReminderMail::class)->where('created_at', '>=', now()->subDays($cooldownDays))->exists()`. Pattern riusabile per qualunque futura regola "non rimandare la stessa notifica due volte in una finestra X": interrogare `email_messages.mailable_class` invece di aggiungere una nuova colonna/migrazione.
- **"Ultima attività rilevante" di un ticket = `max()` tra due tabelle diverse, mai una singola colonna**: nessuna colonna `tickets.last_activity_at` esiste. Il calcolo corretto è `max(ticket_logs.occurred_at)` UNION `max(ticket_views.last_viewed_at)` (fallback a `tickets.created_at` se il ticket non ha mai avuto log/visualizzazioni) — `Ticket::logs()->max('occurred_at')`/`Ticket::views()->max('last_viewed_at')` restituiscono stringhe scalari grezze (query di aggregazione, non un attributo Eloquent castato), vanno wrappate in `Carbon::parse()` prima di confrontarle.
- Test che manipolano il tempo per verificare soglie di giorni lavorativi: usare `$this->travelTo('YYYY-MM-DD HH:MM:SS')` (stesso helper già usato da `TicketLifecycleEndToEndTest`/`RecordTicketViewTest`), mai `Carbon::setTestNow()` diretto — datare esplicitamente sia la creazione dei fixture (log/view/ticket) sia l'esecuzione del comando, scegliendo giorni di calendario noti (qui: lunedì 2026-08-10 → giovedì 2026-08-13, verificato "Mar 18 Ago 2026" nel changelog = martedì).

## Bounce/DSN — correlazione via Message-ID, soglia soft bounce (US-319, §7.5.5)

- **`Webklex\PHPIMAP\Part::isAttachment()` tratta `message/delivery-status` e `message/rfc822` come "allegati"** (nessuna API dedicata ai report di consegna nella libreria): un subtype diverso da `plain`/`html` senza `filename`/`name` ricade nel ramo `return true` di default. `App\Domain\Mail\Actions\ProcessDeliveryStatusNotification` itera quindi `Message::getAttachments()` cercando per `getContentType()` (case-insensitive, nessun parametro nel content-type di una `Part`: già isolato da `explode(';', ...)` in `Part::parse()`), non un metodo `getReport()`/simile che non esiste.
- **Il Message-ID dell'email originale non è mai negli header del DSN stesso** (quelli si riferiscono solo alla nuova notifica di mancato recapito): va estratto dal contenuto della parte `message/rfc822` (o `text/rfc822-headers`), con una regex mirata sulla riga `Message-ID:` di quella parte — `Message::fromString()` non è riusabile lì perché quel contenuto non è garantito avere la struttura header+CRLFCRLF+body attesa dalla libreria. Il valore estratto va confrontato con `email_messages.message_id` **senza** `<`/`>` (stesso formato usato ovunque nel modulo, `Header::set('message_id', ...)` di webklex li rimuove già a monte — vedi la sezione VERP/US-306 sopra).
- **Soglia soft bounce implementata SENZA una colonna aggiuntiva**: `email_suppressions.bounce_count` (già esistente da Fase 0) viene incrementato a ogni soft bounce, ma la riga sospende davvero l'invio solo quando `EmailSuppression::scopeActive()` la considera attiva (`expires_at` nullo o futuro). Sotto soglia (`config('mail_pipeline.bounce.soft_bounce_threshold')`) `expires_at` è impostato esplicitamente a `now()` (già "scaduto" per costruzione): la riga esiste e conta, ma non blocca ancora l'invio. Un hard bounce successivo può sempre sospendere permanentemente (`expires_at = null`); un soft bounce arrivato DOPO un hard bounce non deve mai retrocederlo — guardia esplicita in `registerSoftBounce()`.
- **Azione non ancora agganciata a nessuna pipeline**: `ProcessDeliveryStatusNotification::run()` opera su un `EmailMessage` già `status = discarded` / `failure_reason = delivery_status_notification` (scartato da `ClassifyInboundEmail`, US-304), ma nessun comando/Action la richiama ancora — stesso pattern "Action pronta, wiring rimandato al checkpoint" già seguito da `ResolveEmailSender`/`ResolveEmailThread` prima di US-307. Il wiring reale (chiamarla per ogni DSN scartato da `mail:fetch-inbound`) è compito di US-326.

## Tabella destinatari attore×transizione, sostituisce il blanket `messageRecipients()` di E4 (US-318, §7.5.3)

- **La colonna "Effetti" della macchina a stati di §6.1.3 (voce "notifica X") è la fonte di verità dei destinatari**, non un'invenzione della story: `App\Domain\Mail\Support\NotificationRecipientResolver::resolve(Ticket $ticket, TicketStatus $from, TicketStatus $to, User $actor)` riproduce riga per riga SOLO le transizioni che in quella tabella hanno un "notifica X" scritto esplicitamente (`new→rejected`, `progress→testing`, `testing→tested`, `testing→todo`, `testing→rejected`, `{new,backlog,assigned,todo,progress}→waiting`, `{new,backlog,assigned,todo,progress}→problem`, più il catch-all `*→rejected`) — qualunque altra transizione (es. `todo→progress`, `progress→released`, `released→done`) risolve a **nessun destinatario**, per design, non per omissione.
- **Struttura**: una lista ORDINATA di righe `{from: ?list<TicketStatus>, to: TicketStatus, roles: list<NotificationRecipientRole>}` (mai un'espressione booleana `&&`/`||`, causa del bug v1 problema 12), risolta con lo stesso principio di precedenza "prima riga che matcha vince" già usato da `TicketStateMachine::findTransition()` — le righe specifiche (`new→rejected`, `testing→rejected`) vanno elencate PRIMA del catch-all generico (`*→rejected`), altrimenti quest'ultimo le intercetterebbe per prima.
- `NotificationRecipientRole` (enum: `Requester`/`Assignee`/`Tester`/`Manager`) è un ruolo ASTRATTO, mai un `User` diretto: il resolver lo traduce contro il `Ticket` (`requester`/`assignee`/`tester`) o, per `Manager`, contro l'intero pannello (`User::query()->active()->whereHas('roles', ...UserRole::Manager...)->get()`, stesso idiom `whereHas('roles', fn ($q) => $q->where('name', ...))` già usato da `WorkBoard::assigneeOptions()`/`InternalTicketsQuery`, mai lo scope Spatie `role()` che lancia `RoleDoesNotExist` se la tabella `roles` è vuota).
- **L'esclusione "nessuno riceve la notifica di un'azione che ha eseguito lui stesso" vive in un unico punto, alla fine di `resolve()`** (`reject(fn ($u) => $u->is($actor))`), applicata dopo aver risolto tutti i ruoli della riga — mai duplicata per singolo ruolo.
- `App\Domain\Mail\Actions\SendTicketStatusChangedMail` (E4, US-313) ora chiama `NotificationRecipientResolver::resolve()` invece di `Ticket::messageRecipients($actor)`: quest'ultimo metodo resta su `Ticket` (ancora usato da E5, US-314, che notifica correttamente TUTTI i partecipanti di un messaggio pubblico, comportamento diverso e corretto per quel caso) ma non è più la sorgente dei destinatari di un cambio di stato.
- Se una story futura del catalogo E1-E9 diventa "trigger-da-transizione" (nuova comunicazione dichiarata dalla colonna Effetti di §6.1.3), riusare `NotificationRecipientResolver` aggiungendo una riga alla tabella — mai una nuova query/condizione ad hoc nella sua Action.

## Localizzazione reale delle comunicazioni — RecipientLocale, subject tradotto per destinatario, test di completezza (US-320, §7.6)

- **`App\Domain\Mail\Support\RecipientLocale::resolve(User $user): string`** è l'unico punto che decide la lingua di UNA comunicazione: `users.locale` (colonna sempre valorizzata, default `it` da schema — il ramo "vuoto" è raggiungibile solo forzando una stringa vuota, es. nei test), fallback alla prima `organizations.locale` dell'utente (`$user->organizations()->first()?->locale`), poi `config('app.locale')`. Va chiamato per OGNI Mailable del catalogo E1-E9 in due punti distinti dello stesso invio: (1) dentro `SendOutboundTicketMail::run()`, che ora fa `Mail::to($recipient->email)->locale(RecipientLocale::resolve($recipient))->queue(...)` — il meccanismo standard Laravel (`Mailable::$locale` pubblico, applicato da `PendingMail::fill()` prima di `Mailer::queue()`) rende tutte le viste Blade tradotte senza toccare Action/Mailable esistenti; (2) in ogni Action/Listener che COSTRUISCE il subject come stringa PRIMA di chiamare `SendOutboundTicketMail::run()` (il parametro `subject: string` è già risolto quando arriva lì, non lazy) — il subject va quindi generato con `__('chiave', [...], RecipientLocale::resolve($recipient))`, passando esplicitamente il locale come 3° argomento di `__()` invece di affidarsi al locale globale dell'app (che a quel punto è ancora quello della request/comando in corso, non quello del destinatario).
- **Le chiavi di traduzione sono scritte in inglese** (convenzione Laravel per `lang/*.json`: la chiave è anche il fallback quando manca una traduzione), con `lang/it.json` che traduce in italiano e il nuovo `lang/en.json` (creato in questa story, prima non esisteva) che ripete la chiave stessa come valore — ridondante con il comportamento di fallback-alla-chiave di Laravel quando `APP_FALLBACK_LOCALE=en` (già impostato in `.env`), ma richiesto alla lettera dall'AC ("lang/en.json presente e COMPLETO"), verificato da un test dedicato (sotto).
- **Placeholder HTML in una traduzione**: quando il testo tradotto deve contenere markup (es. `<strong>` attorno a un nome di stato o a un indirizzo email), la stringa passata a `__()` resta puro testo con placeholder `:nome`, il VALORE del placeholder porta l'HTML già escapato a mano (`'<strong>'.e($valore).'</strong>'`), e l'output nella vista usa `{!! __(...) !!}` invece di `{{ __(...) }}` — mai interpolare l'HTML dentro la CHIAVE di traduzione stessa (renderebbe la traduzione it/en accoppiata al markup). `Illuminate\Translation\Translator::makeReplacements()` non fa alcun escaping automatico dei valori sostituiti: un valore contenente dati utente (es. l'email del mittente in E9) deve sempre passare da `e()` PRIMA di essere incapsulato in `<strong>`, mai lasciato grezzo.
- **Scope deliberatamente escluso da questa story**: `TicketStatus::getLabel()` (e ogni altro label di enum di dominio già esistente, usato ovunque nell'app, non solo nelle email di questa fase) NON è stato tradotto — tradurlo avrebbe un impatto trasversale su tutto il pannello Filament, ben oltre "le comunicazioni" di §7.6, e non è richiesto dall'AC ("nessuna stringa hard-coded in italiano in nessun Mailable/template **di questa fase**"). Stesso principio per le notifiche in-app Filament (`StaffDatabaseNotification::send()`, titoli hard-coded 'Nuovo ticket cliente'/'Mittente sconosciuto', US-312): sono notifiche interne allo staff nel pannello admin, non un Mailable/template email.
- **Test di completezza vero (non una lista statica)**: `tests/Feature/Domain/Mail/LocalizationCompletenessTest.php` scansiona `app/Domain/Mail`, `resources/views/emails`, `resources/views/components/emails` con una regex (`/\b(?:__|trans)\(\s*'((?:[^'\\]|\\.)*)'/`) che estrae OGNI chiave passata a `__()`/`trans()` in quei file, poi verifica che esista con un valore non vuoto in ENTRAMBI `lang/it.json` e `lang/en.json` — aggiungere una nuova chiave di traduzione in una story futura senza aggiornare uno dei due file fa fallire questo test automaticamente, senza doverlo aggiornare a mano ogni volta (a differenza di un elenco di chiavi scritto a mano nel test stesso, che richiederebbe manutenzione parallela).

## Registro email — prima Filament Resource di Fase 3, campo array in un componente Filament, bug pre-esistente scoperto (US-321, §7.7)

- **`App\Filament\Resources\EmailMessages\EmailMessageResource`** (index/view soltanto, nessuna create/edit) è la prima UI Filament di questa fase — riusa ALLA LETTERA le due convenzioni già stabilite in Fase 0/1 (`RoleResource`/`UserResource`, US-021/US-110): `EmailMessage` ha una Policy propria (`App\Domain\Mail\Policies\EmailMessagePolicy`, `Permission::EmailView`/`EmailManage`) risolta automaticamente da Laravel via convenzione di naming, quindi la Resource NON sovrascrive nessun metodo `can*` (Convention A, come `UserResource`) — a differenza di `RoleResource`, che gestisce un modello Spatie senza Policy propria e deve quindi negare `canCreate`/`canEdit`/`canDelete` a mano (Convention B). La sola lettura è garantita registrando in `getPages()` esclusivamente `index`/`view`, mai dai metodi `can*`.

Il fix è sempre `->state(fn (EmailMessage $record): string => implode(', ', $record->to ?? []))` (assegna lo stato dell'intera colonna esplicitamente, bypassando l'iterazione automatica) invece di `->formatStateUsing()`, riusabile per qualunque futura colonna/entry Filament su un attributo castato array che va mostrato come stringa singola.
- **`to`/`cc`/`bcc` sono `array<int, string>` di soli indirizzi email**, mai coppie `{email, name}` (verificato su `RawInboundEmail::$to` e `SendOutboundTicketMail`, `'to' => [$recipient->email]`): un filtro "destinatario" può quindi usare `whereJsonContains('to', $email)` con un confronto esatto sulla stringa, portabile sia su Postgres (dev/CI) sia su sqlite (grammar Laravel astrae `json_each` per sqlite automaticamente) — mai una `LIKE`/cast testuale Postgres-only (`::text ILIKE`) su queste colonne: la suite Pest gira su sqlite in-memory (`phpunit.xml`), non su Postgres.
- **Bug pre-esistente scoperto in questa story, NON del sottosistema email, da correggere in una story dedicata**: `AdminPanelProvider::panel()` chiama `->databaseNotifications()` (attivato da US-312 per E3/E9) ma la migrazione `2026_08_18_090000_create_notifications_table` (committata in US-312) non era MAI stata eseguita sul database Postgres di sviluppo persistente prima di questa story — nessuno aveva ancora navigato il pannello reale dopo quella migrazione. Una volta eseguita (`php artisan migrate`, azione sicura e additiva, fatta qui), il pannello resta comunque rotto su OGNI pagina autenticata: la query del badge di notifiche di Filament usa l'operatore JSON `->>'format'` su `notifications.data`, ma quella colonna è dichiarata `text` (non `json`/`jsonb`) nella migrazione — Postgres risponde `SQLSTATE[42883]: operator does not exist: text ->> unknown`. Verificato disabilitando temporaneamente `->databaseNotifications()` (poi ripristinato, nessuna modifica committata a `AdminPanelProvider.php` da questa story) solo per completare la verifica in browser di US-321. **Da correggere in una story dedicata** (probabilmente un fix mirato nel prossimo checkpoint US-326, o una story a parte prima che una vera notifica E3/E9 in-app raggiunga il pannello in produzione): cambiare la colonna `data` in `json`/`jsonb` con una nuova migrazione (mai modificare la migrazione già committata di US-312), oppure verificare se una versione più recente della migration-stub standard Laravel usa già `json`. **Stesso identico bug ri-verificato empiricamente in US-322**: qualunque pagina/azione Filament autenticata rimane rotta su Postgres reale finché non si ripete lo stesso workaround temporaneo per la verifica in browser — non è stato ancora corretto.

## Amministrazione email — azioni e quarantena, gotcha ResolveEmailSender, mailable non ricostruibili (US-322, §7.3.8/§7.7)

- **`App\Domain\Mail\Actions\ApplyInboundEmail` ha ora DUE punti di ingresso**: `run()` (pipeline automatica, invariato) e il nuovo `runForResolvedSender(EmailMessage $emailMessage, User $user)`. ## Pagina Soppressioni/metriche — getHeaderWidgets() su una Page custom, gotcha canAccess()/Livewire::test(), bounce rate senza Sent (US-323, §7.5.5/§7.7)

- `App\Filament\Pages\EmailSuppressions` combina lo stesso pattern "tabella senza Resource" di `EmailQuarantine` (US-322) con un widget di metriche in testa: `protected function getHeaderWidgets(): array { return [EmailPipelineMetricsOverview::class]; }` è un metodo NATIVO di `Filament\Pages\Page` (`vendor/filament/filament/src/Pages/Page.php`), indipendente da `content()` — il wrapper `<x-filament-panels::page>` renderizza ENTRAMBI (header widgets + content), quindi una pagina "solo tabella" può avere widget in testa senza toccare `content()`. Il widget stesso è un normale `Filament\Widgets\StatsOverviewWidget` con un proprio `canView()` statico (gate `email.view`), scoperto e discoverabile via `->discoverWidgets(in: app_path('Filament/Widgets'), ...)` già configurato in `AdminPanelProvider` — nessuna registrazione manuale necessaria.
- **Gotcha importante per qualunque test Livewire su una custom `Filament\Pages\Page` (non una Resource)**: `Filament\Pages\Concerns\CanAuthorizeAccess::mount()` chiama `abort_unless(static::canAccess(), 403)` — a differenza di quanto sembra leggendo solo `Page.php` (dove `canAccess()` appare usato solo per la visibilità in navigazione), il mount REALE della pagina lo applica sempre. Un `Livewire::test(CustomPage::class)` con un utente per cui `canAccess()` è `false` fallisce con una risposta 403, e qualunque `->callTableAction()`/`->callAction()` successivo esplode con un fuorviante `Attempt to read property "mountedActions" on null` (l'istanza Livewire non esiste). Per una pagina come `EmailSuppressions` il cui `canAccess()` richiede solo `email.view` ma un'azione di riga richiede `email.manage` separatamente, un test che vuole invocare quell'azione deve comunque concedere ENTRAMBI i permessi all'utente di test — `EmailQuarantine` non aveva mai reso visibile questo comportamento perché il suo `canAccess()` usa lo stesso, unico permesso (`email.manage`) di tutte le sue azioni.
- **Bounce rate mai calcolato su `EmailStatus::Sent`**: nessun listener di questa fase transita mai un outbound da `queued` a `sent` (nota lasciata in US-311). `EmailPipelineMetrics::bounceRate()` usa quindi `bounced / (bounced + queued)` come proxy di "tentativi di invio", mai `sent` — qualunque metrica futura sullo stato di un invio outbound deve ricordare che `sent` in questo schema non è mai popolato finché non arriva la story dedicata (menzionata come gap aperto in US-311).

## Voce di menu Mailpit, gotcha interpolazione `.env`, visibilità di navigazione testabile senza montare l'intero pannello (US-324, §7.7)

- **`phpdotenv` (usato da Laravel per `.env`/`.env.example`) NON supporta la sintassi bash `${VAR:-default}`**: il resolver (`Dotenv\Loader\Resolver::resolveVariable()`) matcha solo la regex `\A\${([a-zA-Z0-9_.]+)}` — nessun `:-`, nessun default. Il PRD di questa story chiedeva letteralmente `MAILPIT_URL=http://localhost:${MAILPIT_UI_PORT:-8025}`; verificato empiricamente con `env('MAILPIT_URL')` in tinker che la stringa resta LETTERALE (`${MAILPIT_UI_PORT:-8025}` non risolto), mentre `MAIL_FROM_NAME="${APP_NAME}"` (già in uso, solo `${VAR}` senza default) si risolve correttamente. La forma corretta, usata sia in `.env.example` sia in `.env.uat.example`, è `${MAILPIT_UI_PORT}` senza fallback — valido solo perché quella variabile è già definita PRIMA nello stesso file. Qualunque futura variabile che voglia comporre un URL/path da un'altra variabile `.env` deve verificare che quest'ultima sia sempre valorizzata a monte, mai affidarsi a un default bash-style che phpdotenv non applicherà.
- **Regole di visibilità di un `Filament\Navigation\NavigationItem` estratte in una classe pura testabile** (`App\Filament\Navigation\MailpitNavigationItem::isVisible()`/`::url()`, usata sia dal `->visible()`/`->url()` closure in `AdminPanelProvider` sia dai test): testare la visibilità condizionale iterando `Filament::getNavigation()` (l'array unito/filtrato/ordinato di TUTTE le Resource/Page del pannello) richiederebbe un utente con permessi sufficienti per ogni singola Resource esistente, altrimenti `canViewAny()`/gate falliti su risorse non correlate rompono il test — fragile e destinato a rompersi ad ogni nuova Resource futura. ## Colonna custom con markup HTML in una tabella Filament (barra SAL, US-403) — `ViewColumn`, non `TextColumn->html()`, e rebuild CSS obbligatorio

- **`TextColumn::make(...)->html()->formatStateUsing(fn () => new HtmlString(...))` NON è il pattern giusto per un layout non banale** (es. una barra di progresso con più `<div>` annidati): Filament avvolge lo stato di un `TextColumn` in `<div class="fi-ta-text fi-ta-text-item ...">`, che applica troncamento/line-clamp pensato per testo — dei `<div>` a blocco annidati dentro quel wrapper vengono compressi/non visibili (verificato via screenshot Playwright: solo il testo del `<span>` finale restava visibile, la barra colorata no). Per markup HTML non banale usare `Filament\Tables\Columns\ViewColumn::make('nome')->view('filament.tables.columns.mia-vista')`: la vista Blade dedicata riceve `$record` (il model Eloquent della riga) direttamente come variabile, senza il wrapper di troncamento testo — vedi `app/Filament/Resources/Tags/Tables/TagsTable.php` (colonna `sal`) e `resources/views/filament/tables/columns/tag-sal-bar.blade.php`. `->getStateUsing()` resta comunque utile su una `ViewColumn` solo per rendere lo stato ispezionabile da `assertTableColumnStateSet()` nei test, il rendering vero e proprio lo fa la vista leggendo `$record`.

Sintomo osservato: l'HTML renderizzato era corretto (`grep` sull'output confermava il markup atteso), ma lo screenshot Playwright non mostrava alcun elemento visivo — nessun errore, nessun log, il browser semplicemente non aveva le regole CSS per quelle classi. Dopo aver aggiunto/modificato markup con classi Tailwind non ancora usate altrove nel repo, eseguire `npm run build` PRIMA di uno screenshot di verifica, altrimenti il verdetto visivo è falso negativo. `public/build/` non è tracciato da git (verificato `git status`), quindi la rebuild non sporca il commit.

## Model con visibilità per categoria/ruolo — `scopeVisibleTo()` + Policy che delega (`DocumentationPage`, US-404)

- **Pattern canonico per "un record non è raggiungibile via URL diretto da chi non ha il permesso"**: un `scope<Nome>(Builder $query, User $user): Builder` sul model (es. `DocumentationPage::scopeVisibleTo()`, già usato da `TicketMessage`/`Ticket`), e la Policy `view()` delega a quello scope invece di ripetere la logica sul model già caricato: `Model::query()->whereKey($model->getKey())->visibleTo($user)->exists()`. Un solo punto di verità, riusabile sia per il controllo puntuale (Policy) sia per filtrare un elenco (query su `Model::query()->visibleTo($user)`, utile per la futura Resource Filament di US-405 e per qualunque comando/report che debba iterare solo sui record visibili).
- **Attenzione a non trattare due permessi "categoria" come una gerarchia se non lo sono esplicitamente**: `documentation.view.customer` e `documentation.view.internal` sono due gate indipendenti (§9.4) — avere `.view.internal` NON implica vedere anche le pagine `category=customer`. Nella pratica tutti i ruoli con `.view.internal` (staff, fundraising) hanno anche `.view.customer` via `RolePermissionSeeder`, quindi il bug sarebbe invisibile nei test end-to-end per ruolo ma rotto in un test isolato con un solo permesso — prima di scrivere `scopeVisibleTo()`/`Policy::view()` per un nuovo model a categorie multiple, verificare nel PRD/matrice se i gate sono davvero gerarchici o indipendenti, non assumerlo.
- **Media collection su un model con visibilità ristretta (internal/customer) va sempre su un disco privato dedicato**, mai sul disco `public` di default di medialibrary: un allegato "internal" su disco pubblico è raggiungibile via URL diretto indipendentemente da qualunque Policy. Pattern: nuovo disco in `config/filesystems.php` (`root` sotto `storage_path('app/private/...')`, `serve` a `false`), richiamato con `->useDisk('nome-disco')` in `registerMediaCollections()` — vedi `documentation-attachments`, stessa motivazione già documentata per `ticket-attachments`.

## Auto-tag da evento di dominio, ricerca full-text, form con upload di media (`DocumentationPageResource`, US-405)

- **La cartella di una Filament Resource sotto `app/Filament/Resources/` deve corrispondere allo slug/plurale della Resource, non al namespace del dominio sottostante**: creare `app/Filament/Resources/Documentation/DocumentationPageResource.php` (cartella singolare, presa dal namespace `App\Domain\Documentation`) produce un URL annidato e sbagliato (`admin/documentation/documentation-pages`, verificato con `php artisan route:list`) invece di `admin/documentation-pages`. Il fix è rinominare la cartella per farla coincidere con il plurale del model/risorsa (`DocumentationPages`, come già fanno `Tags`, `Tickets`, `Users`, `EmailMessages`) — dopo un rename di namespace ricordarsi anche `docker compose exec app php artisan route:clear` se si sta verificando nel container.
- **Un `hasMany`/`belongsTo` con FK esplicita su un lato deve avere la stessa FK esplicita anche sul lato inverso**: `Tag::documentationPage()` dichiarava `belongsTo(DocumentationPage::class, 'documentation_id')`, ma `DocumentationPage::tags()` (pre-stubbato da una fase precedente) era un `hasMany(Tag::class)` senza secondo argomento — Eloquent deduce quindi la convenzione `documentation_page_id` (dal nome corto del model), colonna che non esiste. Bug latente, mai esercitato dai test di visibilità di US-404 (che non chiamavano `->tags()`): esploso alla prima query reale in US-405. Quando si aggiunge la seconda metà di una relazione già esistente, verificare sempre la FK effettiva in migrazione, non fidarsi della convenzione di naming Eloquent quando l'altro lato della stessa relazione l'ha già resa esplicita.
- **La "ricerca full-text" di questo repo (già usata per `tickets.title`) è, all'atto pratico, un `TextColumn::make(...)->searchable()` Filament standard (LIKE/ILIKE)**: l'indice GIN Postgres `to_tsvector(...)` che accompagna la colonna in migrazione è un'ottimizzazione lato DB mai interrogata da query applicativa con `@@`/`plainto_tsquery`. Per cercare su più colonne (es. `title` e `body`) basta marcare `->searchable()` su entrambe le `TextColumn` — Filament le combina in OR sulla stessa query di ricerca. Se una colonna cercabile non deve essere visibile di default (es. `body`, HTML lungo), usare `->toggleable(isToggledHiddenByDefault: true)`, MAI `->hidden()`: una colonna `->hidden()` è esclusa dalla definizione della tabella e quindi anche dalla ricerca, non solo dal rendering.
- **Un evento di dominio innescato da un cambio-di-campo specifico (qui: rinomina di `title`) va emesso SOLO quando il valore è davvero cambiato**, confrontando `$model->title` prima/dopo il `fill()+save()` dentro l'Action — mai su ogni update, altrimenti il listener a valle (qui: rinomina del Tag collegato) scatterebbe anche per un salvataggio che non tocca quel campo.
- **Pattern per "un Model A crea/rinomina un Model B collegato" senza hook Eloquent**: Action di dominio (`CreateDocumentationPage`/`UpdateDocumentationPage`) che fa `DB::transaction` + `event(new XxxEvent($model))`, listener in un modulo di dominio diverso da quello dell'evento se è il modulo del *risultato* a possederne la logica (qui i listener che creano/rinominano `Tag` vivono in `App\Domain\Tags\Listeners`, non in `App\Domain\Documentation\Listeners`, perché sono i `Tag` ad avere le regole di slug/nome), e registrazione manuale in `AppServiceProvider::boot()` (nessuna auto-discovery per `App\Domain\*\Listeners`, pattern già consolidato in Fase 3 per i listener di `Mail`/`Ticketing`).
- **Un `Filament\Forms\Components\FileUpload::make('nome')->storeFiles(false)` in un form che NON è un attributo Eloquent del model** (qui `documents`/`images`, salvati su media collection Spatie) va rimosso esplicitamente da `$data` prima di passarlo all'Action di creazione/aggiornamento (altrimenti finisce nel `fill()`/`create()` e Eloquent lo ignora silenziosamente solo se non è `Fillable` — non contarci, va tolto a mano), poi processato a parte con `$record->addMedia($file)->toMediaCollection('nome')` nella pagina Filament (`handleRecordCreation()`/`handleRecordUpdate()`), stesso idioma già usato da `AddTicketAttachment` (US-107). Se sia `CreateXxx` sia `EditXxx` devono ripetere questa logica, estrarla in un trait condiviso (qui `AttachesDocumentationMedia`) invece di duplicarla.
- **Verifica in browser (Playwright) di un submit Filament che redirige dopo il salvataggio**: non fidarsi di `page.click(...)` seguito subito da `page.url()` — il redirect post-`create()`/`save()` non è istantaneo rispetto a `waitForLoadState('networkidle')` e lo script può leggere l'URL vecchio (rischio concreto: eseguire il click una seconda volta e creare un record duplicato, come successo in verifica). Usare `page.waitForURL(url => ...)` con una condizione esplicita sul cambio di path (es. `!url.pathname.endsWith('/create')`) prima di procedere.

## Generazione PDF con `spatie/laravel-pdf` — driver `chrome` invece di `browsershot`, job+Action, evento separato dal Tag (US-406, §6.4.3)

- **`spatie/laravel-pdf` (v2) supporta più driver intercambiabili via `config('laravel-pdf.driver')`**: `browsershot` (il default del pacchetto, richiede Node.js+Puppeteer) e `chrome` (`chrome-php/chrome`, Chrome DevTools Protocol in puro PHP) sono i due basati su Chromium. Questo repo usa `chrome`: nessun secondo runtime Node.js da mantenere a runtime nelle immagini Docker (Node esiste già, ma solo come stage di build scartato per gli asset Vite, `docker/uat/Dockerfile`). Motivazione completa in `README.md`, sezione "Generazione PDF" (richiesta esplicita §6.4.3 del PRD).
- **Il binario Chromium va installato con `apk add chromium` in entrambe le immagini** (`docker/php/Dockerfile` sviluppo, `docker/uat/Dockerfile` stage finale) — `apk` risolve da solo tutte le librerie condivise necessarie (nss, freetype, harfbuzz, ...), nessun pacchetto da elencare a mano. `LARAVEL_PDF_CHROME_BINARY` va lasciato vuoto in `.env.example`: la classe `HeadlessChromium\AutoDiscover` di `chrome-php` cerca da sola `google-chrome`/`chromium-browser`/`chrome`/`chromium` nel `PATH` su Linux e il path standard di `Google Chrome.app` su macOS — un percorso hardcoded romperebbe uno dei due ambienti. `LARAVEL_PDF_CHROME_NO_SANDBOX=true` è invece necessario in QUALSIASI container — **non solo quelli che girano come root**: verificato di persona che il container `app` di sviluppo (`docker/php/Dockerfile:50`, `USER www-data`) fallisce comunque con `RuntimeException: Chrome process stopped before startup completed... Failed to move to new namespace... Operation not permitted` senza questo flag, perché il sandbox di Chrome richiede di creare user/PID namespace e il runtime container nega di norma quella syscall a prescindere dall'utente. (Il container `uat`/`FrankenPHP` gira invece davvero come root, nessun `USER` nel Dockerfile — ma non è quello il motivo del flag.) Nella suite CI (`ubuntu-latest`, `.github/workflows/ci.yml`) serve comunque un passo esplicito `browser-actions/setup-chrome@v1`, non fidarsi che l'immagine del runner abbia già Chrome installato.
- **Un `.env` di sviluppo già esistente (container non ricreato da zero) NON eredita automaticamente le nuove variabili aggiunte a `.env.example`**: dopo aver aggiunto `LARAVEL_PDF_*`/`PDF_*`, un ambiente dev provisionato prima di questa story genera comunque l'errore sandbox sopra finché qualcuno non le aggiunge a mano al `.env` reale. Inoltre `php artisan config:clear` NON basta a far ripartire il job in coda con le variabili nuove se il worker (qui Horizon, processo long-running) le ha già lette una volta all'avvio: serve `docker compose restart queue` (o l'equivalente riavvio del processo Horizon/worker) dopo aver modificato `.env`, non solo pulire la cache di config.
- **Header/footer del PDF vanno incorporati nell'HTML del contenuto, non passati come `headerHtml()`/`footerHtml()` di Chrome**: il template header/footer nativo di Chrome (`Page.printToPDF`, CSS molto limitato, niente font custom, niente immagini se non già base64) è pensato per numerazione pagina/data, non per un vero blocco di brand. Il logo (da `PDF_LOGO_PATH`, un percorso file system, mai un URL: il job gira in coda e non deve dipendere dalla raggiungibilità HTTP dell'app verso se stessa) va letto ed embeddato come data URI base64 nel `<body>` della vista, stesso principio del logo nel layout email ma senza dipendenza di rete.
- **Pattern Action+Job+comando, tre chiamanti un solo punto di generazione**: `GenerateDocumentationPagePdf::run($page)` (Action, mai duplicata la chiamata a `Pdf::view(...)->save(...)`) è chiamata sia dal `GenerateDocumentationPagePdfJob` (ShouldQueue, dispatchato da un listener su creazione/modifica) sia dal comando `documentation:regenerate-pdfs` — stesso principio "singolo entry point" già in uso per `CreateDocumentationPage`/`UpdateDocumentationPage`.
- **Un evento "il contenuto è cambiato" per innescare un side-effect NON deve essere confuso con un evento più specifico già esistente per un side-effect diverso**: `DocumentationPageRenamed` (solo `title`, consumato dal listener che rinomina il Tag collegato) e il nuovo `DocumentationPageContentChanged` (`title` O `body`, consumato dal listener che rigenera il PDF) restano due eventi distinti emessi dallo stesso `UpdateDocumentationPage::run()` — un cambio del solo `body` deve rigenerare il PDF ma non deve rinominare il Tag. Riallargare la semantica di un evento esistente invece di aggiungerne uno nuovo avrebbe accoppiato due side-effect che devono poter variare indipendentemente.

## Primo Filament `RelationManager` del repo — autorizzazione ad ogni hydrate sul model correlato, non solo sulla Resource (`OrganizationResource`, US-407)

- **Un `RelationManager` (es. `UsersRelationManager` su `users()` di `OrganizationResource`) ri-autorizza `viewAny` sul MODEL CORRELATO (qui `User`, via `UserPolicy`) ad OGNI hydrate Livewire, non solo alla prima mount**: anche se l'utente ha già `organization.update`/`organization.view` (sufficienti a raggiungere la pagina Edit della Resource proprietaria), il RelationManager stesso resta bloccato con un 403 silenzioso in fase di hydrate se manca il permesso di `viewAny` sul model relazionato (`user.view`/`UserPolicy::viewAny()`) — `RelationManager::hydrateCanAuthorizeAccess()` chiama `canViewForRecord()`, che fa `authorize('viewAny', $relatedModelClass)`. Sintomo in test: non un'eccezione di dominio leggibile ma `ErrorException: Attempt to read property "mountedActions" on null` dentro l'helper di test `TestsActions::callAction()` — il vero errore (`HttpException` 403) va scoperto avvolgendo la chiamata in `$this->withoutExceptionHandling()` e ispezionando lo status code, non fidandosi del messaggio di errore superficiale. Quando si aggiunge un nuovo RelationManager, elencare esplicitamente TUTTI i permessi coinvolti (proprietario + correlato) sia nei test sia nella documentazione utente, non solo il permesso della Resource ospitante.
- **`AttachAction`/`DetachAction`/`DetachBulkAction`/`AssociateAction`/`DissociateAction` di un RelationManager controllano SOLO `RelationManager::isReadOnly()`** (che dipende dalla pagina — `false` per una pagina Edit, potenzialmente `true` su una pagina View se il panel ha `hasReadOnlyRelationManagersOnResourceViewPagesByDefault()`), non un metodo di Policy dedicato tipo `attach()`/`detach()`: la sicurezza reale del "chi può aggiungere/rimuovere un membro" è quindi delegata interamente a **quali pagine espongono il RelationManager** (qui: solo Edit, raggiungibile solo con `organization.update`, cioè solo admin per §9.4) — nessun `RelationManagerPolicy` separato da scrivere.
- **Test di un'azione header (`AttachAction`) o di record (`DetachAction`) su un RelationManager**: usare `Livewire::test(NomeRelationManager::class, ['ownerRecord' => $model, 'pageClass' => EditXxx::class])->callTableAction('attach', data: ['recordId' => $id])` / `->callTableAction('detach', record: $relatedRecord)` — **non** `->callAction(...)` (quello è per azioni di pagina, non di tabella: fallisce con lo stesso errore fuorviante "mountedActions on null" perché l'azione non viene trovata nel contesto giusto). Il campo dati dell'`AttachAction` è sempre `recordId` (anche per attach singolo).
- **Nei test, disaccoppiare i test che NON riguardano il side-effect in coda con `Queue::fake()`**: con `QUEUE_CONNECTION=sync` in `phpunit.xml`, ogni `CreateDocumentationPage::run()`/`UpdateDocumentationPage::run()` innesca per davvero il job di generazione PDF (Chromium reale) a meno che la coda non sia fake — `DocumentationPageAutoTagTest`/`DocumentationPageResourceTest` (che riguardano il Tag/la Resource, non il PDF) usano `Queue::fake()` in un `beforeEach` proprio per questo, mentre `DocumentationPagePdfTest` lo lascia deliberatamente reale per verificare un PDF non vuoto (`substr($contents, 0, 4) === '%PDF'`) — non è questo il posto per `Pdf::fake()` del pacchetto, che eviterebbe la generazione reale invece di verificarla.

## PDF report attività — locale per record, filename vs percorso su disco, bugfix di scoping su una Policy `.view.own` pre-stubbata (`ActivityReport`, US-409, §6.5.3)

- **`LogoDataUri::resolve()` (`App\Support\Pdf\LogoDataUri`) è ora l'unico punto che incorpora un logo come data URI**, estratto dal metodo privato duplicato in `GenerateDocumentationPagePdf` (US-406) quando `GenerateActivityReportPdf` (US-409) ha avuto bisogno esattamente della stessa logica: qualunque terzo PDF generato in coda in una fase futura deve riusare questa classe, non riscrivere il mimetype-sniffing da capo.
- **Un PDF generato in coda con contenuto per-record in una lingua diversa (qui `activity_reports.locale`, già derivato in US-408) richiede `App::setLocale($report->locale)` esplicito prima del render e il ripristino nel `finally`**: a differenza di un Mailable (dove `Mail::to(...)->locale(...)` gestisce da solo lo switch temporaneo), `Pdf::view(...)->save(...)` renderizza una vista Blade con l'`App::getLocale()` corrente del processo — un job in coda che processa report di owner con locale diversi in sequenza (stesso worker, stesso processo PHP long-running) lascerebbe l'ultimo locale "vincente" su tutti i job successivi senza il ripristino esplicito. Le stringhe statiche della vista PDF passano da `__()` (chiavi in `lang/it.json`/`lang/en.json`, stesso pattern del layout email §7.6/US-320) — gli accessor già locale-aware del model (es. `periodLabel()`, che applica `->locale($this->locale)` a Carbon direttamente) non hanno invece bisogno di questo wrapping, perché non dipendono dall'app locale globale.
- **Il nome del file scaricato (`ActivityReport::pdfDownloadFilename()`, da `PLATFORM_ACRONYM`+owner+periodo) è deliberatamente un concetto diverso dal percorso su disco (`pdf_path`, sempre `activity-reports/{id}.pdf`)**: stesso principio già stabilito in US-406 per `DocumentationPage` (slug per il download, id per il path), qui esplicitato perché l'AC lo richiede per la prima volta come requisito indipendente (nome-file basato su owner/periodo, non solo un identificatore stabile).
- **`ActivityReportPolicy::view()` pre-stubbato da uno stage precedente era un bug da correggere, non solo da estendere**: `viewAny()`/`view()` collassavano `.view.any` e `.view.own` nella stessa condizione (`canAny([...])`), quindi un customer con solo `.view.own` poteva vedere/scaricare il report di **qualunque** owner, non solo il proprio — mai esercitato da un test prima (nessun test montava due owner diversi). Corretto delegando a un nuovo `ActivityReport::isOwnedBy(User $user): bool` (utente owner diretto, o organizzazione owner di cui l'utente è membro via `$user->organizations()`) — quando in futuro si aggiunge un secondo permesso "own" in questa fase (fundraising? altri owner "on behalf of"?), verificare sempre con un test esplicito a due owner diversi che ".own" non stia implicitamente autorizzando anche "any", non solo che il caso positivo funzioni.
- **Pulizia del PDF su cancellazione del record (`static::deleting()` in `booted()`) è un hook Eloquent accettabile qui**, a differenza del divieto esplicito di hook impliciti per side-effect di dominio (Tag da evento, US-405/US-406): la cancellazione del file è una pulizia tecnica di risorsa (stesso principio di spatie/medialibrary che cancella da sé i propri file al delete del model), non una regola di business con effetti su un altro dominio — non introdurre un evento/listener dedicato solo per questo.

## Comando schedulato che scopre i propri owner + `scopeVisibleTo()` query-equivalente di un check per-record (`reports:generate-monthly`, US-410, §6.5.2/§9.4)

- **Un comando §10.1 che deve "scoprire" i propri destinatari (qui: owner attivi) non ha bisogno di una nuova relazione Eloquent inversa solo per quello**: `User` non ha (e non serve che abbia) un `tickets()`/`ticketsAsRequester()` — la query parte sempre da `Ticket::whereBetween('done_at', [...])->pluck('requester_id')->unique()` e poi filtra `User`/`Organization` con `whereIn('id', ...)`/`whereHas('users', fn ($q) => $q->whereIn('users.id', ...))`. Aggiungere una relazione solo per un comando di scoperta owner è un'astrazione prematura finché nient'altro nel dominio ne ha bisogno.
- **Un'Action "singolo entry point" che già rifiuta i duplicati con un'eccezione (`CreateActivityReport::run()`, US-408) non basta da sola per un comando batch idempotente con `--dry-run`**: il comando deve comunque ripetere lo stesso controllo `exists()` (owner+periodo, stesso pattern `when($valore !== null, where, whereNull)` di US-408) PRIMA di chiamare l'Action, per due motivi — (1) in `--dry-run` non si può invocare l'Action (scriverebbe se non fosse dry-run) solo per scoprire se esiste già; (2) usare l'eccezione come unico segnale di "già esistente" per un batch di N owner renderebbe il conteggio "saltati" indistinguibile da un vero errore nel log strutturato. Il `try/catch` sull'Action resta comunque presente per la vera race condition (owner concorrente tra il check e la creazione), ma non è la via primaria per l'idempotenza attesa dal test.
- **`ActivityReport::scopeVisibleTo(Builder $query, User $user)` è il query-equivalente di `isOwnedBy()` (US-409)**, stesso principio già documentato sopra per `DocumentationPage`/`Ticket`: un check per-record (`Policy::view()`) e un filtro di lista (Resource Filament `getEloquentQuery()`) non devono mai duplicare la logica di ownership in due posti — se in futuro cambia la definizione di "owner" (es. un'organizzazione può avere un owner secondario), aggiornare solo lo scope e verificare che `isOwnedBy()` non sia rimasta un'implementazione parallela ormai disallineata.
- **Un'unica Resource Filament in un unico pannello Filament (nessun pannello cliente separato in questo repo, §9.1) può restare "sola lettura" semplicemente non registrando pagine create/edit/delete in `getPages()`**, senza dover azzerare `can*()` come fa `RoleResource` (quello non ha Policy propria): `ActivityReportResource` è Policy-backed come `TicketResource`/`DocumentationPageResource`, il fatto che non esista una pagina "create" la rende sola lettura di per sé, a prescindere da cosa dice `ActivityReportPolicy::create()` (mai invocata perché non c'è un'azione UI che la triggeri).

## Chrome/ext-sockets — 3 gotcha distinti scoperti solo al primo merge/deploy reale di Fase 4 (US-406, §6.4.3)

I test locali/CI di US-406 (PDF via `spatie/laravel-pdf`, driver `chrome-php/chrome`) passavano tutti prima del
merge della PR di Fase 4 (PR #9): questi 3 problemi sono emersi **solo** al primo giro reale di CI su GitHub-hosted
runner e al primo deploy UAT reale, mai prima — nessuno dei due ambienti era mai stato esercitato end-to-end con
questa nuova dipendenza prima di allora. Pattern generale per qualunque futura dipendenza di sistema aggiunta a
`composer.json`/Docker: "i test passano in dev" non è prova che CI e l'immagine di produzione la vedano — vanno
verificati esplicitamente, non assunti allineati.

  `google-chrome`/`chromium-browser`/`chrome`/`chromium` nel `PATH`, e questo funziona nelle immagini Docker

- **`ext-sockets` mancante sia in `docker/php/Dockerfile` (dev) sia in `docker/uat/Dockerfile` (UAT/produzione)**:
  `chrome-php/wrench` (dipendenza di `chrome-php/chrome`, parla col protocollo DevTools via websocket) la

  Il job CI "Build Docker containers" (`docker compose build app`, usa `docker/php/Dockerfile`) l'ha intercettato

  `docker-php-ext-install` su un'immagine Alpine va verificata per bisogni di `-dev`/`-headers` aggiuntivi, non

## Griglia reattiva (Placeholder + `Get`) e permesso distinto per un'azione dentro una Resource già autorizzata (`FundraisingOpportunityResource`, US-504)

- **Un `Placeholder::make(...)->content(function (Get $get) {...})` SI aggiorna da solo quando un altro campo
  dello stesso schema ha `->live()`**, senza bisogno di marcare il Placeholder stesso: ogni richiesta Livewire
  innescata da un campo `->live()` ri-renderizza l'intero schema e rivaluta tutte le closure `content()`/`visible()`
  con lo stato corrente. Nessun `wire:poll`/computed property extra necessario per un totale calcolato in tempo
  reale da altri campi del form (pattern generico, non specifico a Fundraising).
- **Gotcha di verifica Playwright su un campo `->live()` senza `onBlur: true`**: il default (`wire:model.live` su
  evento `input`, nessun debounce esplicito) parte comunque con un piccolo ritardo lato Livewire. Uno script che fa
  `fill()` + `blur()` + `waitForLoadState('networkidle')` può leggere `networkidle` PRIMA che la richiesta
  Livewire sia partita (nessuna richiesta ancora in volo = "idle" falso positivo) e screenshottare lo stato vecchio
  — successo scoperto verificando US-504, il Placeholder sembrava "non reattivo" ma era solo un problema dello
  script di verifica, non del codice. Serve un `waitForTimeout(...)` esplicito (800–1200ms) DOPO il cambio,
  PRIMA di `waitForLoadState('networkidle')`, ogni volta che si verifica in browser un campo `->live()` di
  Filament senza `onBlur: true`.
- **`Tabs`/`Tab` di `Filament\Schemas\Components\Tabs` sono puro layout**: non alterano lo state path dei campi
  annidati, quindi avvolgere un form Filament esistente in `Tabs::make(...)->tabs([...])` non richiede toccare
  i test esistenti che usano `fillForm(['campo' => ...])` con i nomi originali.
- **Un tab/azione dentro una Resource già gated da un permesso "generico" (qui `fundraising.update`, che apre la
  pagina Edit) può richiedere un permesso PIÙ specifico per una singola sotto-funzionalità** (qui
  `fundraising.evaluate`, distinto e già esistente nel catalogo `Permission`/nella `Policy::evaluate()` da
  scaffolding precedente, semplicemente mai consumato finché non è arrivata la story che lo richiedeva) —
  `->visible(fn () => Auth::user()?->can(Permission::X))` sul tab/campo interessato basta come UI gating: Filament
  esclude i componenti non visibili anche dalla dehydration di `getState()` durante il save, quindi lo stato di un
  tab nascosto non arriva mai al metodo che salva. Un controllo esplicito lato server (`abort_unless($user->can(...), 403)`
  nel punto in cui i dati di quel tab vengono effettivamente persistiti) resta comunque la difesa autorevole — non
  fidarsi della sola visibilità come unico confine di sicurezza, anche se in pratica risulta irraggiungibile dal
  flusso normale di Livewire. Verificare sempre prima nel catalogo `Permission`/nelle `Policy` esistenti se un
  permesso più specifico di quello che gestisce l'intera Resource è già stato predisposto da una fase precedente,
  prima di riusare quello generico per una sotto-funzionalità che meriterebbe il proprio controllo.

## `view.involved` per-record vs per-modulo, e query "coinvolti" su relazioni multiple (`FundraisingProject`, US-506)

- **`fundraising.view.involved` non ha lo stesso significato su tutti i model del dominio**: su `FundraisingOpportunity`

  può delegare a `viewAny()` come `FundraisingOpportunityPolicy::view()` fa — verificare sempre nel PRD se
  "coinvolto" è definito a livello di modulo o di singolo record prima di riusare lo stesso pattern tra due Policy
  dello stesso dominio che sembrano simili.
- **Pattern "coinvolti" (OR su più colonne + una pivot)**: `FundraisingProject::scopeInvolving(Builder $query, User $user)`
  combina `where('lead_user_id', ...)->orWhere('responsible_user_id', ...)->orWhere('created_by', ...)->orWhereHas('partners', ...)`
  dentro un unico `where(function ...)` innestato, cosi resta sicuro anche se incatenato dopo altri `where()` (stesso
  idioma di `Ticket::scopeVisibleTo()`). Riusabile in US-507 (filtro "coinvolti" sull'elenco progetti) e US-508
  (vista cliente) chiamando `FundraisingProject::query()->involving($user)` invece di riscrivere la condizione.
- **Fix del bug v1 `partnerCustomers()`**: v1 filtrava i partner con ruolo customer con `whereHas('roles', ...)` su
  una colonna JSON (query non eseguibile). In v2 i ruoli sono la pivot Spatie `model_has_roles`, esposta dalla
  relazione `roles()` di `HasRoles` sul model `User` — un `whereHas('roles', fn ($q) => $q->where('name', UserRole::Customer->value))`
  incatenato su una `BelongsToMany` esistente (qui `partners()`) funziona senza bisogno di join manuali.
- **Macchina a stati "leggera"**: `FundraisingProjectStateMachine` replica solo la parte tabellare/dichiarativa di
  `TicketStateMachine` (`transitions()`/`canTransitionTo()`/`authorize()` che lancia `ValidationException`), SENZA

  un'autorizzazione differenziata per attore sulla stessa transizione (a differenza dei ticket, dove assignee/tester/
  admin hanno diritti diversi sullo stesso stato) — l'autorizzazione resta quella uniforme della Policy
  (`fundraising.update`). Non aggiungere la macchina completa "per coerenza" se l'AC non la richiede.

## Filtri "capofila/partner/coinvolti" su una Resource, secondo RelationManager, select cross-dominio ristretta per Policy (`FundraisingProjectResource`, US-507)

- **`SelectFilter::make(...)->relationship('nomeRelazione', 'colonnaTitolo')` funziona sia su una `BelongsTo`
  (qui `lead_user_id` → `leadUser`) sia su una `BelongsToMany` (qui `partner` → `partners()`)**: in test,
  `filterTable('lead_user_id', $id)` / `filterTable('partner', $id)` impostano entrambi `['value' => $id]`
  (vedi `vendor/filament/tables/src/Testing/TestsFilters.php`), Filament costruisce da sé la `whereHas`
  giusta in base al tipo di relazione — nessuna differenza nel codice del test tra i due casi.
- **Filtro booleano "coinvolti" con `Filter::make(...)->toggle()->query(...)`**: in test si usa
  `filterTable('nome', true)` (imposta `isActive => true`), MAI `filterTable('nome', ['value' => ...])`
  come per un `SelectFilter`/`TernaryFilter` — sono tre meccanismi di stato diversi nello stesso helper
  (`value` per `SelectFilter`, `value` anche per `TernaryFilter` ma con default `true` se omesso, `isActive`
  per un `Filter` generico). La query di un `Filter::make()` riusa direttamente lo scope del model
  (`->query(fn (Builder $query) => $query->involving(Auth::user()))`), mai una condizione OR riscritta qui.
- **`Livewire::test(NomeRelationManager::class, [...])->callTableAction('attach', data: [...])` (il pattern
  documentato sopra per `UsersRelationManager`, US-407) NON funziona più in modo affidabile in questo ambiente**:
  fallisce con `"mountedActions.0.data.recordId": "The record field is required"` anche passando `recordId`
  esplicito — stesso sintomo, root cause diversa, della voce sotto su `fillForm()`. Workaround verificato:
  `mountTableAction('attach')` → `->set('mountedActions.0.data.recordId', $id)` → `callMountedTableAction()`
  → `assertHasNoTableActionErrors()`. Aggiornare qualunque test futuro su `AttachAction`/azioni con `data`
  a questo pattern, non al vecchio `callTableAction(..., data: [...])`.
- **`fillForm()` nei test Livewire NON applica più correttamente lo stato in questo ambiente, su QUALUNQUE
  form Filament del repo, non solo Fundraising**: verificato isolando la causa a `Filament\Schemas\Concerns\InteractsWithSchemas::fillFormDataForTesting()`
  (il metodo interno che `fillForm()` chiama per iniettare i dati nei test) — un `->set('data.<campo>', valore)`
  esplicito applica invece lo stato correttamente e permette comunque di eseguire `->call('create')`/`->call('save')`
  con dati reali. Confermato con `git stash` che il problema è preesistente al lavoro di Fase 5 (già presente
  su `TicketResourceTest.php` a HEAD prima di questa story, 7 test su 16 già rotti, mai investigato prima

## Vista cliente in sola lettura come Resource Filament separata dalla Resource staff (`CustomerFundraisingOpportunityResource`/`CustomerFundraisingProjectResource`, US-508)

- **Pattern riusabile "stessa entità, due Resource Filament distinte, staff CRUD vs cliente sola lettura"**:
  quando un dominio ha sia una Resource di gestione staff (`FundraisingOpportunityResource`/
  `FundraisingProjectResource`) sia una vista cliente con permessi/scope diversi (§6.6.4), NON provare a far
  convivere i due casi d'uso in un'unica Resource con `visible()` condizionali sui campi/azioni — creare una
  seconda Resource dedicata (`Customer<Nome>Resource`), stesso model, `getPages()` che registra SOLO
  `'index'`/`'view'` (mai `'create'`/`'edit'`/`'delete'`: sola lettura reale, non azioni nascoste in UI),
  `table()`/`infolist()` con solo i campi previsti per il cliente (mai responsabile/creatore/dati di
  valutazione interni), `headerActions([])`/`toolbarActions([])` sulla tabella, un solo `ViewAction::make()`
  come `recordActions()`. Le pagine List/View di sola lettura non hanno bisogno di override di
  `getHeaderActions()` per `ViewRecord` (default già vuoto, nessuna `EditAction` a meno di aggiungerla
  esplicitamente come fa `ViewUser`), ma serve per `ListRecords` (default include una `CreateAction`
  condizionata da `canCreate()`: meglio azzerarla esplicitamente per chiarezza, pattern già usato da
  `ListActivityReports`).
- **Evitare due voci di navigazione duplicate per lo stesso dominio quando entrambe le Resource condividono
  lo stesso `Policy::viewAny()` permissivo**: `FundraisingOpportunityPolicy`/`FundraisingProjectPolicy::viewAny()`
  ritornano true sia per chi ha `fundraising.view.any` (staff) sia per chi ha solo `fundraising.view.involved`
  (cliente, US-501/US-506), quindi nessuna delle due Resource può delegare `canViewAny()` al default
  Filament→Policy. La Resource staff resta ristretta a `->can(FundraisingViewAny)` (già da US-502/US-507); la
  Resource cliente usa il gate simmetrico e opposto `->can(FundraisingViewInvolved) && ! ->can(FundraisingViewAny)`
  — nella matrice ruoli attuale (§9.4, `RolePermissionSeeder::ROLE_PERMISSIONS`) l'unico ruolo con
  `view.involved` ma senza `view.any` è `customer`, quindi ogni altro ruolo vede al massimo una delle due
  Resource, mai zero e mai due.
- **Due scope diversi sullo stesso model per due significati diversi di "coinvolto", NON un unico scope
  riusato ovunque**: `FundraisingProject::scopeInvolving()` (US-506, uso interno staff/filtro §6.6.3) include
  capofila, partner, responsabile E creatore — semanticamente corretto per un membro dello staff che vuole
  "i progetti su cui sto lavorando in qualunque ruolo". La vista cliente (§6.6.4) è esplicitamente più
  stretta: SOLO capofila o partner, responsabile/creatore sono ruoli interni allo staff e non devono mai far
  apparire un progetto nella lista di un cliente. Riscrivere `scopeInvolving()` per escluderli avrebbe rotto
  i test di Policy già committati in US-506 (`FundraisingProjectPolicyTest`, che asserisce esplicitamente che
  un customer impostato come `responsible_user_id`/`created_by` PUÒ vedere il progetto via `Policy::view()` —
  ability generica, mai raggiunta in pratica da staff perché short-circuita prima su `FundraisingViewAny`).
  Soluzione: un secondo scope dedicato `scopeInvolvingAsCustomer()` (solo `lead_user_id`/`partners`), usato
  ESCLUSIVAMENTE da `CustomerFundraisingProjectResource::getEloquentQuery()` — mai dalla Policy generica, che
  resta quella dello staff. Se compaiono due AC che descrivono "coinvolgimento" con perimetri diversi sullo
  stesso model, non assumere che debbano condividere lo stesso scope solo perché il nome è simile.
- **Difesa a due livelli per "il dettaglio non è raggiungibile via URL diretto se non coinvolto" (stesso
  principio di `DocumentationPageResource`/`ActivityReportResource`)**: `getEloquentQuery()` incatena SEMPRE
  lo scope di visibilità PRIMA che Filament risolva il route-model-binding di `ViewRecord` — un record fuori
  scope dà **404** (`ModelNotFoundException`), non 403, perché la richiesta non arriva mai fino al controllo
  Policy. Il test HTTP corrispondente deve quindi asserire `assertNotFound()`, non `assertForbidden()`, per un
  record esistente ma fuori dallo scope del cliente corrente (diverso dal caso "nessun permesso sul modulo
  intero", quello sì `assertForbidden()` su `canViewAny()` a livello di indice/Resource).

## Gruppo di navigazione condiviso staff/cliente — `getNavigationGroup()` dinamico, non `$navigationGroup` statico (US-602, §8.4)

- **Quando una Resource è visibile sia allo staff sia al customer** (`TicketResource`, `ActivityReportResource`,
  `DocumentationPageResource` — tutte policy-backed su permessi che *entrambi* i tipi di utente possono avere,
  es. `TicketViewOwn`/`ActivityReportViewOwn` per customer e `TicketViewAny`/`ActivityReportViewAny` per
  staff), il gruppo di navigazione **non può essere la proprietà statica** `protected static
  UnitEnum|string|null $navigationGroup`: quella è condivisa da TUTTI gli utenti, staff compreso. Va
  sovrascritto `public static function getNavigationGroup(): string|UnitEnum|null` (firma esatta di
  `Filament\Resources\Resource`/`Filament\Pages\Page`) che ramifica su
  `Auth::user()?->hasRole(UserRole::Customer->value)` — stesso idioma già in uso in
  `CustomerDashboard::canAccess()` — restituendo `'Area cliente'` per un customer, il gruppo originale
  altrimenti. Per una Resource **esclusivamente** customer (`canViewAny()`/`canAccess()` già vero SOLO per
  quel ruolo, es. `CustomerFundraisingProjectResource`/`CustomerFundraisingOpportunityResource`,
  `CustomerDashboard`) la proprietà statica resta corretta e più semplice: non serve il metodo dinamico se
  nessun altro ruolo vedrà mai quella voce.
- **Ogni voce di navigazione registrata globalmente in `AdminPanelProvider` va riverificata contro un login
  reale da customer**, non solo le Resource toccate dalla story: la voce "Mailpit" (`->navigationItems()`,
  US-324) era gated SOLO su `app()->environment(['local','staging'])` + URL configurato, **nessun controllo
  di ruolo** — quindi visibile anche a un customer in locale/staging, violando silenziosamente l'AC "nessuna
  voce dei gruppi staff visibile a un cliente". Scoperto SOLO nello screenshot di verifica browser richiesto
  dalla story (mai dai test, che non toccavano quella classe): `MailpitNavigationItem::isVisible()` ora nega
  esplicitamente se l'utente corrente ha il ruolo customer, PRIMA del check su ambiente/URL. Lezione
  generale: la verifica in browser di una story di navigazione deve controllare l'INTERA sidebar per il
  ruolo target, non solo le voci esplicitamente elencate nell'AC — un item pre-esistente e apparentemente
  non correlato può violare la stessa regola.
- La pagina `App\Filament\Pages\Dashboard` (root `/`, landing per ruolo) va tenuta fuori da qualunque voce di
  navigazione (`protected static bool $shouldRegisterNavigation = false;`) da quando OGNI ruolo autenticato
  viene reindirizzato altrove nel suo `mount()` (dopo US-602 anche customer e fundraising, prima di allora
  solo staff): altrimenti resta una voce "Dashboard" cliccabile che si limita a rimbalzare l'utente altrove,
  duplicando la voce "Dashboard" reale (`CustomerDashboard`) per un customer.

## Badge di navigazione combinato con cache — `getNavigationBadge()` su una Resource singola (`TicketResource`, US-604, §8.4)

- `TicketResource` è l'UNICA voce di menu per i ticket (US-110, AC #1: "nessuna sottoclasse per filtro" —
  ogni vista per stato è una tab di `ListTickets`, mai una Resource/Page dedicata). Un requisito che chiede
  un badge "per voce di menu" su più stati (qui: in attesa/problema/da testare) non può tradursi in tre
  `getNavigationBadge()` distinti, perché non esistono tre voci — la soluzione è UN SOLO badge con il
  conteggio combinato (somma) più `getNavigationBadgeColor()`/`getNavigationBadgeTooltip()` per comunicare
  il dettaglio per categoria (colore = categoria più urgente presente, tooltip = riga con i tre conteggi).
  Riusare questo stesso schema per qualunque futuro badge "per stato" su una Resource a viste-come-tab.
- I conteggi riusano direttamente i query object esistenti (`WaitingQuery`/`ProblemTicketsQuery`/
  `ToTestByMeQuery` in `App\Domain\Ticketing\Queries`, già scoped per Policy/`tester_id`) — mai una nuova
  query duplicata solo per il badge.
- Cache: UNA sola chiamata `Cache::remember()` per tutti e tre i conteggi insieme (array associativo),
  chiave scoped per utente (`ticket-navigation-badge-counts:{user_id}`), TTL da
  `config('ticketing.navigation_badges.cache_ttl_seconds')` (env `TICKET_NAVIGATION_BADGE_TTL`). I tre
  metodi `getNavigationBadge*()` chiamano lo stesso helper privato: nessuna query duplicata anche se
  Filament invoca badge/colore/tooltip separatamente nello stesso render.
- Gotcha PHPStan: un metodo static **privato** chiamato con `static::` (non `self::`) dentro la stessa
  classe genera `staticClassAccess.privateMethod` ("Unsafe call to private method ... through static.") —
  usare sempre `self::` per chiamate a metodi privati statici, `static::` è per late static binding su
  metodi che possono essere sovrascritti (non il caso di un helper privato).
- Il tooltip è reso da Filament via Alpine (`x-tooltip="{content: '...'}"`, no attributo HTML `title`): per
  verificarlo in browser leggere l'`innerHTML` del nodo badge, uno screenshot statico senza hover reale non
  lo mostra.

## MFA nativa Filament per ruolo — timing di `isRequired`, e una view di login custom che ignorava il challenge (US-606, §6.7.2)

- `Panel::multiFactorAuthentication([...], isRequired: ...)`: il parametro `isRequired` (bool|Closure) è
  valutato in `routes/web.php` (vendor) alla REGISTRAZIONE delle route — cioè al boot della richiesta,
  PRIMA che la sessione/il guard `Auth::user()` siano disponibili (la sessione parte dentro la pipeline di
  middleware 'web', che gira dopo il boot dei provider). Una closure che tenta di leggere il ruolo
  dell'utente autenticato lì (`fn () => Auth::user()?->hasRole(...)`) vede sempre `null` e non funziona MAI
  per un controllo per-ruolo — né in produzione né nei test (in test, la `config()` impostata dentro il
  corpo del test arriva dopo che `setUp()` ha già ri-registrato le route per quella richiesta). La soluzione
  adottata: `isRequired: true` sempre (così la route "set-up-required" e il middleware esistono sempre per
  ogni richiesta), e tutta la logica per-ruolo spostata in un middleware custom
  (`App\Filament\Auth\Middleware\EnsureRoleRequiresMultiFactorAuthentication`, sostituisce
  `multiFactorAuthenticationRequiredMiddlewareName()`) che legge `config('mfa.required_roles')` e
  `Filament::auth()->user()` A RUNTIME (dentro `handle()`, quando la sessione è reale) e delega al
  middleware nativo `EnsureMultiFactorAuthenticationIsEnabled` solo se il ruolo dell'utente è nella lista —
  altrimenti lascia passare. Con `mfa.required_roles` vuoto di default (nessun env impostato), ogni
  richiesta esistente resta invariata: zero regressioni sui test HTTP già esistenti con utenti `admin`.
- **Gotcha scoperto SOLO in verifica browser (i test Pest con `actingAs()` non lo intercettano, perché
  bypassano interamente `Filament\Auth\Pages\Login::authenticate()`)**: questo repo sostituisce l'intera
  view della pagina di login (`App\Filament\Auth\Pages\Login::$view = 'filament.auth.login'`, per il brand
  "Montagna Servizi", da un ciclo precedente a questa MFA) con un blade scritto a mano che renderizza `<form
  wire:submit="authenticate">` con i soli campi email/password — MAI attraverso il meccanismo
  `content(Schema $schema)` nativo di Filament, che è quello che normalmente mostra/nasconde condizionalmente
  il secondo step (`multiFactorChallengeForm`) in base alla proprietà Livewire
  `$userUndertakingMultiFactorAuthentication`. Risultato: abilitare la MFA sul pannello NON bastava, un
  utente con la MFA configurata restava bloccato per sempre sulla schermata email/password (il server
  segnava correttamente lo stato "sfida in corso" ma la view non lo rifletteva mai). Fix: nella stessa view,
  `@if ($this->userUndertakingMultiFactorAuthentication)` renderizza `{{ $this->multiFactorChallengeForm }}`
  (la `Schema` di Filament implementa `Htmlable`, si stampa con `{{ }}` senza altro wiring) dentro un secondo
  `<form wire:submit="authenticate">`, altrimenti il form originale. Ogni futura modifica a una pagina di
  auth Filament con view completamente custom in questo repo deve verificare se sta bypassando un
  meccanismo nativo condizionale (MFA, verifica email, ecc.) allo stesso modo.
- Contratti Filament per l'autenticazione da app (`Filament\Auth\MultiFactor\App\Contracts\
  HasAppAuthentication`/`HasAppAuthenticationRecovery`) implementati su `User` con cast `encrypted`/
  `encrypted:array` sulle due nuove colonne (`app_authentication_secret`,
  `app_authentication_recovery_codes`) — mai in chiaro a riposo, stesso principio delle altre colonne
  sensibili del progetto.
- `->profile()` (default `Filament\Auth\Pages\EditProfile`, mai creato prima in questo repo) è
  l'UNICO punto in cui Filament espone la UI di gestione/setup della MFA (`getManagementSchemaComponents()`
  per provider, via `content()`): abilitare la MFA senza abilitare anche `->profile()` lascerebbe la
  configurazione teoricamente attiva ma senza alcuna schermata reale da cui un utente possa impostarla.
- Verifica in browser end-to-end di un flusso MFA reale (setup + login con sfida) richiede di calcolare un
  OTP valido per il secret generato: `docker exec <container> php artisan tinker --execute="echo
  app(PragmaRX\Google2FAQRCode\Google2FA::class)->getCurrentOtp('<secret>');"` — riusabile per qualunque
  verifica futura che tocchi l'autenticazione da app.

## Impersonation — guardia `Impersonation::isImpersonating()` in `UserPolicy::viewAny()`, effetto collaterale noto (US-607, §6.7.2)

- `stechstudio/filament-impersonate` richiede, per il proprio bug noto (documentato nel README del
  pacchetto, sezione "Potential Issues and Workarounds — 403 when a ListUsers widget has
  `InteractsWithPageTable`"), un guard esplicito in cima a `UserPolicy::viewAny()`:
  `if (Impersonation::isImpersonating()) { return true; }`. Senza questo guard, il redirect
  post-impersonation genera un 403 spurio perché i componenti Livewire della tabella tentano un
  re-render con l'utente appena impersonato prima che il browser navighi via.
- **Effetto collaterale accettato consapevolmente, non un bug di questa story**: finché
  un'impersonation è attiva, QUALUNQUE utente impersonato (anche un customer) può navigare
  direttamente a `/admin/users` e vedere l'elenco completo di tutti gli utenti reali — perché il guard
  è cieco rispetto a CHI è impersonato, controlla solo "è in corso un'impersonation nella sessione".
  Verificato in browser: un customer impersonato da un admin raggiunge `/admin/users` e vede anche
  l'email dell'admin che lo sta impersonando. Non è uno sfruttamento praticabile da un attaccante reale
  (la sessione è comunque guidata dall'admin che ha già il permesso `UserImpersonate` ed è quindi già
  un utente privilegiato), ma rompe la premessa "vedere il pannello con gli occhi dell'altro utente" per
  questa specifica Resource. Rimuovere il guard reintroduce il 403 spurio documentato dal pacchetto —
  nessuna soluzione pulita nota che eviti entrambi i problemi con l'API pubblica del pacchetto. Flaggato
  per revisione esplicita col committente al checkpoint US-618, non silenziato.
- Metodi di contratto del pacchetto (`User::canImpersonate()`/`canBeImpersonated()`, rilevati via
  `method_exists()`, nessuna interfaccia da implementare): `canImpersonate()` delega a
  `Gate::forUser($this)->check('impersonate', $this)` (unica fonte di verità in
  `UserPolicy::impersonate()`, mai un controllo di ruolo duplicato); `canBeImpersonated()` esprime solo
  il vincolo indipendente dall'attore (`deactivated_at === null`).
- Log strutturato tramite gli eventi nativi del pacchetto (`STS\FilamentImpersonate\Events\
  EnterImpersonation`/`LeaveImpersonation`), NON un observer/hook Eloquent: due nuovi listener
  (`App\Domain\Identity\Listeners\LogImpersonationStarted`/`LogImpersonationStopped`) registrati in
  `AppServiceProvider::boot()`, stesso pattern `Log::info('dominio.azione.evento', [...])` già in uso
  dai comandi schedulati — nessuna nuova tabella dedicata (l'impersonation non è legata a un ticket).
  `LeaveImpersonation::$impersonated` è nullable nell'evento del pacchetto (sessione ripulita da un
  guard esterno, es. logout): gestito come opzionale nel log, mai un accesso diretto che esploda.
- Test dell'intero ciclo (impersona → banner → log → esci) NON affidabile con `Log::spy()->
  shouldHaveReceived(...)->once()` quando lo stesso metodo viene invocato più volte nello stesso test
  (le expectation successive sul metodo `info` contano le invocazioni cumulate, non solo quelle che
  combaciano con la propria closure) — catturare invece la cronologia reale con `Log::listen(function
  ($event) use (&$logs) { $logs[] = [...]; })` e asserire sull'array raccolto.

## Disattivazione utente — un solo choke point per la soppressione email, `recordSelectOptionsQuery` per i picker M:N (US-608, §6.7.5)

- Azione "Disattiva"/"Riattiva" unica (mai due Action separate) estratta in
  `App\Filament\Resources\Users\Support\DeactivateUserAction::make()`, riusata sia dalla riga di
  `UsersTable` sia dall'header di `ViewUser` (stesso idioma di `TicketTransitionActions`/`Impersonate`).
  Autorizzazione delegata interamente a `UserPolicy::deactivate()` (`Permission::UserDeactivate`, unica
  fonte di verità, nessun controllo di ruolo duplicato nell'Action). Valorizza/azzera `deactivated_at`
  con un assegnamento diretto di proprietà + `save()`, mai `fill()`/`update()`: la colonna non è nel
  `#[Fillable]` del model *di proposito* (non deve essere editabile dal form utente), quindi un
  mass-assignment verrebbe scartato silenziosamente senza errore.
- **La soppressione delle comunicazioni per un utente disattivato va aggiunta in UN SOLO punto**:
  `SendOutboundTicketMail::blockedReason()`. È l'unico punto di invio dell'intero catalogo E1-E11
  (documentato nella classe stessa), quindi un controllo `if ($recipient->deactivated_at !== null)`
  lì copre automaticamente ogni Mailable futuro, senza dover filtrare a monte ogni possibile fonte del
  destinatario (`NotificationRecipientResolver::usersForRole()` risolve `Requester`/`Assignee`/`Tester`
  direttamente dalle relazioni del ticket, SENZA `->active()` — e va bene così: filtrare lì sarebbe
  ridondante e più fragile di un controllo unico a valle, prima dell'invio vero e proprio).
- **Verificare ogni picker "utente" prima di dare per scontato che escluda i disattivati**: `Select` su
  relazioni dirette (`belongsTo`, es. `assignee_id`/`tester_id` di `TicketForm`) si scopano con
  `->relationship('assignee', 'name', modifyQueryUsing: self::activeUsersQuery(...))`; un `AttachAction`
  su relazione `belongsToMany` (es. `PartnersRelationManager`, partner ↔ progetto fundraising) è un
  meccanismo DIVERSO e va scopato con `->recordSelectOptionsQuery(fn (Builder $query) => $query
  ->active())` — nessuno dei due copre l'altro caso, un audit di "tutti i picker utente pertinenti"
  deve controllare quale dei due meccanismi usa ciascuna Resource/RelationManager. Effetto lato server
  gratuito: `AttachAction` ri-applica la stessa query scopata nel proprio `action()` per ri-risolvere il
  record dal `recordId` inviato — un id di un utente disattivato non viene trovato, quindi non viene
  mai allegato, anche in un'ipotetica richiesta malformata che aggirasse la UI.
- Gotcha PHPStan: `Builder $query` (non generico) non porta il tipo del model collegato, quindi
  `$query->active()` (local scope di `User`) risulta "metodo indefinito" — va estratto in un metodo
  privato tipizzato `@param Builder<User> $query` / `@return Builder<User>` (mai una closure inline),
  stesso pattern già in uso da `TicketForm::activeUsersQuery()`.

## Comandi schedulati T3/T4 — `TransitionActor::System` spesso già pre-wired in `TicketStateMachine` (`tickets:progress-to-todo`/`tickets:auto-close-released`, US-610, §6.1.5/§10.2)

- **Prima di aggiungere un attore a una riga della tabella dichiarativa, verificare se è già lì**: la riga
  `progress → todo` (T3) aveva già `TransitionActor::System` fra gli attori ammessi fin da US-106 (aggiunto
  per un motivo estraneo a questa story), quindi `tickets:progress-to-todo` non ha richiesto alcuna
  modifica alla macchina a stati — solo il comando artisan che delega a `ChangeTicketStatus` con
  `User::system()`. La riga `released → done` (T4) invece NON l'aveva: aggiunta qui
  (`TicketStateMachine::transitions()`), unica modifica allo stato machine per questa story. Non fidarsi
  del commento di classe che elenca "righe non ancora esistenti": può essere rimasto indietro rispetto al
  codice reale, controllare sempre `transitions()` riga per riga.
- Pattern comando ormai consolidato per queste automazioni (stesso schema di `mail:retry-failed`/
  `reports:generate-monthly`): `User::system()` come attore, delega totale a `ChangeTicketStatus::run()`
  (mai un update diretto su `status`/`done_at`/`previous_status` — gli `effects` della transizione e
  `writeStatusLog()` con `is_system = $user->isSystem()` arrivano gratis), `--dry-run` che non chiama mai
  l'Action, log strutturato `started`/`item_failed`/`finished`, idempotenza per costruzione (la query
  `where('status', ...)` non seleziona più un ticket già transitato alla ri-esecuzione, nessun flag
  "già processato" da gestire a mano).
- I feature flag (`config('orchestrator.features.tickets_progress_to_todo')`/
  `tickets_auto_close_released`) e le relative env var erano già scaffoldati in `config/orchestrator.php`/
  `.env.example` da Fase 0: nessuna nuova voce lì, solo la cadenza cron (nuova sezione
  `config('ticketing.progress_to_todo'/'auto_close_released')`, stesso env pattern
  `*_SCHEDULE_CRON` di `reports.php`) e la soglia giorni lavorativi per T4 (riuso diretto di
  `WorkingDaysCalculator::haveElapsed()`, stesso calcolo del reminder E7/US-316, mai una nuova
  implementazione del conteggio giorni lavorativi).

## Digest periodico E8 — Mailable multi-ticket senza `Ticket` singolo, query "utenti per ruolo" senza `RoleDoesNotExist` (`mail:send-digest`, US-614, §7.5.2/§10.2)

- Un Mailable che riepiloga PIÙ ticket dello stesso destinatario (non uno solo) estende
  `OutboundMailable` direttamente, non `TicketOutboundMailable` — stesso schema già usato da E9
  (`UnknownSenderStaffMail`, "nessun Ticket associato"), qui applicato per un motivo diverso ("più
  ticket", non "nessun ticket"). `SendOutboundTicketMail::run()` accetta comunque `ticket: null`
  (parametro nullable da US-312): la riga `email_messages` outbound del digest ha `ticket_id = null`.
  Contenuto aggregato per ticket incapsulato in un piccolo DTO immutabile dedicato
  (`App\Domain\Mail\Support\TicketDigestEntry`: ticket + conteggio nuovi messaggi + eventuale
  cambio di stato), non un array associativo libero — stesso principio di leggibilità già seguito
  altrove nel dominio Mail.
- **Query "tutti gli utenti con un dato ruolo" (qui: i clienti) non deve mai usare lo scope `role()`
  di Spatie** (`User::role(UserRole::Customer->value)`): quello scope risolve il ruolo con
  `findByName()` e lancia `RoleDoesNotExist` se la riga `roles` non esiste ancora nel DB (es. suite di
  test senza `RolePermissionSeeder`, o ambiente reale senza mai un cliente registrato) — un comando
  schedulato non deve mai poter fallire per questo. Usare invece
  `User::query()->whereHas('roles', fn ($q) => $q->where('name', UserRole::Customer->value))`, che
  produce semplicemente zero righe quando il ruolo non esiste. Stesso idioma già documentato da
  `App\Domain\Ticketing\Queries\AllCustomerTicketsQuery` per un motivo identico — prima di scrivere
  `::role(...)` in un nuovo comando, controllare se esiste già un precedente `whereHas('roles', ...)`
  da riusare.
- Idempotenza "un digest al giorno per cliente" verificata con lo stesso pattern già in uso per il
  cooldown di `tickets:remind-waiting` (E7): `EmailMessage::where('user_id', $customer->id)
  ->where('mailable_class', MailDigestMail::class)->where('created_at', '>=', $todayStart)->exists()`,
  PRIMA di costruire il contenuto del digest (evita lavoro inutile se il cliente ha già ricevuto un
  digest oggi). Distinto dalla finestra di contenuto "24h scorrevoli" (`now()->subHours(24)`, usata per
  decidere COSA includere): l'idempotenza guarda il giorno di calendario (`today()`), il contenuto
  guarda le ultime 24h assolute — le due finestre non vanno confuse né unificate.
- Soppressioni/preferenze di notifica (E8 disabilitabile da US-605) NON richiedono nessun controllo
  aggiuntivo nel comando: restano un'unica responsabilità di `SendOutboundTicketMail::blockedReason()`
  (già verificato da `NotificationGate` + `deactivated_at` + `EmailSuppression`), stesso principio "un
  solo punto di invio per l'intero catalogo E1-E11" già documentato per US-608.

## Report attività pronto E10 — evento su "prima valorizzazione" di una colonna, Mailable verso tutti i membri di un'organizzazione (`ActivityReportPdfGenerated`, US-615, §7.5.2)

- Un evento di dominio che deve scattare SOLO la prima volta che una colonna viene valorizzata (qui
  `ActivityReport.pdf_generated_at`, mai per una rigenerazione successiva dello stesso PDF) si cattura
  leggendo lo stato PRIMA della mutazione: `$isFirstGeneration = $report->pdf_generated_at === null;`
  subito prima di `$report->update([...])`, poi `if ($isFirstGeneration) { event(...); }` dopo — non
  `wasChanged()`/`getOriginal()` dopo l'update, che richiederebbero capire se l'update passa da un hook
  Eloquent o da una chiamata diretta. L'evento arriva "gratis" su entrambi i percorsi che generano il PDF
  (rigenerazione manuale e job schedulato da `reports:generate-monthly`, US-410) perché entrambi passano
  dall'unico punto `GenerateActivityReportPdf::run()` — nessuna duplicazione del dispatch nei due chiamanti.
- Un Mailable che deve raggiungere TUTTI i membri di un'organizzazione owner (non un singolo utente,
  `ActivityReportOwnerKind::Organization`) non ha bisogno di nessuna nuova infrastruttura di invio
  multiplo: iterare `$report->ownerOrganization->users` (stessa relazione `BelongsToMany` già usata da
  `ActivityReport::isOwnedBy()`) e chiamare `SendOutboundTicketMail::run()` una volta per destinatario —
  lo stesso Action pensato per un singolo utente, in loop. `Mail::assertQueued(MailableClass::class,
  $count)` (secondo argomento intero) verifica il numero di invii in test, stesso idioma di
  `Queue::assertPushed(JobClass::class, $count)`.
- Gotcha Larastan: un accesso nullsafe (`$report->ownerOrganization?->users`) su una relazione `BelongsTo`
  la cui firma è annotata `@return BelongsTo<Organization, $this>` (senza `|null`) produce l'errore
  `nullsafe.neverNull` — Larastan la considera mai-null indipendentemente dalla nullabilità reale della
  foreign key a livello di colonna DB. Verificare il tipo di ritorno annotato sul metodo relazione prima
  di aggiungere un nullsafe "difensivo": nel contesto chiamante è spesso davvero superfluo.
